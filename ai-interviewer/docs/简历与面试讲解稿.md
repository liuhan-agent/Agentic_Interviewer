## 2. 30 秒讲解

我做的是一个生产化的 AI 模拟面试系统，不是普通聊天机器人。主链路用 LangGraph 编排多个 agent 完成面试设置、问题生成、回答评估、追问、最终报告和复练建议；外层补了账号登录、面试记录归属、平台额度账本、BYOK、admin 后台和生产预检。这个项目的重点是把 agentic workflow 和真实产品需要的 control plane 接起来，让它不只是能跑一场面试，而是能恢复、能归属、能计费、能运营、能做上线前风险检查。

## 3. 2 分钟讲解

这个项目叫 Agentic Interviewer，是一个 AI 模拟面试系统。它的产品目标不是让用户玩模型，而是完成一次高质量模拟面试，并拿到结构化反馈和复练建议。

后端我用 FastAPI 和 LangGraph 搭了面试主链路。一次面试会经过 setup、简历/JD 解析、self intro、director 策略选择、ask question、wait answer、evaluator 评分、verifier 校验、reward update、follow-up 或下一题，最后生成 report 和 training plan。这里不是简单地调用一次 LLM，而是一个多轮 HITL 状态机，用户回答、模型评估、追问策略和最终报告都在统一状态里推进。

为了让主链路更像真实产品，我又补了 control plane。用户可以注册登录，登录后的面试记录绑定账号；未登录时也能体验，但匿名记录只属于本浏览器，必须显式保存到账号才会归属。平台托管模型调用用额度控制，一场面试扣一次；如果用户配置个人 API Key，也就是 BYOK，就不消耗平台额度。额度变化用 append-only ledger 记录，admin 可以手动调整，也可以审批用户的额度申请。

Admin 侧我做了 role=admin 的后台，不再依赖普通用户拿 admin token。后台能看用户、禁用普通账号、查额度、查账本、处理额度申请、看面试历史和 trace explorer。最后我还加了 production preflight 和 runbook，比如生产环境会拦住 memory backend、stub LLM、缺 admin token，以及“开放注册 + 免费额度 + 不要求邮箱验证”的危险组合。

所以这个项目我想展示的不是单点功能，而是一个完整闭环：agentic workflow runtime、账号与归属、平台使用治理、admin observability，以及上线前的工程边界。

## 4. 架构讲解版本

如果面试官让你画架构，可以按四层讲：

1. **Frontend 层**：Next.js 负责 setup、interview room、report、history、account dialog 和 admin panel。前端尽量薄，核心面试状态由后端返回。
2. **API/control-plane 层**：FastAPI 负责 auth、account、interview、voice、admin、credits、credit requests 和 production preflight。
3. **Workflow runtime 层**：LangGraph 负责多节点面试状态机，包括 director、generator、evaluator、verifier、reward update、final report。
4. **Data/runtime dependency 层**：Postgres 保存 session、checkpoint、账号、额度、trace；Redis 做 rate limit、cache、voice ticket；Chroma/knowledge files 做检索和上下文支撑。

一句架构总结：

> 前端负责体验，FastAPI 负责产品边界，LangGraph 负责面试状态机，Postgres/Redis/Chroma 负责持久化、共享状态和检索，Admin/credits/auth 把 workflow 包成一个可运营的产品。

## 5. 核心难点

### 难点 1：不是一次 LLM 调用，而是多轮 HITL 状态机

面试不是问一句答一句就结束。系统需要知道当前轮次、上一题、用户是否已回答、评分是否完成、是否需要追问、是否可以生成报告，还要支持刷新和恢复。所以我把它设计成 LangGraph 状态机，而不是普通 request-response 调用。

### 难点 2：匿名体验和账号归属要同时存在

一开始为了降低门槛，匿名用户也能体验。但账号化后，如果直接把本地历史混进账号记录，用户会误以为新注册账号继承了旧数据。所以我把账号记录和本机匿名记录分区展示，匿名记录需要有效凭证并由用户显式 claim 后才进入账号。

### 难点 3：平台 Key 和 BYOK 的资源边界

平台托管 Key 会消耗我的模型额度，所以需要 credits gate；BYOK 消耗的是用户自己的服务额度，所以不能扣平台次数。这里不仅是 UI 文案问题，还要在 start session 的 billing mode 上区分 `platform_credits`、`byok` 和 dev unmetered。

### 难点 4：Admin 不能只是一个 token 页面

早期 admin token 适合开发调试，但产品化后普通用户不能看到后台，也不能靠共享 token 当身份。所以我补了 role=admin、promote_admin 脚本、AdminAccessGate、后端 admin role gate，同时保留 API_TOKEN 作为 emergency fallback。

### 难点 5：生产化不是上线按钮，而是危险配置要能被拦住

这个项目里生产 preflight 会检查 memory backend、stub LLM、缺 API_TOKEN、voice ticket 后端、rate limit 后端、开放注册免费额度等问题。这样不是靠人记住所有风险，而是在 `APP_ENV=prod` 时直接失败启动。

## 6. 面试追问 Q&A

### Q1：为什么用 LangGraph，而不是普通链式调用？

因为面试是一个有状态、多轮、可中断、可恢复的流程。普通链式调用适合线性任务，但面试需要根据用户回答决定追问、换题、验证或结束，还要保留 HITL 中断点。LangGraph 可以把这些节点和条件路由显式建模，让状态推进、恢复和 trace 更清楚。

### Q2：多 agent 是怎么分工的？

我没有把所有事情塞进一个大 prompt，而是按职责拆分：Director 负责下一步策略，Generator 负责生成问题，Evaluator 负责按 rubric 评分，Verifier 负责边界答案校验，Guard/contract 相关逻辑负责约束输出和安全边界。这样每个 agent 的输入输出更稳定，也方便在 admin trace 里定位问题。

### Q3：RAG 在这个项目里起什么作用？

RAG 不是为了堆知识库，而是为了给面试提供更贴近候选人和岗位的上下文。项目里有简历/JD 解析、session anchors、结构化题库、skill playbook 和 Chroma/BM25 检索。Generator 可以基于这些上下文生成更具体的问题，Evaluator/报告也能更好地引用候选人的回答和项目经历。

### Q4：为什么要做 verifier？

Evaluator 评分可能会受模型不稳定、证据不足或边界答案影响。Verifier 是一个质量闸门，用来对边界情况做二次检查，尤其是 senior、system design 或容易 bluff 的维度。它不是每轮都无脑调用，而是通过规则和 drift 观测控制触发。

### Q5：session recovery 是怎么考虑的？

面试是 HITL 流程，用户可能刷新页面、断线、服务重启。后端用 Postgres checkpoint 和 session persistence 保存关键状态；前端保存恢复凭证，但不把高敏 session token 长期放在 localStorage。这样可以恢复会话，又尽量减少凭证泄漏风险。

### Q6：为什么匿名记录不能直接算账号记录？

因为匿名记录的归属只证明“这个浏览器曾经访问过”，不证明“当前登录账号拥有它”。如果新注册账号直接看到旧匿名记录，会产生数据归属误解。所以登录后主列表只展示账号记录，匿名记录放在单独区块，用户显式保存到账号时才 claim。

### Q7：为什么要做额度账本，而不是只存一个 balance？

只存 balance 很难解释“为什么少了/多了几次”。append-only ledger 可以记录免费赠送、面试扣减、退款、admin 调整和额度申请审批，方便用户理解，也方便 admin 排查。cached balance 负责查询效率，ledger 负责可追溯性。

### Q8：BYOK 和平台托管 Key 怎么隔离？

Start session 时会解析 LLM config。如果用户传了个人 API Key 或 role override key，就判定为 BYOK，不扣平台额度；生产环境下没有 BYOK 就走 platform credits，要求登录并扣 1 次。平台 Key 只放后端环境变量，不能进入 `NEXT_PUBLIC_*`。

### Q9：admin 权限怎么设计？

普通账号是 `role=user`，后台账号是 `role=admin`。Admin API 优先检查 active admin cookie；`API_TOKEN` 只保留为 bootstrap/emergency fallback。前端也用 AdminAccessGate 包住后台页面，不让普通登录用户直接看到后台数据。提升 admin 不开放 UI，只通过后端 promote 脚本做。

### Q10：生产 preflight 解决什么问题？

它解决“开发默认配置误上生产”的问题。比如 memory checkpoint 会导致重启丢会话，stub LLM 会让生产报告来自假模型，开放注册加免费额度会被滥用。preflight 在 `APP_ENV=prod` 下会把这些高风险组合直接变成启动失败。

### Q11：项目里最有工程含量的部分是什么？

我会说是把 agentic workflow 和 control plane 接起来。单独做一个 LangGraph demo 不难，单独做登录/后台也不稀奇；难点是让面试主链路、账号归属、额度扣减、BYOK、admin、生产预检这些边界互相一致，不让用户体验、资源治理和数据归属脱节。

### Q12：如果继续做 Phase 3.x，你会补什么？

我会优先补邮箱验证或邀请码，解决公开注册和免费额度防滥用；其次是密码找回、账号安全和 admin action audit log；再往后才是支付、会员、订单账本和自动充值。也就是说，公开上线前先补安全和运营边界，再补商业化。

### Q13：这个项目现在为什么不继续做支付？

因为当前目标是作品集收口。支付、会员、发票、退款、风控、客服流程都会把项目带进商业运营长尾。现在这个项目已经能证明 workflow、control plane 和 production readiness，继续做支付的边际收益不如整理 README、架构说明和面试讲解材料。

### Q14：这个项目有什么不足？

我会主动承认三点：第一，公开上线前还需要邮箱验证或邀请码来控制注册滥用；第二，支付和会员还只是 backlog，没有正式接入；第三，生产部署虽然有 runbook 和 smoke drill，但还可以进一步做 CI/CD、监控告警、备份恢复演练和安全审计。这样回答比硬说“都做完了”更可信。

## 7. 不建议这样讲

不要说：

- “我做了一个 AI 面试聊天机器人。”
- “我接了登录和后台。”
- “这个项目可以直接商业化上线。”
- “admin token 就是管理员账号。”
- “BYOK 和平台 Key 都差不多。”

建议说：

- “我做的是 agentic mock interview workflow，不是单轮聊天。”
- “账号、额度、admin 是围绕主 workflow 的 ownership/control-plane。”
- “当前适合作品展示和 private beta，公开上线前还要补邮箱验证/邀请码。”
- “admin role 是产品化权限，API_TOKEN 只是 bootstrap/emergency fallback。”
- “BYOK 不扣平台额度，平台托管模式才走账号 credits。”

## 8. 最后收尾口径

如果面试官问“你为什么停在这里”，可以这样答：

> 我把这个项目停在 Phase 3.0，是因为主 workflow、账号归属、额度治理、admin 后台和 production readiness 已经形成闭环。继续往下做会进入邮箱验证、邀请码、支付、会员、审计、运维这些商业化长尾。它们我已经在 backlog 里明确了，但对当前作品集来说，先把项目讲清楚、验证清楚、收口清楚，比继续堆功能更有价值。
