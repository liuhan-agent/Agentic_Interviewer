# 锚点 chunk 双轨合并与粒度问题

> 日期：2026-05-21
> 状态：draft
> 标签：ai-interviewer, rag, chunking, retrieval, debugging

## 一句话结论

候选人锚点 RAG 的召回质量不只取决于 embedding 和 retriever，chunk 生成如果只信 parsed projects 或 LLM anchor cards，就会出现“有向量但锚点过粗”的隐性失效。

## 背景

Session Anchor RAG 的目标是把候选人的简历项目和自我介绍重点转成可检索的语义锚点，供正式题和追问使用。这个链路看起来可以拆成：解析资料、切分 chunk、embedding、写入 PgVector、检索、放进 prompt。

实际调试中，最容易误判的是“PgVector 里有 rows”就等于 RAG 正常。用户用真实 Java 后端简历和真实自我介绍跑面试后发现，系统确实写入了向量，但 resume 只有 2 个粗 chunk，self_intro 命中也不稳定。问题不是向量库没有数据，而是 chunk 粒度没有承载足够具体的可追问事实。

## 现象

### 事实

- 用户跑 session 后发现 Session Anchor RAG 有时没有有效命中，最初怀疑是 query 和 self_intro chunk 相似度没过阈值。
- 用户进一步指出“也可能是 self_intro 切块的粒度问题”，随后又发现 resume rows 只有 2 个。
- 用户上传 `刘韩 - Java后端_测试.pdf` 作为真实样本，询问 resume chunk 是否合理。
- 排查后确认：当前 Mode A 在 parsed projects 非空时提前 return，导致只生成少量项目级粗 chunk。
- 这类粗 chunk 虽然可以 embedding，但单个 chunk 混合了项目背景、职责、技术、成果，后续 query 很难精准命中特定技术或追问点。
- 修复方案将 resume chunker 改成 `parsed anchors + raw text anchors` 双轨合并：
  - parsed projects / skills / focus_areas 生成结构化 anchors。
  - raw text 中的项目经历、技术亮点、职责、成果继续补充 anchors。
  - 去重、排序、限量，Mode A 最多 24 个 chunks。
- self_intro 也暴露出相似问题：如果只信 LLM 返回的 `anchor_cards`，可能只得到 1 张 summary 卡或泛泛卡。
- 修复方案将 self_intro 改成 `LLM cards + deterministic supplement` 双轨合并：
  - LLM cards 优先，但要经过质量闸门。
  - 规则从自我介绍原文、项目名、技术词、profile fields 中补具体 cards。
  - 中等文本和长文本用不同策略，最终最多 8 张 cards。

### 推断

- RAG 质量的第一层瓶颈可能在 chunker，而不是 embedding model 或向量距离阈值。
- 结构化解析结果适合提供项目名、技术栈、职责字段，但不一定覆盖原文里的所有细节。
- 原始文本适合补充模块化标题、时间段、bullet、技术词和结果描述，但需要去重和上下文增强，避免碎片失语义。
- LLM 生成的 self_intro anchor cards 适合抓语义重点，但它可能保守、泛化或漏掉可追问事实，因此需要 deterministic supplement 兜底。

### 未确认假设

- Mode A 最多 24 个 resume chunks 是否适合所有简历长度和岗位类型，还需要更多样本验证。
- self_intro 最多 8 张 cards 是否足以覆盖长自我介绍中的多项目、多技术、多结果表达。
- chunk 粒度变细后，retriever 的 `top_k_resume=2` 和 `top_k_self_intro=1` 是否仍是最佳配比。
- 技术词典是否需要继续扩充，尤其是中文简历里的大小写、别名和国产中间件表达。

## 期望行为

一份项目丰富的简历不应只产出 1-2 个项目级粗 chunk，而应拆出项目摘要、职责、技术、难点、成果、focus、skill 等可独立追问的 anchors。

一段正常自我介绍也不应只产出整段 summary embedding，而应拆出候选人主动强调的项目、技术、职责、难点、结果或 claim。长自我介绍需要先分段，再保留高信息片段。

最终写入 PgVector 的 rows 应该能支撑这样的查询：问 Redis Lua 原子扣减时能命中相关项目锚点，问 Flowable 或 XXL-JOB 时能命中对应技术锚点，问候选人自称解决过的问题时能命中自我介绍里的主动 claim。

## 根因判断

直接原因：

- resume Mode A 在 parsed projects 非空时提前返回，跳过 raw text anchors，导致 chunk 只有项目级粗粒度。
- self_intro 向量化过度依赖 LLM `anchor_cards`，当 LLM 返回 summary 或泛泛卡片时，fallback 仍可能太粗。

深层原因：

- 早期把“解析结果存在”误当作“anchor 质量足够”，没有单独验证 chunk 是否可支撑一道具体追问。
- chunker 的职责不是简单分段，而是把候选人材料转成可检索、可引用、可追问的事实单元。
- 结构化解析和原始文本各自都有盲区；单轨方案容易在真实简历格式、中文模块标题、项目 bullet、口语自我介绍里失真。

触发条件：

- 简历解析产出了 projects，因此 Mode A 走 parsed projects 快路径。
- 项目经历较丰富，但每个项目内含多个技术点、职责和结果。
- 自我介绍较长或较口语化，LLM 倾向总结而不是拆事实卡。

## 调试过程

1. 先看 RAG 是否有写入向量库，确认不是纯粹的 embedding 失败。
2. 观察 retriever 命中不稳定，初步怀疑 query 相似度和阈值。
3. 用户指出 self_intro 可能存在切块粒度问题。
4. 进一步检查 resume rows，发现真实简历只生成 2 个 chunks。
5. 回看 chunker 逻辑，定位 Mode A parsed projects 非空时提前返回。
6. 设计 resume 双轨方案：parsed anchors 保留结构化优势，raw text anchors 补充模块化和非结构化细节。
7. 设计 self_intro 双轨方案：LLM cards 提供语义判断，deterministic supplement 补具体事实和长文本分段。
8. 增加测试覆盖，确保新 session 的 resume rows 不再只有 2 条，self_intro 不再只有粗 summary card。

## 解决方式

- Resume chunker：
  - `_chunk_mode_a()` 不再在 parsed chunks 非空时提前 return。
  - 从 `projects / focus_areas / skills` 生成 parsed anchors。
  - 从 raw text 模块标题、日期、bullet、技术词中生成 raw anchors。
  - 项目 detail chunk 带项目名和技术栈上下文，避免单条 bullet embedding 失去语义。
  - 增加中文模块识别和技术词典。
  - 去重后按项目摘要、parsed detail、focus/skill、raw text anchors 排序，最多 24 个。
- Self-intro cards：
  - 优化 LLM prompt，要求每张卡必须支撑一道具体追问。
  - `_clean_anchor_cards()` 丢弃泛泛、过短、重复、无追问价值的卡。
  - deterministic supplement 从自我介绍原文和 profile fields 中补 project、tech、responsibility、difficulty、result、claim cards。
  - 长文本先按话语标记、句子和项目名分段，再从高信息片段补卡。
  - 最终 cards 统一去重、限量、排序，并记录 `source = llm | supplement | fallback`。

## 验证方式

- Resume chunker 测试覆盖：
  - parsed 项目夹具不再只有 2 个 chunks，数量在合理范围内。
  - chunk 文本覆盖 `Flowable`、`Redis Hash`、`XXL-JOB`、`Lua`、`RabbitMQ`、`RAG` 等关键锚点。
  - 中文 raw text 仅靠“项目经历 + 中文日期 + bullet”也能生成 project / highlight / skill chunks。
  - parsed + raw 重复时不重复写入，最终不超过 24。
- Session vectorize 测试覆盖：
  - parsed 项目输入调用 `vectorize_resume()` 后写入 resume rows 数量大于 2。
  - self_intro 向量化写入多张 cards，`chunk_index` 连续。
  - `self_intro_vector_status.strategy`、`card_sources`、`card_count_by_kind` 可用于排查。
- 手动验证：
  - 新上传同类简历并开启 session 后，`session_anchor_chunks` 中 resume rows 约 10-24 条，而不是 2 条。
  - 新 self_intro 通常产生 3-8 张可追问 cards。

## 可复用教训

- RAG 排查顺序不能只看“有没有 rows”，还要看 rows 是否是可追问事实单元。
- parsed-only 是快路径，不是质量保证；只要真实输入有格式差异，就需要 raw text supplement。
- LLM cards 适合表达语义，但不能独占事实抽取入口；规则补卡能提供稳定的召回底座。
- 每个 chunk/card 都应该能回答一个问题：它能直接支撑一道追问吗？如果不能，就太泛或太碎。
- Chunk 变细后要保留上下文，例如项目名、技术栈、角色，否则 embedding 会失去语义锚点。
- 粒度修复会影响 retriever 参数，chunker 改完后应重新观察 `top_k`、阈值、prompt block 长度。

## 未解问题

- 是否需要为不同岗位和简历长度动态调整 Mode A 最大 chunks 数。
- 是否要把 retriever 从固定 `top_k_resume=2` 扩展为按 query 意图或 source_type 动态配额。
- 是否需要 mid-interview adhoc claim anchors，把候选人在中途新提到但不在简历/自我介绍里的项目也入库。
- 是否需要更系统的 chunk quality eval，例如检查每个 chunk 是否包含项目名、技术点、行动和结果中的至少两类信息。
