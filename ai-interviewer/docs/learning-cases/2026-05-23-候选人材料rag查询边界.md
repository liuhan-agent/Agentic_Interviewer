# 候选人材料 RAG 查询边界

> 日期：2026-05-23
> 状态：draft
> 标签：ai-interviewer, rag, retrieval, resume-anchor, boundary

## 一句话结论

resume/self_intro RAG 的主 query 应该由当前 `resume_anchor` 驱动；自我介绍是 boost，dimension、target skills 和 seed 是约束或 rerank 信号，不能混成一条杂 query。

## 背景

在讨论“标准/深度面试按多个简历锚点展开”时，用户追问 RAG query 是否就是 `focus_areas`，并明确支持“被选中的 focus_area 更适合做 query”。随后继续拆解 resume RAG、self_intro RAG 和普通知识 RAG 的边界，最后拍板把候选人材料 RAG 改成三路 query 与 Top N 排序。

## 现象

### 事实

- 原 query 倾向把选中的简历锚点、自我介绍强调内容、当前维度、目标技能、seed 场景拼在一起。
- 用户指出 query 内容可能杂乱，并追问这是否会影响 resume/self_intro RAG。
- 用户确认：`resume_anchor` 才更适合语义检索 resume RAG 和 self_intro RAG。
- 用户拍板三路方案：
  - `anchor_query`：主检索
  - `boost_query`：带锚点限定的自我介绍增强
  - `constraint_query`：不单独向量检索，只做 rerank
- 普通知识 RAG 保留为 fallback / supplement，不再承担候选人事实 grounding。

### 推断

- 如果把 anchor、self-intro、dimension、seed、target skills 全拼进一条 query，embedding 会被多个意图拉扯，命中结果可能贴维度但不贴候选人经历。
- `boost_query` 必须带上 `resume_anchor.label/project_name`，否则自我介绍强调内容可能把检索带到另一个项目。
- `constraint_query` 更适合做可解释 rerank，而不是单独召回，否则容易把泛技术材料拉进候选人事实 RAG。

### 未确认假设

- `anchor 0.70 / boost 0.20 / constraint 0.10` 的默认权重是否最优，需要更多真实 session 命中质量验证。
- 不同简历质量和不同自我介绍长度下，boost query 的收益可能差异较大。

## 期望行为

当前题目选择了某个 resume anchor 后，候选人材料检索应优先围绕该锚点的 label、project、skills、tech stack、question anchors 和 dimensions。自我介绍只增强这个锚点相关的语义，不应反客为主。维度、目标技能和结构化题库 seed 只作为约束项影响排序解释，不单独产生候选 chunk。

## 复现线索

- 讨论场景：用户从“简历锚点怎么选”追问到“RAG query 是不是 focus_areas”。

  - 普通知识 RAG 和候选人材料 RAG 的职责边界容易混淆。
  - `constraint_query` 的作用需要解释为 rerank，而不是第三路召回。

## 根因判断

直接原因：

- 单条拼接 query 同时承担主检索、boost 和约束职责，导致检索意图不清。

深层原因：

- RAG query 里混合了三种不同语义：
  - 候选人事实主语：当前 resume anchor。
  - 候选人自述增强：self intro emphasized fields。
  - 出题约束：dimension、target skills、seed。
- 这些语义在排序阶段可以协作，但不应该在 embedding query 阶段无差别混合。

触发条件：

- 当前题目有明确 resume anchor。
- 自我介绍强调了多个项目或技能。
- seed 场景或目标技能与当前 anchor 只有部分相关。

## 调试过程

1. 先确认普通知识 RAG 不再承担候选人事实 grounding，主要是 fallback / supplement。
2. 明确 resume/self_intro RAG 的主语应该是当前被选中的 resume anchor。
3. 讨论自我介绍是否影响简历锚点，结论是只做 query boost，不反向改变锚点选择。
4. 拆解三部分 query 内容：anchor、boost、constraint。
5. 解释 constraint 的作用：不召回，只给候选 chunk 加可解释排序分。
6. 拍板权重：`anchor 0.70 / boost 0.20 / constraint 0.10`。
7. 实现 merge/dedupe/rank，artifact 保留分项分数和 query profile。

## 解决方式

- `anchor_query` 单独 embedding，作为主检索。
- `boost_query` 在有 self-intro boost terms 时单独 embedding，并强制带 anchor/project 限定。
- `constraint_query` 不 embedding，只计算 `constraint_match`。
- 候选 chunk 按 identity merge/dedupe，最终分为：
  - `0.70 * anchor_score`
  - `0.20 * boost_score`
  - `0.10 * constraint_match`
  - 减去 used project penalty
- artifact 中保留 `anchor_query_text`、`boost_query_text`、`constraint_query_text`、`ranking_weights` 和每条 hit 的分项分数。

## 验证方式

- focused tests 覆盖 anchor/boost 分别调用 embedding、constraint 不触发第三次 embedding、boost 失败 fail-open、hash 型 anchor_key 不污染 query。
- ask_question flow 测试确认 `resume_rag_mode=primary` 时候选人材料 RAG 注入 Generator。
- docs 测试确认默认 primary 与 shadow/off 回滚说明。

## 可复用教训

- RAG query 设计要先区分“主召回语义”“增强信号”“约束信号”。
- 不是所有影响排序的文本都应该进入向量检索。
- 当前业务实体的主语必须清楚；在候选人材料 RAG 中，主语就是当前 resume anchor。
- artifact 要保留 query profile 和分项分数，否则后续很难解释为什么命中某个 chunk。

## 这次容易误判的地方

- 看到 query 里包含了 dimension、target skills 和 seed，容易认为信息越多越好。对 embedding 来说，信息过多可能稀释当前 resume anchor，导致命中贴技术主题但不贴候选人经历。
- 看到 self-intro 强调某个项目，容易让它反向影响锚点选择。更稳妥的边界是：锚点选择仍由调度层决定，自我介绍只在当前锚点范围内做 boost。
- 看到 constraint terms 和 anchor terms 都是文本，容易想让 constraint 也单独检索。这样会把“约束”变成第三路召回，增加泛技术材料进入候选人事实 block 的风险。
- 看到结构化题库 seed 命中，容易把所有 RAG 都压掉。实际只应该压普通知识 RAG，不应该压掉候选人材料 RAG。
- 看到 `anchor_key` 可用，容易把它直接塞进 query。hash 型 key 对 embedding 没有语义价值，只有可读语义 key 才适合拆词辅助。

## 下次优先检查项

1. 先打印 artifact 里的 `anchor_query_text`、`boost_query_text`、`constraint_query_text`，确认三者职责没有混在一起。
2. 检查 boost query 是否带着 `resume_anchor.label` 或 `project_name`，防止自我介绍把检索带到其他项目。
3. 检查 constraint 是否只参与 `constraint_match`，没有触发第三次 embedding。
4. 对每条 hit 同时看 `anchor_score`、`boost_score`、`constraint_match` 和 `final_score`，不要只看一个总分。
5. 如果候选人材料 RAG 没命中，先看 query profile 和 chunk identity，再看向量距离阈值；不要直接归因于 embedding provider。

## 未解决问题

- 权重是否需要按 source_type、面试深度或维度动态调整。
- 如果 boost query 长期贡献很低，是否需要改为只在自我介绍明确提到当前项目时启用。
- used project penalty 的强度是否需要和锚点调度层联动。
