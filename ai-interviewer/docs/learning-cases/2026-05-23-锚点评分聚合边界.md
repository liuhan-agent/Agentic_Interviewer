# 锚点评分聚合边界

> 日期：2026-05-23
> 状态：draft
> 标签：ai-interviewer, scoring, resume-anchor, aggregation, boundary

## 一句话结论

同维度多轮评分不能只按 turn 序列聚合；当问题围绕不同简历锚点展开时，应按 `turn -> anchor -> dimension` 的层级汇总。

## 背景

在讨论“标准/深度面试按多个简历锚点展开”后，用户追问同一个维度多轮 turn 在面试报告里的维度总分是否仍然正确。继续分析后确认：同维度同锚点的第二轮追问，和同维度不同锚点的横向覆盖，评分语义不同，不能用同一套简单 turn 聚合解释。

## 现象

### 事实

- 原先维度总分更接近按 turn 序列聚合。
- 用户拍板采用最推荐版本：
  - same anchor：`weighted_recent`
  - multi-anchor dimension：`0.8 * anchor_average + 0.2 * best_anchor_score`
  - unanchored turns：`unanchored:{dimension}`
  - `dimension_status` 不变
  - 不改 DB schema
- 后续真实会话中出现报告解释：“本维度综合了 2 个简历锚点，锚点均值 8.5，最佳锚点 9.0；综合分 8.6。”
- 用户进一步确认“2 个简历锚点”和“同一高价值锚点最多问 2 轮”需要在概念上区分。

### 推断

- turn 是出题粒度，anchor 是证据主题粒度，dimension 是评分维度粒度。
- 同一 anchor 的第二轮追问更像对同一证据主题的加深，应给近期回答更高权重。
- 不同 anchor 代表同一维度下的多个事实主题，维度分应体现平均覆盖，同时保留最佳锚点的亮点贡献。

### 未确认假设

- `0.8 / 0.2` 的权重是否适合所有维度，需要后续真实评分分布验证。
- 未绑定锚点的 turn 是否都应该合并到 `unanchored:{dimension}`，未来如果有更多非简历来源，可能需要更细分。

## 期望行为

报告计算维度总分时，先把同一维度内的 turn 按 resume anchor 分组。每个 anchor 内用 weighted recent 得到锚点分；同一维度多个 anchor 时，用锚点均值和最佳锚点分混合得到维度总分。未绑定锚点的 turn 使用稳定的 unanchored key 参与同一层级聚合。

## 复现线索

- 讨论场景：用户从“同维度多个简历锚点展开”追问报告维度总分是否正确。
- 关键问题：
  - 同维度同锚点多轮，是深挖同一证据主题。
  - 同维度不同锚点多轮，是覆盖多个候选人经历。
  - 二者都表现为同一维度多个 turn，但评分含义不同。

## 根因判断

直接原因：

- 面试调度从“维度覆盖”升级到“维度内多个简历锚点展开”后，原有按 turn 聚合的维度分语义不够精确。

深层原因：

- 评分层级没有显式表达锚点这一中间层，导致同锚点追问和多锚点覆盖都被压扁成 turn 序列。
- 报告解释如果只说“多轮综合”，用户无法判断这是同一经历被追问，还是多个经历共同贡献。

触发条件：

- 一个维度下问到多个 resume anchor。
- 一个高价值 anchor 被问到第 2 轮。
- 某些 turn 没有 resume anchor，需要兼容旧数据或非简历题。

## 调试过程

1. 用户先确认标准/深度模式会围绕多个简历锚点展开。
2. 随后追问同一维度多轮 turn 的维度总分是否仍然正确。
3. 区分同维度同锚点和同维度不同锚点两种情况。
4. 拍板聚合策略：same anchor 用 weighted recent，multi-anchor 用 `0.8 * anchor_average + 0.2 * best_anchor_score`。
5. 使用 TDD 实现，保持 `dimension_status` 和 DB schema 不变。
6. 新会话报告中出现多锚点解释后，再确认“锚点数量”和“锚点第几轮追问”的前端文案应区分。

## 解决方式

- 维度分从 turn 序列升级为锚点分序列汇总。
- 同一 anchor 内采用 weighted recent，体现追问后的最近证据。
- 多 anchor 维度采用锚点平均和最佳锚点混合，兼顾稳定覆盖和亮点表现。
- 未绑定锚点的 turn 使用 `unanchored:{dimension}` 保持兼容。
- 报告保留 `dimension_status` 语义，避免把“未评分/证据不足”等状态和聚合算法混淆。

## 验证方式

- focused tests 覆盖同锚点、多锚点、unanchored、status 不变。
- 后端全量单测最终通过：`1820 passed, 2 skipped`。
- 真实 session 报告出现锚点级聚合解释，手动确认和会话 turn 分布一致。

## 可复用教训

- 当调度层新增业务实体后，评分层也要检查是否需要同样的实体层级。
- turn 是记录单位，不一定是评分语义单位。
- 报告解释应区分“覆盖了几个锚点”和“某个锚点追问到第几轮”。
- 不改 DB schema 时，也可以通过现有 turn metadata 重建更准确的聚合语义。

## 这次容易误判的地方

- 看到同一维度出现多轮 turn，容易直接套用“越新的回答越重要”。这只适合同一锚点追问，不适合多个锚点共同覆盖同一维度。
- 看到报告里写“2 个简历锚点”，容易和“同一个高价值锚点最多问 2 轮”混淆。前者是覆盖了两个不同证据主题，后者是同一主题被追问到第几轮。
- 看到维度分没有明显异常，容易忽略解释语义。即使数值大致合理，如果解释不能说明 anchor 层级，用户仍然难以理解分数来源。
- 看到不改 DB schema 的约束，容易以为无法做锚点级聚合。实际只要 turn metadata 中有稳定 anchor key，就可以在报告生成阶段重建层级。
- 看到 `dimension_status` 已经能表达 scored/unscored，容易把它和聚合算法混在一起。状态表示是否可评分，算法表示如何汇总可评分证据。

## 下次优先检查项

1. 检查每个 scored turn 是否有 `resume_anchor_key`；没有时是否落到稳定的 `unanchored:{dimension}`。
2. 对同一维度先按 anchor 分组，再检查每组内的 turn 次序和 weighted recent 是否符合预期。
3. 对多 anchor 维度，手算一次 `0.8 * anchor_average + 0.2 * best_anchor_score`，确认报告分和解释一致。
4. 检查报告文案是否同时能解释“多锚点覆盖”和“单锚点追问”，不要用同一个短语覆盖两种语义。
5. 确认 `dimension_status` 不因聚合策略改变而漂移；证据不足仍应保留原本状态。

## 未解决问题

- 是否需要在报告 API 中显式暴露 anchor-level breakdown 的完整结构，而不是只给解释文案。
- 未来如果引入岗位要求锚点、自我介绍锚点，是否仍与 resume anchor 共用同一聚合层。
