# 简历向量缓存与 session 隔离删除语义

> 日期：2026-05-21
> 状态：draft
> 标签：ai-interviewer, rag, cache, privacy, boundary

## 一句话结论

同一份简历的向量可以跨面试复用，但检索、报告、隐私删除仍必须保持 session-scoped，所以 v1 更适合“全局缓存 + 绑定时复制”，而不是让 retriever 直接跨 session 查共享表。

## 背景

Session Anchor RAG 最初按 session 维度设计：每场面试把简历和自我介绍转成 `session_anchor_chunks`，retriever 只按当前 `session_id + source_revision_id + embedding_model_version` 查询。这保证了面试隔离和隐私清理语义。

用户随后提出一个成本和体验问题：同一份简历可能会跑多场面试，AI 简历解析已经有缓存，Session Anchor RAG 是否也可以缓存或复用。这个问题把两个维度拆开了：embedding 成本与简历内容相关，但检索边界与 session 相关。

## 现象

### 事实

- 首次同简历面试需要 chunk + embedding + 写入 PgVector，耗时和 Qwen embedding 调用成本都较明显。
- 第二场同简历面试在内容、chunker 版本、embedding model version 都相同时，理论上可以复用同一批 resume vectors。
- 直接让 retriever 查全局共享表会改变原有隔离模型：原本所有候选人 anchors 都是 session-scoped rows。
- 已拍板 v1 采用“全局简历向量缓存 + session 绑定时复制”：
  - 首次 cache miss：正常写当前 session rows，并把同一批 redacted chunks + embeddings 存入 `resume_anchor_cache_chunks`。
  - 后续 cache hit：不调用远程 embedding，直接复制 cache rows 到当前 session 的 `session_anchor_chunks`，生成新的 `resume_revision_id`。
  - retriever 仍只查当前 session rows，不直接 join 或查询全局 cache 表。
- 后续又补了 retention 策略：
  - global resume cache TTL 默认 7 天。
  - session-bound anchor rows 保留时间从较短窗口延长到约 7 天以上，以支持拖得较久的面试恢复。
  - 面试完成时自动清理该 session 的 session anchor rows，但不影响正常可复用的 global cache，除非走显式隐私删除。
- 实测两场同简历面试：
  - `sess-20260521-084109-65e24d` 首场 cache miss，写入 resume rows 并生成 global cache。
  - `sess-20260521-084651-6d1d32` 第二场 cache hit，复制 rows 到新 session，Session Anchor RAG 仍正常命中。

### 推断

- “能复用”不等于“可以共享检索边界”。缓存表属于成本优化层，session rows 属于业务语义层。
- copy-on-bind 比 retriever join 更适合 v1，因为它保持了现有 `session_anchor_chunks` 查询、Admin metrics、trace 和删除路径的语义稳定。
- global cache 不能存原始简历、parsed JSON 或 API Key，只能存 redacted chunk 文本、metadata、embedding 和缓存等价信息。
- 删除语义需要区分“用户显式删除某场面试的锚点数据”和“系统为了节省成本保留可复用缓存”。

### 未确认假设

- global cache TTL 7 天是否是成本和隐私之间的最佳平衡。
- 显式删除 session anchor 时同步删除对应 global cache 是否过于保守；从隐私预期看保守更安全，但会降低后续复用率。
- 未来如果 cache hit 量很高，copy-on-bind 带来的重复 session rows 是否需要优化。
- Admin 是否需要展示 cache hit/miss、source_cache_key、hit_count 等信息，帮助理解“为什么第二场更快”。

## 期望行为

同一份简历、同一 chunker 版本、同一 embedding model version 下，第一场面试可以正常消耗 embedding，第二场面试应尽量命中缓存，避免重复远程 embedding。

无论缓存是否命中，当前面试的 retriever 都只能查询当前 session 的 `session_anchor_chunks`。每场面试都有自己的 `resume_revision_id`，trace、Admin metrics、Generator prompt 都保持 session 语义。

当用户或管理员显式删除某场面试的 anchor data 时，该 session 的 rows 必须删除；如果这些 rows 来自 global resume cache，也应按当前隐私策略清理对应 cache rows。普通面试完成后的自动清理只应清理 session-bound rows，不应把 global cache 当成临时 session 数据误删。

## 根因判断

直接原因：

- 每场面试都按 session 重新 embedding 同一份简历，会重复消耗时间和 provider 调用成本。

深层原因：

- Session Anchor RAG 同时承担两个职责：检索时的 session 隔离和资料向量化的成本优化。二者等价边界不同，不能用同一张表和同一套语义粗暴解决。
- 业务层的 session rows 需要能被报告、trace、Admin、隐私删除明确归属；缓存层只应表达“这份 redacted resume anchors 在某个 chunker/version/model 下已经算过”。
- 如果为了省成本让 retriever 直接跨 session 查全局缓存，会把优化层泄漏到主链路，增加后续权限、删除、审计和调试复杂度。

触发条件：

- 同一候选人或同一简历反复开启新面试。
- embedding provider 较慢或需要 BYOK 成本控制。
- Session Anchor RAG 已经进入 primary prompt，首次向量化时间会影响用户对系统速度的感知。

## 调试过程

1. 用户提出“Session Anchor RAG 能做缓存吗，或者多份面试共用一个 Session Anchor RAG”，指出同一份简历会重复使用。
2. 分析两个方案：
   - 直接共享/引用全局 rows，成本低但破坏 session 查询和删除语义。
   - 全局缓存 + 绑定时复制，略有重复写入但保持现有主链路隔离。
3. 拍板 v1 使用 copy-on-bind。
4. 设计 cache key：由 redacted resume text hash、chunk-affecting parsed hash、chunker version、embedding model version 组成，不包含 API Key。
5. 新增 `resume_anchor_cache_chunks` 和 `session_anchor_chunks.source_cache_key`。
6. 改造 background resume vector job：先尝试 cache bind，命中则复制 rows，未命中则正常 embedding 并存入 cache。
7. 补 Admin 删除和清理脚本，避免 global cache 成为隐私清理盲区。
8. 用户担心 session-bound rows TTL 太短，可能影响长时间继续面试；后续补充延长 session retention，并在面试完成时自动清理 session rows。
9. 通过两场同简历面试验证 cache miss / hit 和 RAG 命中都正常。

## 解决方式

- 新增 global cache 表 `resume_anchor_cache_chunks`，存储：
  - redacted chunk text
  - chunk metadata
  - embedding vector
  - `cache_key`
  - `embedding_model_version`
  - `expires_at`
  - `last_used_at`
  - `hit_count`
- 在 `session_anchor_chunks` 上增加 nullable `source_cache_key`，记录当前 session rows 来自哪个 cache key。
- 新增 `resume_anchor_cache.py` 服务：
  - 生成 cache key。
  - 尝试把 cache rows 复制绑定到当前 session。
  - cache miss 后存储 cache rows。
  - 显式删除或过期清理 cache rows。
- `resume_vector_jobs`：
  - 先 consume parse artifact 并计算 cache key。
  - cache hit 时复制 rows，返回 `status="ready", cache_hit=true`。
  - cache miss 时正常 vectorize，返回 `cache_hit=false` 并写入 global cache。
- 清理策略：
  - 定时清理过期 global cache。
  - 面试完成自动清理当前 session 的 session-bound anchors。
  - 显式 `/admin/sessions/{session_id}/anchor-data` 删除 session rows，同时按 `source_cache_key` 清理对应 global cache rows。

## 验证方式

- 单元测试覆盖：
  - cache key 忽略 `parse_status.cached/cache_age_ms` 等非 chunking 字段。
  - parsed 项目内容、chunker version、embedding model version 变化会 cache miss。
  - cache hit 能复制 rows 到新 session，`session_id/source_revision_id/source_cache_key/chunk_index` 正确。
  - cache hit 不调用 `embed_chunks`。
  - cache write 失败不影响当前 session vectorization ready。
  - Admin `/anchor-data` 删除 session rows 时能删除相关 global cache rows。
  - 完成面试自动清理 session anchor rows，但不误删 global cache。
- 手动验证：
  - `sess-20260521-084109-65e24d` 首场为 cache miss，产生 global cache rows。
  - `sess-20260521-084651-6d1d32` 第二场为 cache hit，不重新发起远程 embedding。
  - 第二场仍拥有自己的 session rows 和新的 `resume_revision_id`。
  - Session Anchor RAG 在第二场仍正常进入主链路并命中 resume/self_intro anchors。

## 可复用教训

- 缓存等价条件和业务隔离边界不要混在一起；能复用计算结果，不代表能共享业务记录。
- 对含隐私数据的缓存，key、payload、TTL、删除语义要和功能一起设计，不能事后补。
- copy-on-bind 是适合 v1 的保守方案：它用少量存储冗余换来 retriever、trace、Admin 和隐私删除的稳定语义。
- cache key 不应包含 API Key，但必须包含 embedding model version；不同 provider/model/dimensions 的向量不能混用。
- 自动清理和显式删除不是同一语义：完成面试清理 session 临时数据，用户删除数据则应更保守地清理可追溯 cache。

## 未解问题

- global cache TTL 7 天是否需要按环境或用户隐私策略配置。
- 显式删除 session anchor 时同步删除 global cache 是否会过度降低命中率，是否需要未来提供更细的“删除本场数据 / 删除该简历缓存”语义。
- copy-on-bind 在大量重复面试下的存储放大是否可接受。
- 是否需要 Admin UI 展示 cache hit/miss、cache age、hit_count、source_cache_key。
- 未来是否要支持引用式检索；如果支持，需要重新设计权限、删除、trace 归属和 session metrics。
