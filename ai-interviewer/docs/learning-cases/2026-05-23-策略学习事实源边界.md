# 策略学习事实源边界

> 日期：2026-05-23
> 状态：draft
> 标签：ai-interviewer, strategy-learning, memory, database, boundary

## 一句话结论

`experience_extractor -> StrategySignal` 不能依赖当前进程里的 `qa_history` 和 bandit 内存状态；学习、晋升、观测和回放需要有可恢复、可解释的 DB 事实源。

## 背景

这次讨论从后台观测台的“策略学习”“策略记忆”“Verifier 监控”等指标开始，逐步追到 Director、Generator、Evaluator、bandit、`qa_history` 和 `experience_extractor` 的真实数据来源。用户反复追问“这些指标是不是在乱说”“最根本源头是不是 DB”“`qa_history` 是不是也是内存”，暴露出策略学习链路里事实源不稳定的问题。

## 现象

### 事实

- `Director` 热路径运行时读的是内存里的 `ThompsonBandit.priors`，服务重启后如果没有恢复机制，后台观测和策略学习会看到空状态或短期状态。
- `experience_extractor` 原先更依赖当前 state 中的 `qa_history` 和内存 bandit，无法稳定覆盖旧会话、重启后的会话或后台回放场景。
- `generation_traces` 能提供历史线索，但它更像事件日志，不是为“每轮面试事实”和“bandit 聚合后验”直接服务的事实表。
- 用户拍板采用两张事实/聚合表：`interview_turns` 和 `bandit_posteriors`，保持 `experience_extractor -> StrategySignal -> strategy_promotion -> StrategyMemory` 主链路不变。

### 推断

- 后台观测台读内存指标时，容易把“当前进程暂时知道什么”误展示成“系统长期学到了什么”。
- `qa_history` 适合表达当前工作流上下文，但不适合作为跨会话、跨进程的学习事实源。
- `generation_traces` replay 可以作为兼容老环境的恢复路径，但长期更适合作为审计日志，而不是 extractor 的主输入。

### 未确认假设

- 老会话中 trace 数据的完整度和结构一致性可能不足以完美回填 `interview_turns`。
- delayed reward 的重复计数风险需要继续靠幂等键和测试覆盖保证。

## 期望行为

每轮面试结束后，系统应该把脱敏问答、维度、锚点、Evaluator/Verifier 结果、即时 reward 和延迟 reward 写入可查询的事实表。bandit 更新也应该同步写入聚合后验表。`experience_extractor` 读取 DB 事实源生成 `StrategySignal`，而不是把当前内存状态当成长期学习状态。

## 根因判断

直接原因：

- 策略学习链路把一部分运行时状态当成可复用学习状态，导致服务重启、旧会话、后台观测和自动晋升之间存在语义落差。

深层原因：

- 系统里同时存在 trace、workflow state、内存 bandit、策略记忆库等多种数据形态，但一开始没有明确区分“事件日志”“当前上下文”“聚合后验”“可检索策略记忆”。
- `StrategyMemory` 是晋升后的长期经验，不等于每轮面试刚产生的事实；二者中间需要 `StrategySignal`，而 `StrategySignal` 需要可靠事实源。

触发条件：

- 后台观测、服务重启、旧会话 replay、delayed reward 回写、策略晋升这些场景都要求数据跨越当前进程生命周期。

## 调试过程

1. 从后台观测台指标开始，先确认“策略学习臂数”“策略记忆条数”“Verifier 监控”各自来源。
2. 追到 Director 和 Generator 的分工，确认 Director 运行时读 bandit 参数而不是直接把历史反馈文本塞给 LLM。
3. 继续追问 bandit 参数来源，确认 reward update 才是后验更新的直接入口。
4. 判断仅靠内存 bandit 和 `qa_history` 不足以支撑可靠观测和 extractor。
5. 拍板新增 `interview_turns` 与 `bandit_posteriors`，并保持 `StrategySignal` 主链路不绕开。

## 解决方式

- 新增 `interview_turns` 记录每轮脱敏问答事实、评价、Verifier 结果、reward 和简历锚点字段。
- 新增 `bandit_posteriors` 记录 Thompson bandit 聚合后验。
- evaluator、verification、reward update、delayed reward bridge 同步写 DB。
- `experience_extractor` 优先从 DB 事实源恢复 QA pattern 和 bandit insight，仅在缺失时 fallback 到 legacy state。
- `ThompsonBandit.rehydrate_from_db()` 优先读取 `bandit_posteriors`，空表时再 fallback 到 `generation_traces` replay。

## 验证方式

- 后端全量单测通过：`1820 passed, 2 skipped`。
- focused tests 覆盖模型、写入、extractor、rehydrate 与 replay 兼容。
- 手动检查新会话时，`interview_turns` 与 `bandit_posteriors` 能反映新链路数据。

## 可复用教训

- 凡是“学习、晋升、观测、回放”链路，都应先明确事实源在哪里。
- 内存状态可以服务热路径，但不能作为长期学习和后台观测的唯一依据。
- trace 可以用于审计和回放，不应被迫承担所有聚合事实语义。
- 不要绕开既有 `StrategySignal` 晋升链路，否则会让“候选事实”和“长期策略记忆”混在一起。

## 这次容易误判的地方

- 看到后台观测台里“策略学习 10 个臂”或“策略记忆 0 条”时，容易把它们理解成同一种策略学习状态。实际上前者更接近 bandit 后验状态，后者是已经晋升、可被 Generator 检索复用的 `StrategyMemory`。
- 看到 `generation_traces` 有历史数据时，容易以为 extractor 可以直接稳定复用它。实际 trace 是事件日志，字段形态和写入时机都不一定等同于“每轮事实表”。
- 看到 `qa_history` 里有问答时，容易把它当成真实学习事实源。它更像 workflow state 的工作记忆，适合当前会话推进，不适合跨进程的学习和后台观测。
- 看到 Director 读 bandit 参数，容易误解成 LLM 直接读了“历史反馈文本”。实际 Director 只读统计后验并选择 action，LLM 看到的是被选出的策略动作和上下文，而不是完整历史反馈。
- 看到服务重启后指标变少，容易先怀疑 UI 展示或 API fallback。更关键的检查点是：bandit 后验有没有持久化，启动时有没有 rehydrate。

## 下次优先检查项

1. 先给每个指标标注来源：内存、workflow state、trace、事实表、聚合表，还是晋升后的策略记忆。
2. 如果观测值和直觉不一致，先重启服务再看是否丢失；能被重启影响的状态，不应被宣传成长期学习状态。
3. 检查 reward update 是否同时更新内存 bandit 和 `bandit_posteriors`，不要只验证热路径行为。
4. 检查 `experience_extractor` 的输入 source 标记，确认是 DB facts 还是 legacy fallback。
5. 对历史数据问题，先判断是“旧会话没有事实表”还是“新会话未落库”，这两类问题的修复方式不同。

## 未解决问题

- 历史 trace 回填的覆盖率和脏数据处理仍需要更多真实样本验证。
- 是否需要更细的幂等事件表来表达 delayed reward 已应用状态，仍可继续评估。
