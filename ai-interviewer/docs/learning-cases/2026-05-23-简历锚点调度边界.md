# 简历锚点调度边界

> 日期：2026-05-23
> 状态：draft
> 标签：ai-interviewer, scheduling, resume-anchor, workflow, boundary

## 一句话结论

标准/深度面试不能只以“维度覆盖完成”作为结束依据；面试深度还需要看简历锚点覆盖和高价值锚点追问次数。

## 背景

用户在标准面试中观察到“训练回放”只有 6 或 7 轮问答，但入口卡片写的是“标准面试，约 8 轮，覆盖核心项目”。继续分析后发现，系统实际覆盖了多个维度，但没有充分按多个简历锚点展开，也没有稳定把高价值锚点追问到最多 2 轮。

## 现象

### 事实

- 标准面试配置期望约 8 轮，但部分真实会话在 6/7 轮结束。
- 面试维度数量有限，单纯“每个维度一题”无法自然撑起标准/深度模式的轮次差异。
- 用户拍板：标准和深度模式都允许同一个高价值锚点最多问 2 轮。
- 用户进一步明确：增加轮次更适合“围绕多个简历锚点展开”，而不是临时增加维度。
- 后续发现旧形态 `focus_areas` 中 `anchor_key` 为空、`dimensions` 是自由标签，可能影响锚点选择和已用锚点判断。

### 推断

- 原调度更偏 dimension coverage scheduler：覆盖完核心维度后就容易判断可以结束。
- 标准/深度模式真正要体现的是：在维度约束下，覆盖更多候选人经历锚点，并对高价值锚点进行第二轮追问。
- 如果 setup snapshot 保存的是未归一化 candidate，即使选择时能临时派生 key，也会增加旧形态数据绕过调度预期的风险。

### 未确认假设

- 个别“7 轮结束”是否完全由服务未加载最新代码造成，还是也存在边界条件遗漏，需要更多新进程会话验证。
- 不同岗位方向下，默认最多 2 轮追问是否都合适，仍可通过真实面试数据校准。

## 期望行为

标准面试应优先保证核心维度至少各有一题；覆盖完成后，如果还没达到目标轮次，应继续选择未覆盖的 resume focus，或对高价值锚点进行最多 2 轮追问。深度面试也遵循同样锚点逻辑，只是目标轮次和探索空间更大。

## 根因判断

直接原因：

- 路由和调度层曾把“核心维度已覆盖”过早等同于“当前面试可以结束”。

深层原因：

- 维度是评价框架，简历锚点是候选人事实主题；两者不应互相替代。
- 标准/深度面试的深度差异应该由锚点覆盖、锚点追问和目标轮次共同表达。
- 简历解析产物如果没有稳定 `anchor_key` 和标准维度，会让“是否已问过某个锚点”的判断变脆弱。

触发条件：

- 候选人简历 focus 数量足够，但维度数量较少。
- 面试模式目标轮次大于核心维度数量。
- 服务未加载最新调度代码或 session 使用旧形态解析快照。

## 调试过程

1. 先确认标准面试“约 8 轮”不是硬编码报告错误，而是调度实际提前结束。
2. 分析所有维度数量有限，判断不能靠增加维度来扩展轮次。
3. 明确“多个简历锚点”才是标准/深度面试扩展深度的自然单位。
4. 讨论同一个高价值锚点是否允许 2 轮追问，用户拍板标准和深度都允许。
5. 检查真实 session 的 `focus_areas` 形态，发现旧解析结果存在 `anchor_key` 空和自由维度标签。
6. 补充归一化：解析后、创建 session 前、保存 setup snapshot 时都使用 normalized candidate。

## 解决方式

- 调度层增加 resume anchor slot 判断，在维度覆盖完成但目标轮次未满时继续补锚点 turn。
- 同一高价值锚点最多 2 轮追问，问满后切到其他未问过的 resume focus。
- 简历 focus 增加稳定 `anchor_key`，维度归一到运行时维度枚举。
- 保存 setup snapshot 时也保存归一化后的 candidate，降低旧形态数据绕过调度的风险。

## 验证方式

- 通过真实 session 对比服务重启前后行为。
- 单测覆盖 coverage routing、resume anchor baseline、resume driven interview 等调度场景。
- 后端全量单测最终通过：`1820 passed, 2 skipped`。

## 可复用教训

- “维度覆盖”是评分覆盖，不等于“面试深度完成”。
- 面试调度的状态单位至少包括：维度、简历锚点、锚点追问次数、目标轮次。
- 解析结果是调度上游事实源，必须在 session 边界前归一化。
- 出现“目标轮次未达但提前结束”时，优先检查 router 结束条件，而不是只看 Generator 是否能继续出题。

## 这次容易误判的地方

- 最初看到“标准面试只有 6 轮”，容易以为只是前端卡片“约 8 轮”的文案不严谨。后续确认这是调度层结束条件的问题，不只是展示问题。
- 看到“这场实际覆盖了 6 个维度”，容易认为面试已经完整。实际上维度覆盖只说明评分框架被扫过一遍，不说明候选人的核心经历被充分展开。
- 讨论“同一个高价值锚点最多 2 轮”时，容易担心它会和“每个维度至少一题”冲突。更合理的顺序是先保证维度覆盖，再在剩余轮次里做锚点扩展。
- 看到旧会话 `focus_areas` 没有 `anchor_key`，容易认为选择时临时派生 key 就够了。真实风险是 setup snapshot、已用锚点判断、回放和后续报告可能读到不同形态的数据。
- 当用户重启后仍看到 7 轮结束时，容易直接归因于“修复没生效”。后来需要把当前代码模拟、进程加载状态和真实 session 数据分开判断。

## 下次优先检查项

1. 先确认当前进程是否真的加载了最新代码，再分析调度逻辑；否则会把旧进程行为误当成新 bug。
2. 检查 router 的结束条件：是否只看了维度覆盖、是否还看目标轮次、是否还有可用 resume anchor slot。
3. 检查 `focus_areas` 是否已归一化：`anchor_key`、标准维度、project id、label 是否稳定。
4. 检查已用锚点判断是否优先使用 `anchor_key`，不要只依赖旧的 `focus_id` 或 project id。
5. 对“轮次太少”的问题，同时看三个数：目标轮次、已覆盖维度数、可继续展开的锚点数。

## 未解决问题

- 不同面试模式下，锚点优先级和追问次数是否需要更细配置。
- 如果候选人简历 focus 很少，是否需要 fallback 到同维度不同问题类型，而不是强行重复锚点。
