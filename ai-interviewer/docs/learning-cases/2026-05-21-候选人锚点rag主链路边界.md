# 候选人锚点 RAG 主链路边界

> 日期：2026-05-21
> 状态：draft
> 标签：ai-interviewer, rag, workflow, boundary, debugging

## 一句话结论

候选人锚点 RAG 一旦进入面试主链路，就不能只按“检索模块”设计，而要显式处理 ready、pending、fallback、timeout、状态回写和首屏体验。

## 背景

这次改造围绕“候选人简历 / 自我介绍 -> 语义锚点检索 -> 生成正式题和追问”展开。目标是让面试官在出题时能利用候选人简历项目、自我介绍重点和技术锚点，而不是只依赖岗位要求、题库和上一轮回答。

最初方案把 Session Anchor RAG 视为一个可接入的 PgVector 检索源：简历解析后切 chunk、写入向量库，后续 `ask_question` 查询候选人 anchors 并放入 Generator prompt。后续测试发现，真正复杂的不是 PgVector 查询本身，而是它和现有 LangGraph workflow、前端首屏、状态快照、降级生成之间的边界。

## 现象

### 事实

- 第一轮设计中，简历向量化倾向于在 `resume_parse_node` 内同步完成，导致进入面试页前需要等待 embedding。
- 用户指出：一轮面试的第一道题是固定自我介绍，此时并不需要简历 RAG；真正需要简历 anchors 的是自我介绍提交后的第一道正式题。
- 用户在进入面试页时观察到首屏“思考中”卡了十多秒，怀疑是 resume embedding 阻塞了固定自我介绍题。
- 后续方案把简历向量化改成后台任务：`resume_parse_node` 启动任务并返回 `resume_vector_status.status = "pending_background"`。
- `self_intro_parse_node` 在解析和向量化自我介绍后，最多等待 resume vector job 约 12 秒，争取第一道正式题拿到完整 anchors。
- `ask_question_node` 在执行局部 plan 前刷新 resume vector status；如果后台任务已完成，当前题即可使用 `resume_revision_id` 检索。
- 如果超时或未 ready，`RESUME_RAG_MODE=primary` 也不阻塞出题，retriever 以 `fallback_reason="not_ready"` 等方式降级。
- 另一个状态边界是 `setup_snapshot`：DB 里的创建时快照曾显示 `pending_node`，但真实 LangGraph checkpoint 已经 ready，可能影响前端或 Admin 对运行态的判断。

### 推断

- 早期方案默认“进入面试前 anchors 应该 ready”，这个假设混淆了 setup 阶段和第一道正式题阶段。
- 固定自我介绍题是一个天然的异步缓冲窗口；候选人在回答自我介绍期间，后台完成 resume embedding 更符合业务时机。
- RAG 进入 prompt 后，状态不能只存在于后台任务或 DB rows 里，还必须被写回 workflow state / checkpoint / snapshot，供前端展示、Admin 排查和后续节点判断。
- `primary` 不应该等于“强制阻塞生成”；它更适合表示“ready 时进入 prompt，未 ready 时带可观测 fallback 继续主链路”。

### 未确认假设

- 12 秒等待阈值是否适合所有 embedding provider、网络环境和简历长度，仍需要更多实测数据。
- 后台 resume vector job v1 使用进程内状态，生产环境是否需要持久化任务表尚未决定。
- Admin 是否需要更明显地展示 `pending_background`、`wait_timed_out`、`cache_hit`、`fallback_reason` 的完整链路状态，仍可继续打磨。

## 期望行为

进入面试页后，用户应尽快看到固定自我介绍题，不应因为简历 embedding 而在首屏等待。

候选人回答自我介绍期间，系统可以在后台做 resume embedding。提交自我介绍后，系统可以短等待一段时间以争取完整 Session Anchor RAG；如果等待成功，第一道正式题使用 resume + self_intro anchors；如果等待超时，第一道正式题继续生成，后续题在后台 ready 后自动吃上 anchors。

任何时候，RAG 未 ready 都不应破坏面试主链路。它应该表现为可观测的降级，而不是异常、空白页面或不可解释的等待。

## 根因判断

直接原因：

- 简历向量化被放在首题前同步路径中，导致固定自我介绍题被不必要地阻塞。

深层原因：

- RAG 被当作“数据准备完成后再进入主链路”的能力，而不是“可异步 ready、可降级、可被节点刷新”的 workflow 附属能力。
- 面试 workflow 中存在多个状态载体：DB session row、setup snapshot、LangGraph checkpoint、trace artifact、Admin summary。只更新其中一处会造成“真实已 ready，但展示仍 pending”的状态漂移。
- `RESUME_RAG_MODE=primary` 的语义容易被误解为“必须等 RAG 成功才能生成”，但面试体验需要的是“能用则强使用，不可用则可解释降级”。

触发条件：

- embedding provider 较慢或网络波动。
- 简历 chunk 数量较多，首次向量化还没有缓存命中。
- 用户进入面试页后，首题本来是固定自我介绍，但 workflow 仍在等待 resume vectorization。

## 调试过程

1. 先确认 Session Anchor RAG 已经接入 ask_question 和 Generator prompt，但实测 session 仍出现 `not_ready` 或未命中。
2. 排查 embedding 配置、resume/self_intro vector status、PgVector rows 和 trace artifact，确认问题不只是“有没有写入向量库”。
3. 观察到进入面试页首屏等待较长，重新审视 workflow 时机：固定自我介绍题不应等待 resume embedding。
4. 将 resume vectorization 从同步节点改为后台 job，`resume_parse_node` 只启动任务并返回 `pending_background`。
5. 在 `self_intro_parse_node` 增加短等待，把“候选人回答自我介绍的时间”作为后台向量化窗口。
6. 在 `ask_question_node` 增加状态刷新，避免后台已完成但 state 仍旧导致当前题继续 `not_ready`。
7. 修补 `setup_snapshot` 状态回写，减少 DB 快照和 checkpoint 的展示差异。

## 解决方式

- 新增 session-scoped resume vector job 服务：
  - 按 `session_id + resume_source_id` 去重启动后台任务。
  - 后台消费 parse artifact 并调用 resume vectorization。
  - 显式携带当前 session 的 embedding override，避免后台线程丢失前端 BYOK Qwen Key。
  - 暴露 start / wait / refresh 状态接口。
- `resume_parse_node` 不再同步等待简历向量化，改为返回 `pending_background`。
- `self_intro_parse_node` 在自我介绍解析和向量化后等待 resume vector job，超时则写入 `wait_timed_out`，继续工作流。
- `ask_question_node` 在局部 plan 前 refresh resume vector status，尽量让当前题吃到刚完成的 anchors。
- retriever 保持降级语义：未 ready 时返回 fallback artifact，不抛错、不阻塞生成。
- 修补 session snapshot 同步，让前端和 Admin 更接近真实运行态。

## 验证方式

- 后端单元测试覆盖：
  - `resume_parse_node` 有 `resume_source_id` 时不会同步调用 `vectorize_resume()`，而是启动后台任务。
  - 后台任务重复启动会去重。
  - self-intro parse 等待 resume status 成功时写回 ready，超时时写入 `wait_timed_out` 并继续。
  - ask_question 在 state 仍是 `pending_background` 时会刷新后台状态，并把 `resume_revision_id` 传给 retriever。
  - 未 ready 时仍生成问题，RAG artifact 记录 `not_ready`。
- 手动验证覆盖：
  - 新 session 进入面试页后，自我介绍题不再因为 resume embedding 长时间卡住。
  - 后续问题在 resume/self_intro anchors ready 后能看到 `candidate_anchor_rag` 命中。
  - 后续缓存命中场景中，第二场同简历面试不再重新发起远程 embedding。

## 可复用教训

- RAG 接入主链路时，优先画清楚“哪个节点真的需要它”，不要把所有准备工作都塞到首屏前。
- `primary` 模式也应该有降级路径。主链路产品体验比“检索一定成功”更重要。
- 异步能力至少要设计四件事：后台任务如何启动、调用节点如何等待、后续节点如何刷新、展示状态如何回写。
- Workflow state、DB snapshot、trace artifact 和 Admin summary 是不同观察面；只修业务结果而不修状态回写，会让后续排查继续绕路。
- 固定题、候选人输入等待、报告生成等自然等待窗口，可以用来吸收 AI/embedding 基础设施耗时。

## 未解问题

- 是否需要把 resume vector job 从进程内状态升级为持久化任务表。
- 12 秒等待阈值是否需要按 provider、简历长度或历史延迟动态调整。
- Admin 是否需要一个更直观的 Session Anchor lifecycle 面板，串起 parse artifact、vector job、cache、session rows、retrieval artifact。
- 如果用户极快提交自我介绍且 embedding 仍未完成，第一道正式题降级是否需要前端提示，还是保持静默即可。
