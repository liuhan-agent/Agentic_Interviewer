# 控制面与权限边界说明

Agentic Interviewer 的主价值是完成一次高质量模拟面试并给出反馈，但它不是一个只有聊天链路的 Demo。账号、记录归属、平台额度、BYOK、Admin 后台和生产预检共同构成产品控制面，决定了谁拥有记录、谁消耗平台资源、谁能管理后台，以及公开上线前哪些配置不能裸奔。

## 1. 设计主张

登录/注册不是一个孤立模块，而是主链路的 ownership/control-plane 补强。

系统需要同时支持两类使用方式：

- 未登录用户可以低门槛体验，尤其是本地开发、内测和 BYOK 调试。
- 登录用户可以把新面试保存到账号，跨设备查看账号记录，并使用平台托管额度。

因此，控制面要回答四个问题：

1. 这场面试属于谁？
2. 这场面试消耗谁的模型资源？
3. 谁能看到或管理这条记录？
4. 公开上线时哪些组合必须被拦住？

## 2. 身份类型

| 身份 | 能力 | 边界 |
| --- | --- | --- |
| 匿名浏览器用户 | 可以使用本机匿名记录；在允许的场景下使用 BYOK；本地开发可继续调试主链路。 | 不拥有账号记录；生产环境不能消耗平台托管 Key；不能访问 Admin。 |
| 普通账号用户 | 可以创建账号归属面试、查看自己的记录、使用平台额度、申请补充额度。 | 只能访问 `owner_user_id == current_user.id` 的记录；不是 Admin。 |
| Admin 账号用户 | 可以进入后台查看用户、额度、申请、面试记录和观测数据。 | Admin 提升不在前端自助完成；不能随意升降其他 Admin；危险操作需要后端保护。 |

`API_TOKEN` 是 bootstrap / emergency fallback，不等同于普通账号身份。产品化后台以 `role=admin` 为主。

## 3. 记录归属

面试记录分为三类：

| 类型 | 来源 | 展示语义 |
| --- | --- | --- |
| 账号记录 | 登录状态创建，服务端写入 `owner_user_id`。 | 属于当前账号，可跨设备查看。 |
| 本机匿名记录 | 未登录时在当前浏览器保存。 | 只属于当前浏览器，不等同于账号资产。 |
| 其他账号本机记录 | 当前浏览器曾登录其他账号留下的 owned 本地行。 | 不进入当前账号主列表，只提示切换账号。 |

登录后，“我的面试”主列表只展示当前账号记录。本机匿名记录进入独立折叠区，并提示“这些记录只在当前浏览器，不属于当前账号”。

匿名记录可以通过显式操作保存到账号，但必须满足：

- 用户已登录；
- 本地仍有有效 `sessionToken`；
- 后端能验证该 session token；
- claim 成功后旋转 session/recovery token，并写回本地 owner 信息。

删除语义也不同：

- 账号记录删除是服务端记录删除。
- 匿名记录“从本机移除”只删除浏览器本地行，不代表删除服务端匿名 session。

## 4. 平台额度与 BYOK

项目默认产品模式是“平台托管 LLM Key + 用户消耗面试次数”。

| 模式 | 是否登录 | 是否扣平台次数 | 说明 |
| --- | --- | --- | --- |
| 平台托管 | 生产环境必须登录 | 是，一场面试扣 1 次 | 用户不需要懂 API Key，适合主产品体验。 |
| BYOK / 个人 API Key | 可用于高级调试和个人使用 | 否 | 不扣平台次数，但会消耗用户自己的模型服务额度。 |
| dev unmetered | 仅本地/开发配置 | 否 | 用于 stub 或开发调试，不应用于生产开放。 |

额度系统采用 cached balance + append-only ledger：

- 免费赠送通过版本化 external ref 保证幂等。
- 平台托管 start 成功后写入 session debit。
- Admin 手动调整、申请审批、补偿等都进入 ledger。
- claim 旧匿名记录不追溯扣费。

当前定价策略故意保持“一场 = 1 次”。深度、模型成本、时长等差异化扣费属于后续商业化阶段。

## 5. Admin 权限

Admin 是运营控制面，不是普通用户功能。

Admin 能力包括：

- 用户列表和用户详情；
- 启用/禁用普通用户；
- 查看用户额度、账本和面试记录概况；
- 额度手动调整；
- 额度申请审批；
- 面试历史、trace explorer 和 workflow 观测数据。

Admin 边界：

- 普通登录用户不能访问 Admin API。
- 不在前端提供提升/取消 Admin。
- 不允许 Admin 禁用 Admin 或操作自己。
- 禁用普通用户不删除历史记录、不回收额度，只影响后续账号能力。
- Admin promotion 通过后端脚本完成，例如 `python -m app.scripts.promote_admin --email admin@example.com`。

## 6. 注册防滥用与生产预检

本地和内测阶段可以保持注册开放、免费额度照常发放。公开上线前必须避免“无限注册领免费次数”的裸奔组合。

生产预检会阻断危险配置：

```text
APP_ENV=prod
+ AUTH_REGISTRATION_MODE=open
+ FREE_INTERVIEW_CREDITS > 0
+ FREE_CREDITS_REQUIRE_EMAIL_VERIFIED=false
```

可接受的生产方向包括：

- 关闭开放注册，只由管理员创建或邀请用户；
- 免费额度为 0，人工补额度；
- 开启邮箱验证要求，再发放免费额度；
- 后续实现邀请码、captcha 或支付体系。

Phase 3.0 之前只埋防滥用钩子和生产预检，不实现完整邮件发送、找回密码、支付或会员系统。

## 7. 上线解释口径

项目目前适合定位为 portfolio-ready、production-aware 的 AI 应用：

- 主链路已经闭环：面试、评分、追问、报告、复练和历史记录。
- 控制面已经补齐：账号归属、额度、BYOK、Admin、申请审批和生产预检。
- 商业化能力有明确边界：支付、会员、邮箱验证、邀请码、完整 audit log 暂不实现。

这个边界不是能力缺失，而是阶段性取舍：先证明 agentic workflow + SaaS control plane 的工程闭环，再把公开运营和商业化作为后续 backlog。
