# 产品经理 题库

面向 C 端用户准备产品经理岗位面试的检索种子题。题目以"请结合你做过的真实项目/功能"为主轴，鼓励候选人回到自己的简历经历展开，避免空谈方法论。每组题目包含一个 base 问题和 2-3 个渐进式 follow-up，配套 2-3 条评分要点（rubric points），与 Generator Agent 的 `proposed_contract.acceptance_checks` 对齐。

难度标签约定：
- `intro` 用于开场或低龄段背景题，候选人能用 1-2 段话讲清楚即可
- `standard` 是主战场题，需要候选人讲清"目标 / 约束 / 决策 / 结果"
- `deep_probe` 是追问深挖题，要求候选人量化、还原冲突场景或解释非显然的取舍

## 维度：用户洞察 (user_insight)

### 1. 真实需求 vs 表层诉求
- **base** [intro]：请挑你做过的一个产品功能，讲讲你当时是怎么理解这个功能的目标用户的——他们在什么场景下、为了完成什么任务、最深层的诉求是什么？
- **follow-up** [standard]：你是怎么验证你对用户的理解是对的？有没有哪个发现让你推翻了最初的假设？
- **follow-up** [deep_probe]：那个被推翻的假设如果当时没被发现，最坏情况会让产品偏到哪里？你怎么把这个风险沉淀成团队的方法？
- **评分要点**：能否区分"用户说的"和"用户实际要的"；是否给出具体验证手段（访谈/数据/可用性测试）；能否反思自己最初判断的偏差来源。

### 2. 用户分层与典型用户
- **base** [standard]：你过往的产品里，是怎么对用户做分层或者识别核心用户群的？为什么这么分？
- **follow-up** [standard]：你是怎么判断哪一群是核心用户、值得优先服务的？非核心用户的体验如何兜底？
- **follow-up** [deep_probe]：分层之后有没有出现"小群体声音很大但不是核心用户"的情况？你是怎么处理这种声音和核心用户优先级的关系的？
- **评分要点**：分层维度是否服务于具体业务问题（不是为分而分）；核心用户判断是否结合规模 / 价值 / 战略方向；能否抵御"喧哗用户"绑架决策。

### 3. 场景还原能力
- **base** [standard]：选一个你设计过的功能，把目标用户使用它的完整场景从开始到结束讲一遍——他在哪里、刚做完什么、心情怎样、为什么打开你的产品？
- **follow-up** [deep_probe]：场景里有没有你最初没考虑到、但上线后发现高频出现的"边缘场景"？你怎么发现它的、怎么消化的？
- **评分要点**：场景描述是否具体到"时间 / 空间 / 触发动机"（而非抽象功能流）；能否承认设计盲区并描述发现机制。

### 4. 用户调研选型
- **base** [standard]：当你不确定一个新方向值不值得做时，你会用什么方式去探索用户？为什么选这个方法、不用别的？
- **follow-up** [standard]：你做过的调研里，哪一次让你最意外？最后这个意外怎么影响了产品决策？
- **评分要点**：方法选型是否考虑成本 / 速度 / 信号质量的取舍；意外发现是否真的影响决策（而非"做完就归档"）。

## 维度：需求分析 (requirement_analysis)

### 5. 需求拆解
- **base** [intro]：业务方丢给你一个一句话的诉求（比如"我们需要让用户更愿意分享"），你接到之后会怎么拆？
- **follow-up** [standard]：拆完之后，怎么和业务方对齐"这个一句话最终落成什么东西"？有过被业务方推翻或重新对齐的经历吗？
- **follow-up** [deep_probe]：拆解过程里你常用的检查清单或者思考框架是什么？这个框架是从哪些项目里沉淀出来的？
- **评分要点**：拆解是否覆盖目标 / 用户 / 场景 / 约束 / 衡量；能否区分"业务诉求"和"功能描述"；是否有可复用的拆解方法论。

### 6. 边界判断
- **base** [standard]：选一个你写过的 PRD，讲讲你是怎么定义"这个版本做什么、不做什么"的？砍掉的那部分基于什么理由？
- **follow-up** [deep_probe]：被砍掉的功能里有没有上线后被证明应该早点做的？你后来怎么调整自己的边界判断？
- **评分要点**：边界判断是否结合时间 / 资源 / 风险；事后复盘是否真的更新了判断方式（不是单纯"下次会更小心"）。

### 7. 方案设计
- **base** [standard]：在你写过的需求里，有没有过同一个问题想了两到三个方案、最后选了某一个的？讲讲方案差异和你最后的选择理由。
- **follow-up** [deep_probe]：选了的方案上线后表现符合你的预期吗？如果不如预期，是方案选错了还是执行没到位？
- **评分要点**：是否真的对比过多个方案（而不是事后包装）；选择标准是否结合用户价值 / 实现成本 / 长期可演进性；能否区分"决策错误"和"执行偏差"。

### 8. 与设计 / 研发的协作设计
- **base** [standard]：你做需求评审时，设计师或者研发同事最常给你提的反馈类型是什么？这些反馈让你怎么调整 PRD 的写法？
- **follow-up** [deep_probe]：有没有过你坚持自己原方案、研发反对、最后你被证明错的（或者反过来）的经历？复盘下你当时怎么没有更早识别这个问题。
- **评分要点**：是否把"协作反馈"内化成 PRD 表达方式的迭代；面对争论是否能用证据 / 数据而不是职级 / 立场推动收敛。

## 维度：优先级判断 (prioritization)

### 9. 排期取舍
- **base** [intro]：你手上同时有 3-5 件事，你怎么决定先做哪个？
- **follow-up** [standard]：举一个你最近排过的优先级例子。当时几个选项分别是什么、各自的理由、你最后选了哪个、为什么？
- **follow-up** [deep_probe]：那次排期之后回头看，是不是真的应该这么排？如果当时多知道一个信息，你的排序会不会变？
- **评分要点**：排序逻辑是否结合价值 / 成本 / 风险 / 时间窗口；具体例子是否能讲清"为什么不是另外那个"；能否承认排期判断会因信息变化而变化。

### 10. 战略 vs 战术
- **base** [standard]：在你过往的工作里，有没有过"短期看很值得做但长期不该做"或者反过来的功能？最后是怎么决策的？
- **follow-up** [deep_probe]：决策过程里，你怎么和老板/业务方沟通这个长期/短期的取舍？有没有被反对、最后是怎么说服的？
- **评分要点**：能否区分战略价值和战术价值；说服过程是否依赖数据 / 假设验证 / 风险量化（而非纯立场对立）。

### 11. 资源约束
- **base** [standard]：你做过的需求里，有没有因为研发资源不足被迫做出"不完美方案"的？讲讲那个方案是什么、你怎么平衡完美度和可交付性的？
- **follow-up** [deep_probe]：那个不完美方案后来有没有需要回头补救的？补救成本和当初做完美方案的差异有多大？
- **评分要点**：是否能在资源限制下选出"可演进的最小可行方案"；能否量化"妥协的代价"。

### 12. 拒绝需求
- **base** [standard]：你拒绝过业务方或老板提的需求吗？最难的一次是什么？你最后是怎么说服对方的？
- **follow-up** [deep_probe]：拒绝之后双方的关系有没有受影响？你怎么经营这种"我说不"之后的协作关系？
- **评分要点**：拒绝理由是否基于用户价值 / 长期收益（而非"我不想做"）；能否兼顾"说不"和"维系协作信任"。

## 维度：指标思维 (metrics_thinking)

### 13. 指标定义
- **base** [intro]：你最近做的产品/功能，核心指标是什么？为什么是这个、不是另一个？
- **follow-up** [standard]：这个指标背后还有哪些"陪跑指标"或者"反向指标"？你是怎么用它们看这个核心指标是不是被钻了空子？
- **follow-up** [deep_probe]：指标体系定下来之后，有没有过被发现"指标涨了但产品体验或长期价值没涨"的情况？你后来怎么调指标？
- **评分要点**：核心指标是否结合用户行为 / 业务目标 / 战略方向；是否有反作弊 / 反 reward hacking 的辅助指标设计；能否承认指标会随阶段调整。

### 14. 数据驱动决策
- **base** [standard]：选一次你用数据推动决策的经历——数据告诉了你什么、你做了什么、最后结果如何？
- **follow-up** [standard]：数据有没有过和你的直觉相反的时候？你最后是相信数据还是相信直觉？
- **follow-up** [deep_probe]：信了"另一边"的那次，复盘下是数据有问题、直觉有偏差，还是两边其实都对但描述了不同的层面？
- **评分要点**：决策过程是否真的让数据起到关键作用（而非装饰）；能否处理数据 / 直觉冲突而不简单二选一。

### 15. A/B 测试 / 实验
- **base** [standard]：你做过 A/B 测试吗？讲一次你印象最深的实验——假设是什么、实验设计、结果、决策。
- **follow-up** [deep_probe]：实验中有没有出现"显著结果但其实是统计假象/外部干扰"的情况？你是怎么识别的？
- **评分要点**：实验设计是否考虑显著性 / 样本量 / 时间窗口 / 流量分配；能否警惕辛普森悖论 / 季节性等常见陷阱。

### 16. 复盘与归因
- **base** [standard]：你过往做过的功能/活动，最让你印象深的一次复盘是哪个？复盘里你发现了什么之前没意识到的东西？
- **follow-up** [deep_probe]：复盘的发现有没有真的回流到下一个版本的设计里？怎么保证复盘不是"开完会就归档"？
- **评分要点**：复盘是否产生具体的下一步动作（不是 checklist）；归因是否同时看产品因素和外部因素。

## 维度：协同推进 (stakeholder_management)

### 17. 与研发的协作
- **base** [intro]：研发同事给你反馈"这个需求估不准 / 边界不清 / 改动太大"时，你一般怎么处理？
- **follow-up** [standard]：举一个你和研发起过冲突的例子。当时分歧是什么、你怎么推进到收敛？
- **follow-up** [deep_probe]：那次冲突让你之后写需求的方式有什么变化？你怎么把这个学习沉淀给团队？
- **评分要点**：能否区分"研发抱怨表面"和"研发真实关切"；冲突收敛是否依赖证据和共识，而非职级 / 强势压制。

### 18. 与设计的协作
- **base** [standard]：当你和设计师对一个交互方案有分歧时，你一般用什么方式推进？
- **follow-up** [deep_probe]：有没有过你坚持自己的方案最后被证明设计师是对的？复盘下当时为什么没听进去？
- **评分要点**：是否尊重设计的专业判断；能否在自己错时复盘"为什么没听进去"而不止"我承认错"。

### 19. 跨部门协调
- **base** [standard]：你做过涉及 3 个以上部门的项目吗？讲一个，重点说说不同部门的目标差异和你怎么对齐的。
- **follow-up** [deep_probe]：项目推进过程里有没有出现部门间利益冲突的时刻？你怎么处理的、最后结果如何？
- **评分要点**：能否清晰描绘各方利益和约束；推进方式是否兼顾"对齐目标"和"避免拖入零和博弈"。

### 20. 向上沟通
- **base** [standard]：你怎么向老板或者更高级别的人汇报一个项目的进展或者风险？讲一次你印象深的汇报。
- **follow-up** [deep_probe]：你的汇报方式有没有因为某次踩坑做过调整？比如"这次老板更想看 X 而不是 Y"？
- **评分要点**：汇报结构是否清晰（结论 → 证据 → 风险 → 求助）；是否会根据听众调整内容密度和切入点。

### 21. 处理反对意见
- **base** [standard]：你提过的方案被多数人反对时，你怎么决定是改方案还是坚持？
- **follow-up** [deep_probe]：有没有过最后你坚持的方案被证明是对的？你当时是怎么承担这个风险的？
- **评分要点**：决策是否区分"多数人反对"和"多数人有不同诉求"；坚持时是否同时承担风险责任而非赌博。

## 通用追问触发器

下列触发词出现在候选人回答里时，触发对应的深挖追问：

- 候选人说"我们做了 XX 调研" → 追问"调研对象多少人？怎么选的？最反直觉的发现是什么？"
- 候选人说"上线后 XX 指标提升了 X%" → 追问"这个百分比的基线是什么？有没有显著性检验？外部因素能否解释？"
- 候选人说"我和老板对齐了优先级" → 追问"对齐过程中老板和你最初的判断差异在哪？谁的观点最后赢了、为什么？"
- 候选人说"这个功能用户很喜欢" → 追问"你是怎么知道的？有没有用户其实不喜欢只是没说？"
- 候选人说"我推动了 XX" → 追问"具体推动里你做了什么动作？哪一步如果你不在会卡住？"
