# 策略统计与晋升边界

> 日期：2026-05-25
> 状态：draft
> 标签：ai-interviewer, boundary, debugging

## 一句话结论

刷新统计只刷新已有策略使用归因的聚合结果，不生成新 signal，也不等于运行自动晋升。

## 背景

后台观测台“策略记忆”模块中同时存在“刷新统计”“立即运行一次”“自动晋升”状态。用户追问“刷新统计有什么作用”“必须手动点吗”“刷新统计与晋升信号积累是否有关”。

这类问题的难点在于：三个操作都和“策略变好”有关，但分别处在不同层级：

- 统计层：把已发生的 usage 事实聚合为 stats。
- 晋升层：把已存在的 signal 聚合为 strategy memory。
- 生成层：在面试完成链路里生成新的 signal。

如果后台把这些入口放在同一张卡里，但没有解释边界，用户会很自然地把“刷新统计”理解为“刷新学习状态”。

## 现象

### 事实

- `refresh_strategy_memory_stats()` 从 `StrategyMemoryUsage` 聚合生成或更新 `StrategyMemoryStats`。
- `run_strategy_promotion_now()` 会先刷新统计，再运行 `promote_strategy_signals()` 与 `apply_strategy_quality_transitions()`。
- 自动晋升 scheduler 只是定期运行 promotion pass，不负责在面试完成链路中生成 signal。
- `strategy_signals` 理论上由 `experience_extractor_node` 在面试完成后生成。
- `/admin/strategy-stats/refresh` 只调用 `refresh_strategy_memory_stats()`。
- `/admin/strategy-promotion/run` 调用 `run_strategy_promotion_now()`，它会执行 refresh stats、promote signals、quality transitions。
- `apply_strategy_quality_transitions()` 使用 `StrategyMemoryStats` 中的全局统计来禁用或稳定已有策略。
- `promote_strategy_signals()` 使用 `StrategySignal`，不读取 `StrategyMemoryUsage`。

### 推断

- “刷新统计”按钮容易被理解成“刷新策略学习/触发晋升”，但它实际只同步 usage stats。
- 如果 `strategy_signals = 0`，点击刷新统计不会让新策略候选出现。
- `strategy_signals = 0` 时，排查重点不在 stats refresh，而在 completed session 是否跑过 `experience_extractor_node`，以及 extractor 的 QA/bandit 条件是否满足。

### 未确认假设

- 当前环境里 `strategy_signals = 0` 的直接原因可能是样本不满足抽取条件，也可能是完成链路中未产生可抽取 pattern，需要数据库样本和 trace 进一步确认。
- 自动晋升 scheduler 在当前 dev 环境是否长期保持开启，取决于 `.env` 和服务重启状态；不能只看 `.env.example` 推断。

## 期望行为

运维入口应清楚区分：

- 刷新统计：同步已有策略使用归因的聚合值。
- 立即运行一次：手动触发一次晋升和质量转换。
- 自动晋升：后台定时执行晋升和质量转换。
- 晋升信号积累：由完成链路中的 experience extractor 产生。

推荐的心智模型：

```text
完成面试
  -> experience_extractor 生成 StrategySignal

策略被注入并完成评分
  -> StrategyMemoryUsage
  -> 刷新统计
  -> StrategyMemoryStats

手动/自动运行晋升
  -> refresh stats
  -> promote StrategySignal
  -> apply quality transitions
```

其中“刷新统计”只覆盖第二段，不会替代第一段。

## 职责矩阵

| 入口/任务 | 读什么 | 写什么 | 是否生成新 signal | 是否创建新策略 | 是否影响已有策略状态 |
|---|---|---|---|---|---|
| `experience_extractor_node` | QA history、BanditPosterior | `StrategySignal` | 是 | 否 | 否 |
| `refresh_strategy_memory_stats()` | `StrategyMemoryUsage` | `StrategyMemoryStats` | 否 | 否 | 否 |
| `promote_strategy_signals()` | `StrategySignal` | `StrategyMemory`、signal status | 否 | 是 | 否 |
| `apply_strategy_quality_transitions()` | `StrategyMemoryStats`、`StrategyMemory` | `StrategyMemory.status`、`promotion_stage` | 否 | 否 | 是 |
| scheduler | 配置和定时器 | 运行结果状态 | 否 | 间接 | 间接 |

这张矩阵是本次复盘最重要的边界：**刷新统计不负责生成证据，晋升任务不负责创造证据，extractor 不负责马上改全局策略。**

## 易混淆操作

### 刷新统计

适合回答：

- 最近 usage 有没有被聚合？
- 全局命中、平均 reward、Verifier 否决率是否更新？
- 已有策略是否具备稳定/禁用的统计基础？

不适合回答：

- 为什么没有晋升候选？
- 为什么新策略没有自然生成？
- 为什么某个 action 的 posterior 没变？

### 立即运行一次

适合回答：

- 已有 signal group 是否达到晋升阈值？
- 已有策略是否应被禁用或标记 stable？
- 手动验证 promotion job 是否能正常跑完。

不适合回答：

- 让完成链路重新抽取 signal。
- 补写某场面试缺失的 generation trace。
- 让没有 usage 的策略凭空产生 stats。

### 自动晋升

适合回答：

- promotion pass 是否会周期性运行。
- 上次自动运行是否成功。
- 下次什么时候运行。

不适合回答：

- signal 为什么没有积累。
- 单场面试为什么没有被 extractor 抽中。

## 根因判断

直接原因：统计刷新、晋升执行、信号生成分别属于三条不同链路。

深层原因：后台观测台将三者放在同一个“策略记忆”操作区，文案若不精确，会把“同步聚合值”误读为“推进学习过程”。

触发条件：当系统尚无晋升候选时，用户自然会尝试点击“刷新统计”，期待它让候选或策略发生变化。

另一个触发条件是“自动晋升”这个词本身很强，它容易让人以为系统会自动完成从 session 到 memory 的所有步骤。但当前 scheduler 自动化的是 promotion pass，不是 completed-session extraction。抽取是在 workflow 完成链路内发生的，scheduler 只消费已存在的结果。

## 调试过程

1. 确认 `refresh_strategy_memory_stats()` 只读 `StrategyMemoryUsage`，写 `StrategyMemoryStats`。
2. 确认 `run_strategy_promotion_now()` 包含刷新统计、signal promotion、quality transition 三步。
3. 确认 `experience_extractor_node` 才是 `StrategySignal` 的生成入口。
4. 将 UI 文案从模糊的“运行晋升/刷新统计”区分为手动刷新 usage 与立即运行晋升。
5. 给 scheduler 增加状态展示，避免用户只能通过配置猜测它是否运行。
6. 将按钮文案从“运行晋升”调整为“立即运行一次”，强调这是一次 promotion pass，不是持续开关。
7. 明确“手动刷新只用于立即同步最新 usage，不会运行晋升”，把 stats refresh 和 promotion run 分开。

## 解决方式

本轮完成了后台观测台文案与状态展示调整：

- “手动刷新”说明为只同步最新 usage，不运行晋升。
- “立即运行一次”用于手动触发晋升。
- “自动晋升”tile 展示 scheduler 是否开启、上次运行结果和错误。

后端侧也补了 scheduler 状态快照，避免 UI 只能显示配置值：

- `enabled`：配置是否打开。
- `running`：当前进程内 scheduler 是否启动。
- `interval_minutes` / `startup_delay_minutes`：调度参数。
- `next_run_at`：APScheduler job 的下次运行时间。
- `last_run_at` / `last_run_kind` / `last_result`：最近一次手动或自动运行结果。
- `last_error` / `last_error_at`：最近失败信息。

## 可复用教训

- 后台操作按钮必须用动词说清楚“刷新什么”“是否产生新数据”“是否改变状态”。
- 发现 signal 没有增长时，优先检查完成链路与 extraction 条件，而不是 stats refresh。
- Scheduler 状态属于运维事实，应独立展示，不要藏在手动操作文案里。
- “统计刷新”只能让已有事实更可见，不能创造事实。
- “自动任务开启”只能保证消费链路定期跑，不能保证上游证据存在。
- 后台诊断卡最好按照数据生命周期分层：事实写入、聚合统计、晋升消费、运行调度。

## 未解问题

- 是否需要为 strategy signal 增加单独的“抽取链路健康”指标。
- 是否需要让 `/admin/strategy-signals` 展示最近一次 extractor 运行时间和跳过原因。
- 是否需要一个专门的 “signal readiness” endpoint，把每个 group 的 distinct session、avg reward、overrule rate 与阈值直接对齐。
- 是否需要在 completed session 详情里展示 extractor 是否执行、保存了多少 signal、跳过原因是什么。
