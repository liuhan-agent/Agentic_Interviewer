# 异步简历解析恢复边界

> 日期：2026-05-13
> 状态：draft
> 标签：ai-interviewer, async-job, boundary, frontend, backend

## 一句话结论

把简历解析改成异步任务时，真正复杂的不是“后台跑解析”，而是要定义用户离开后从哪里回来、回来看到什么、以及什么时候才创建正式面试记录。

## 背景

AI 简历解析阶段在使用较慢模型时可能耗时较长。用户不希望一直停留在 Setup 页面等待，因此需要把解析从同步等待改成后台任务，并允许用户离开页面后再回来继续填写。

## 现象

### 事实

- 用户指出“AI 简历解析”阶段耗时太久，希望可以离开页面。
- 用户进一步指出：只到“AI 简历解析”阶段时，系统还不会生成“面试记录”，因此首页“接着练”和“我的面试”如何恢复是一个边界问题。
- 最终方案定义为：
  - 上传后创建异步 parse job。
  - v1 只支持同一浏览器恢复。
  - 不创建正式面试记录，直到用户点击“开始我的面试”。
  - 前端新增 `setupDrafts`，并与 `interviewHistory` 分离。
  - “我的面试”顶部新增“准备中的面试”区块，而不是混入正式面试列表。

### 推断

- 原同步解析方案把“解析状态”隐含在 Setup 页面组件状态里；一旦用户离开页面，这个状态就没有稳定归属。
- 如果把未完成解析直接写入正式面试历史，会污染报告、回放、统计和正式 session 的语义。
- 如果不创建本地草稿，用户离开后无法找到正在解析的 job，也无法知道解析是完成、失败还是过期。

### 未确认假设

- v1 使用后端进程内 job store，服务重启后 job 丢失可接受；这是否满足真实生产环境，还需要后续产品决策。
- v1 不做跨设备恢复，是否会影响用户预期，需要上线后观察。
- 是否需要浏览器通知、首页 badge 或轮询提醒，尚未决定。

## 期望行为

- 上传简历后，解析可以在后台继续跑。
- 用户可以离开 Setup 页面。
- 用户回来时能从首页“接着练”或“我的面试”的“准备中的面试”恢复。
- 解析未完成时，不创建正式面试记录。
- 用户点击“开始我的面试”后，才创建正式 session，并写入 `interviewHistory`。
- 解析失败、超时、过期或 job 丢失时，用户能看到可理解的状态，并可以重新上传。

## 根因判断

直接原因：

- 简历解析从“页面内同步动作”变成“可离开页面的后台任务”后，缺少一个独立的恢复对象。

深层原因：

- 系统原本的持久化入口主要围绕正式面试 session 和 `interviewHistory`，没有表达“准备中但未创建 session”的中间态。
- 异步任务的 UX 边界不只是 API 状态，还包括导航入口、过期处理、字段编辑保护和正式记录创建时机。

触发条件：

- 解析模型耗时较长，例如使用较慢的 `qwen3.6-plus`。
- 用户在解析完成前离开 Setup 页面。
- 解析阶段尚未创建正式 session。

## 调试过程

1. 先识别同步解析等待太久，用户体验差。
2. 讨论是否直接异步化，确认 v1 可以只支持同一浏览器恢复。
3. 发现解析阶段没有正式面试记录，因此不能只依赖现有 `interviewHistory`。
4. 明确引入 `setupDrafts` 作为本地草稿存储。
5. 设计恢复入口：
   - 首页“接着练”优先恢复最新 setup draft。
   - “我的面试”单独展示“准备中的面试”区块。
6. 明确正式 session 创建时机：用户点击“开始我的面试”后才创建。

## 解决方式

- 后端新增异步简历解析 job 接口：
  - `POST /api/v1/interview/resume/parse-jobs`
  - `GET /api/v1/interview/resume/parse-jobs/{job_id}`
- 后端 job store v1 使用进程内内存和后台线程池，TTL 默认 1 小时。
- 前端新增 `setupDrafts` 存储，保存恢复 job 所需的最小信息。
- Setup 页面打开 `draft_id` 时恢复 job 状态：
  - running：继续轮询。
  - completed：拉取结果并填表。
  - failed / expired / missing：提示草稿失效并允许重新上传。
- 首页“接着练”优先跳转最新可恢复草稿。
- “我的面试”顶部新增“准备中的面试”，不混入正式面试历史。
- 点击“开始我的面试”后删除 setup draft，并正常写入 `interviewHistory`。

## 验证方式

- 后端测试覆盖：
  - 创建 parse job。
  - fake LLM 完成后查询 completed。
  - 缓存命中立即 completed。
  - unknown / expired job 返回 expired。
  - 异步 job 使用更长 LLM timeout。
- 前端测试覆盖：
  - `setupDrafts` 新增、读取最新、更新、删除、过滤过期。
  - SetupForm 恢复 running / completed / failed / expired。
  - 首页“接着练”优先跳 setup draft。
  - “我的面试”展示准备草稿，但不混入正式历史。
- 实际执行过：
  - `npm run typecheck`
  - 相关 frontend source tests。

## 可复用教训

- “异步化”不是把接口改成 job 就结束；必须同步设计恢复对象、恢复入口和结束条件。
- 草稿态和正式记录态要分开建模，尤其是涉及报告、回放、统计等后续语义时。
- 可离开页面的任务至少要回答三件事：用户在哪里找回、状态如何解释、失败/过期如何继续。
- 如果 AI 结果可能回填表单，解析完成前要么锁定相关字段，要么设计明确的合并策略；v1 选择锁定，避免覆盖用户编辑。
- v1 可以接受同浏览器和内存 job store，但必须在 UI 上把过期、丢失和重新上传路径讲清楚。

## 未解问题

- 是否需要服务端持久化草稿以支持跨设备恢复。
- 是否需要后台完成后主动通知用户。
- 是否需要记录 parse job 的可观测事件，用于排查解析慢、失败、过期比例。
- AI 解析结果和用户手动编辑的精细合并策略尚未设计。
