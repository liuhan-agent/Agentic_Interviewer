# 默认配置测试环境隔离

> 日期：2026-05-25
> 状态：draft
> 标签：ai-interviewer, tooling, debugging

## 一句话结论

默认配置测试不能直接使用会读取本地 `.env` 的 `Settings()`，否则开发机配置会污染测试结果。

## 背景

在收尾策略晋升 scheduler 状态展示时，后端测试 `test_strategy_promotion_scheduler_settings_default_disabled` 期望默认关闭 scheduler，但本地 `.env` 中开启了 `ENABLE_STRATEGY_PROMOTION_SCHEDULER=true`。

这次失败暴露的是测试意图和配置加载行为不一致：测试名在验证“默认值”，但构造方式却使用了完整运行时加载路径。运行时加载本地 `.env` 是正确的；默认值测试读取本地 `.env` 则是不稳定的。

## 现象

### 事实

- `Settings` 的 `model_config` 默认加载 `backend/.env`。
- 本地 `backend/.env` 中 `ENABLE_STRATEGY_PROMOTION_SCHEDULER=true`。
- 测试中使用 `Settings()` 时读到了本地 `.env`，导致默认关闭断言失败。
- 将测试改成 `Settings(_env_file=None)` 后，测试通过。
- `backend/.env.example` 中显式记录默认值 `ENABLE_STRATEGY_PROMOTION_SCHEDULER=false`。
- `Settings` 代码默认值也是 `enable_strategy_promotion_scheduler: bool = False`。
- 失败并不是产品逻辑变错，而是测试在开发机配置下不再验证“无 env 默认值”。

### 推断

- 该测试想验证的是代码默认值，而不是本地运行配置。
- 其他直接使用 `Settings()` 验证默认值的测试也可能存在同类风险。
- 对配置类测试来说，最容易被忽略的不是 env var 本身，而是 BaseSettings 的 `env_file` 默认行为。

### 未确认假设

- 尚未全量审计所有 `Settings()` 默认值测试是否都已隔离本地 `.env`。
- CI 环境是否完全没有 `.env`，本次未单独确认；即使 CI 不受影响，本地测试也应该稳定。

## 期望行为

测试代码默认配置时，应显式阻断本地 `.env`：

```python
Settings(_env_file=None)
```

测试运行时配置覆盖时，才应显式传入环境变量或专用 env file。

可以把 Settings 测试分为三类：

| 测试目的 | 推荐构造方式 | 说明 |
|---|---|---|
| 验证代码默认值 | `Settings(_env_file=None)` | 不读本地 `.env` |
| 验证 env override | monkeypatch env + `Settings(_env_file=None)` | 只验证指定环境变量 |
| 验证 `.env` 文件加载 | 临时 env file + `Settings(_env_file=path)` | 明确把文件加载作为被测行为 |

这三类不要混用，否则测试通过/失败会依赖开发机状态。

## 根因判断

直接原因：测试使用 `Settings()`，而 `Settings` 默认读取 `.env`。

深层原因：默认值测试和运行配置测试的边界没有通过构造参数表达出来。

触发条件：开发机本地 `.env` 与代码默认值不一致。

更具体地说，这次触发来自一个合理的本地操作：为了让后台观测台看到 scheduler 状态，本地把 `ENABLE_STRATEGY_PROMOTION_SCHEDULER` 打开。这个运行时设置不应该让“默认关闭”测试失败。测试失败说明它没有隔离自身输入。

## 调试过程

1. 运行后端最小测试集，发现 1 个失败。
2. 查看失败断言，定位到 scheduler 默认关闭测试。
3. 搜索配置来源，确认 `Settings` 默认加载 `backend/.env`。
4. 查看本地 `.env`，确认 scheduler 被设为 `true`。
5. 将测试改为 `Settings(_env_file=None)`，重新验证通过。
6. 同时确认 `.env.example` 和 `settings.py` 的默认值仍保持 `false`，没有产品默认值回归。
7. 重新跑后端和前端验证，避免收尾修复引入其他回归。

## 解决方式

已将 `test_strategy_promotion_scheduler_settings_default_disabled` 中的构造方式改为：

```python
settings = Settings(_env_file=None)
```

这属于测试隔离修复，不改变应用运行时行为。应用启动时仍然通过 `get_settings()` 读取环境变量和 `.env`，本地或部署环境仍可打开 scheduler。

本次没有做全仓批量替换，因为有些 `Settings()` 测试可能本来就在验证真实加载行为；盲目替换会抹掉覆盖点。后续若要治理，应按测试意图逐个分类。

## 可复用教训

- 默认配置测试必须显式隔离本地 `.env`。
- 看到“本地通过/别人不通过”或“默认值断言失败”时，优先检查 settings loader 是否读了本地配置。
- `.env.example` 用于文档化默认值，但测试默认值应以代码默认值为准。
- 配置测试的第一步不是看断言，而是问“这条测试到底想测默认值、环境变量覆盖，还是 env file 加载”。
- 对 Pydantic BaseSettings 这类配置层，`Settings()` 不是“干净默认值”，而是“按 model_config 执行完整加载”。
- 本地 `.env` 是开发者状态，不应成为单元测试隐式输入。

## 未解问题

- 是否需要批量审计测试中的 `Settings()`，把默认值断言统一改成 `_env_file=None`。
- 是否需要增加一个测试 helper 来表达“无 env 的 Settings”。
- 是否需要在贡献文档中补一句：新增默认值测试时优先使用 `_env_file=None`。
- 是否需要在 CI 中显式检查没有意外 `.env` 参与测试，避免将来出现更隐蔽的配置污染。
