# 策略记忆从文件到数据库 · seed + DB 双轨制权衡

> 日期：2026-05-16
> 状态：draft
> 标签：ai-interviewer, boundary, design

## 一句话结论

策略记忆从 file 改 DB 时不要二选一——采用 markdown seed + DB 运行时正本的双轨制，文件保留 review/diff/回滚链路、DB 承担多实例聚合与自动学习，既不放弃可读性又能上 Web SaaS。

## 背景

2026-05-15 早上讨论"策略记忆模块改造方案"时，原始路线是把 `knowledge/strategy/*.md` 改成全 DB 正本。在用户连续追问下，AI 自己把方案从"纯 DB 化"修正为"file seed + DB 运行时"双轨制，并按这条路径完成了 PR1-PR8、最终 commit `538e7f1 feat: add database-backed strategy memory workflow`。

当时背景有两个关键约束：

- 产品发布形态确定是 Web SaaS（不是桌面应用），运行时不能依赖本地文件系统。
- 现有 markdown 策略已经积累了一批人工策略和自动产出策略，且开发者习惯 Cursor 直接编辑、git diff、回滚。

## 现象

### 事实

- 改造前状态：策略正本在 `ai-interviewer/backend/knowledge/strategy/*.md`，`strategy_store._list_file_strategies()` 用 `root.glob("*.md")` + frontmatter 解析读取；`experience_extractor` 通过 `save_strategy()` 直接 `_atomic_write_text(path, content)` 写本地 markdown 文件。
- 用户在 10:25 明确询问："markdown 策略记忆 是存在数据库里的嘛，不是本地文件系统吧？"暴露了 AI 此前讨论中"建议保留 markdown"的措辞被误解为"现状已是 DB"。
- 改造后状态：`strategy_store._strategy_backend()` 读 `settings.strategy_memory_backend`（默认 `"db"`，可选 `"file"` 仅用于测试 / 紧急回退）；DB 表 `strategy_memories` 含 `body_markdown` 字段保留可读正文；`knowledge/strategy/*.md` 留作 `app/scripts/import_strategy_memories.py` 的 seed 来源。
- 自动产出策略不再写本地 markdown——`experience_extractor` 现在写 `strategy_signals` DB 表，由 promotion 服务聚合后晋升为 `strategy_memories`。

### 推断

- 早期"纯 markdown"方案的隐含假设是"单实例本地运行"，未考虑容器临时文件系统、多 worker 不一致、Web UI 无法直接编辑服务器文件。
- 早期"纯 DB"方案的隐含代价是失去文件级 review/diff/回滚——这会让内容治理（人工策略审核）退化为 DB row 操作，难以走 git 工作流。
- 中间态 seed + DB 的可持续性依赖一条**反向通道**：DB 中高价值自动策略应能"导出为 markdown 供人 review 后合入 repo"——这条通道目前未实现。

### 未确认假设

- DB 正本回写到 repo 的版本管理路径尚未敲定，长期来看可能产生"线上 DB 策略 vs repo seed 策略"的分叉。
- `body_markdown` 字段是否要做版本历史（保留所有修改版本），还是只存当前版本——目前是后者，靠 `version` 字段递增但不保留旧 body。

## 期望行为

- 开发期：开发者在 Cursor 编辑 `knowledge/strategy/*.md`，跑 `python -m app.scripts.import_strategy_memories` 将种子导入 DB，运行时从 DB 读策略。
- 生产期：`experience_extractor` 等自动学习路径直接写 DB（`strategy_signals` → 晋升 → `strategy_memories`），不写本地文件。
- 任意时候：`STRATEGY_MEMORY_BACKEND=file` 可作为紧急回滚开关，能让运行时退回纯文件模式做事后排查。
- 长期：高价值自动产出策略能反向导出为 markdown，供 review 后合入 repo seed。

## 根因判断

直接原因：早期 AI 给出的"完整数据中台"方案默认 DB 是正本，未识别"开发期可读性"与"线上多实例运行"是两个不同维度的需求。

深层原因：策略记忆同时承担三类内容来源——人工种子、Bandit posterior 自动总结、Dream 周期合并——这三类对"可读/可 diff/可回滚"的需求强度不同：

- 人工种子：高（必须能在 git 里 review）
- Dream 合并：中（运营可能想看，但不必须 git 化）
- Bandit 自动：低（机器产出，主要供检索消费）

单一存储后端无法同时满足三类需求；只有用 seed + DB 双轨制才能让"开发期人工策略走 git，线上自动策略走 DB"。

触发条件：用户提出"会不会不方便操作文件系统"的产品发布场景质疑，迫使 AI 把"内容形态"和"运行时存储后端"两个概念分开。

## 调试过程

1. 第一版方案（10:15）："建立结构化 `strategy_memories` 表"，但同时强调"建议保留 markdown 展示"——措辞模糊，让对方误以为现状已是 DB。
2. 对方追问（10:18）："这刚才量有些大呀，风险高不高"——AI 立即承认"如果按我刚才那一整套一次性做，风险很高"，给出分阶段渐进版。
3. 对方追问（10:25）："markdown 策略记忆 是存在数据库里的嘛"——AI 才显式澄清"当前是本地文件系统，不是数据库"，并把"当前 vs 建议"二态说清楚。
4. 对方追问（10:26 / 10:31）："Web SaaS 会不会不方便操作文件系统？""那 markdown 策略记忆 还是得写数据库呀"——AI 才落到"markdown 作为内容格式保留，数据库作为运行时存储正本，文件系统只作为开发期种子/导入来源"的双轨制。
5. 实施阶段 PR1-PR8 全部按双轨制执行，最终 commit `538e7f1` 落地。

## 解决方式

最终方案（双轨制）：

- `strategy_memories` DB 表是运行时正本，字段含 `id / slug / source / status / promotion_stage / confidence / support_count / body_markdown / version / content_hash`。
- `knowledge/strategy/*.md` 留作 seed，启动时不自动 import；需要时手动跑 `python -m app.scripts.import_strategy_memories`。
- `strategy_store._strategy_backend()` 默认 `"db"`，`"file"` 仅保留作测试 / 紧急回退。
- 自动产出策略不写本地 markdown——走 `strategy_signals` → 聚合 → `strategy_memories` 链路。

## 可复用教训

- **数据架构选型先问"是否上 SaaS"**：单实例本地运行可用纯文件，多实例 / 容器化必须考虑 DB 或对象存储正本。
- **同一内容来源分类型差异化存储**：人工 / 自动 / 周期合并三类内容对"可读/可 review/可回滚"需求强度不同，强行用单一存储后端会牺牲一边。
- **讨论改造方案时必须先用一句话明确"当前状态 vs 目标状态"**：避免"建议"和"现状"混在一段——本案中 AI 第一次回答把"建议保留 markdown"放在一段措辞里，导致用户误以为现状已是 DB。
- **保留紧急回退开关**：即使默认 DB，`STRATEGY_MEMORY_BACKEND=file` 仍可用作事后排查通道——不要为了"干净"删掉旧路径。
- **`body_markdown` 字段是双轨制的桥**：DB 行里保留 markdown 正文，既能上 SaaS 又不失人类可读性，是后续 skill / 题库等类似系统的参考模板。

## 未解问题

- DB 正本回写 repo 的反向通道尚未实现：自动产出的高价值策略如何"导出为 markdown 供人 review 后合入 repo seed"？
- 长期是否会产生"线上 DB 策略 vs repo seed 策略"分叉？需不需要"定期 sync 检查 / diff 工具"？
- `body_markdown` 是否需要保留版本历史（保留所有修改版本）？当前只靠 `version` 字段递增、旧 body 被覆盖。
- 类似双轨制方案是否适用于结构化题库（P2 路线）和 skill 记忆？题库下一步要做类似选择。

## 扩展发现（2026-05-16 复盘后自检）

后续全 observe-only 路线自检发现，本案不只是"文件到数据库的架构权衡"问题，还暴露出更基础的上线前置条件：`strategy_memories=0`，6 个 `knowledge/strategy/*.md` seed 未导入，导致 db backend 下策略检索实际返空。

已手动补跑 `python -m app.scripts.import_strategy_memories`（`imported=6 updated=0 unchanged=0 skipped=1`）。完整数据真空诊断与健康检查建议集中记录在 `2026-05-16-失败分类升档数据真空.md`，本案只保留这个架构层面的提醒：**双轨制一旦引入 DB，"内容是否已导入"必须成为上线检查的一部分。**
