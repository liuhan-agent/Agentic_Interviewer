# Worktree 运行目录混乱

> 日期：2026-05-21
> 状态：draft
> 标签：ai-interviewer, tooling, debugging, verification

## 一句话结论

多 worktree / 多分支本身没问题，但如果真实后端服务、用户运行目录、Agent 修改目录和 DB 内容导入目录不是同一个工作区，功能验证就会变成“看起来跑了，其实不是同一份代码”的悬空证据。

## 背景

结构化题库改造期间，为了隔离开发，曾使用 Codex worktree 或分支工作区推进。后来用户在真实运行 AI 面试官时，期望统一使用 `D:\Agent\Agentic_Interviewer` 作为当前主工作区。但会话中曾出现分支无法切换、worktree 占用、两份源码和两套环境的问题，导致真实面试 session 的验证结果一度难以和刚实现的代码对应起来。

这类问题不是业务逻辑 bug，但会直接破坏验证可信度：如果 Agent 在 worktree A 改代码，用户在主目录 B 跑服务，DB 又可能导入了另一个目录下的 YAML/Markdown，那么“跑了一轮面试”并不能证明当前代码有效或无效。

## 现象

### 事实

- 会话中用户遇到过类似错误：
  - `fatal: 'codex/structured-question-bank-p0' is already used by worktree at 'C:/Users/34329/.codex/worktrees/structured-question-bank-p0/Agentic_Interviewer'`
- 用户明确要求：从现在开始把 `D:\Agent\Agentic_Interviewer` 当唯一运行目录。
- 后续开发约束已经调整为：
  - 不主动创建新的 worktree。
  - 命令、测试、import、服务验证都以 `D:\Agent\Agentic_Interviewer` 为 workspace root。
- 当前执行 `git worktree list` 仍能看到主目录和一个 Codex worktree 残留：
  - `D:/Agent/Agentic_Interviewer  [main]`
  - `C:/Users/34329/.codex/worktrees/d467/Agentic_Interviewer  [detached HEAD]`
- 当前主工作区分支为 `main`。

### 推断

- 当时结构化题库的部分实现、提交或验证可能发生在 Codex worktree 中，而用户真实后端服务或前端访问的是主工作区。
- 真实 session 验证出现“不像刚实现的代码在生效”的感觉时，除了业务逻辑，还必须检查运行目录、分支、后端进程 cwd、DB import 状态。
- worktree 残留本身未必有害；真正危险的是没有显式确认“当前运行进程使用的是哪份源码”。

### 未确认假设

- 本文没有查当时后端进程的启动日志，因此不能确认具体哪一次真实 session 使用了哪个 cwd。
- 本文没有比对当时两个 worktree 的完整 diff，也不判断某个 worktree 是否可以删除。
- 当前 `C:/Users/34329/.codex/worktrees/d467/Agentic_Interviewer` 是否还有未保留价值，需另行检查后再决定清理。

## 期望行为

在本项目中，涉及真实运行和真实 session 验证时，应默认使用唯一运行目录：

`D:\Agent\Agentic_Interviewer`

验证前至少确认：

- `git worktree list`
- `git branch --show-current`
- `git status --short`
- 后端服务启动 cwd。
- 前端连接的 backend URL。
- question seeds / skill playbooks 是否在同一个运行库中完成 import。
- 当前 session trace 是否来自刚启动的服务。

如果存在多个 worktree：

- 可以保留作为只读历史或隔离实验，但不要把它当运行目录。
- 不要在另一个 worktree 中提交后，直接拿主目录服务验证。
- 切分支失败时，优先检查 worktree 占用，而不是强行 reset 或 checkout。

## 根因判断

直接原因：开发隔离使用了 worktree，但真实运行验证没有同步建立“唯一运行目录”约束，导致分支、目录、服务进程、DB 内容之间的对应关系不清晰。

深层原因：

- Agent 开发偏向“隔离安全”，用户验证偏向“当前本地服务可用”。两者目标不同，如果没有显式约定运行目录，就会出现双轨。
- 结构化题库 / playbook 这类内容系统还依赖手动 import。即使代码合并了，如果 DB 仍是旧内容，也会像代码没生效。
- 长会话中连续提交、push、PR、合并、清理、重新运行服务，容易让“我现在在哪个分支 / 哪个目录 / 哪个进程”变成隐形状态。

## 调试过程

1. 用户在验证结构化题库时发现本地还有不同分支和 worktree。
2. 切换分支时报错，提示目标分支已被某个 Codex worktree 使用。
3. 进一步确认存在主工作区和 Codex worktree 两份源码。
4. 用户要求直接合并到 `D:\Agent\Agentic_Interviewer`，并明确该目录为唯一运行目录。
5. 后续工作改为在主工作区执行，不再主动创建新 worktree。
6. 后续规划文档也补入“不使用新 worktree，除非用户明确要求”的约束。

## 解决方式

已采取的工作方式修正：

- 将 `D:\Agent\Agentic_Interviewer` 作为唯一运行目录。
- 当前任务所有命令都显式设置 `workdir` 到主工作区或其 backend/frontend 子目录。
- 不再主动创建新的 git worktree。
- 在提交前用 `git status --short` 确认只 stage 本次相关文件。
- 对 DB-backed 内容改造，运行 import 命令时也在主工作区 backend 下执行。

建议后续补强：

- 在本地开发命令速查中加入“验证前环境身份检查”：
  - 当前 cwd。
  - 当前 branch。
  - worktree list。
  - 后端进程 cwd。
  - DB import counters。
- 后端启动时在日志中打印 git commit / branch / cwd / question seed count / playbook count，方便把真实 session 绑定到代码版本。
- Admin system overview 可展示 backend cwd、commit sha、question seed active count、skill playbook active count。

## 验证方式

这类问题的验证不是单元测试，而是运行环境核对：

- `git worktree list` 只作为风险提示，不作为失败条件。
- `git branch --show-current` 应与预期一致。
- `git status --short` 应能区分本次改动、无关 untracked、已 stage 文件。
- 后端服务进程 cwd 应位于 `D:\Agent\Agentic_Interviewer\ai-interviewer\backend` 或由该目录启动。
- 内容 import 输出应匹配预期，例如 question seeds / playbook cards 的 imported/updated/unchanged 计数。
- 真实 session trace 中最好能看到 commit/version/cwd，当前系统这点仍需补强。

## 可复用教训

- Worktree 是开发隔离工具，不是运行环境管理工具。
- 真实面试验证前，必须先证明“跑的是哪份代码”。
- 对内容驱动系统来说，代码版本和 DB 内容版本同样重要；只确认 git commit 不够。
- 分支切换失败时，不要急着 reset/checkout，先查 `git worktree list`。
- 长会话中，Agent 应定期复述当前工作目录、分支、服务状态，尤其在用户开始真实验证前。
- “测试通过”不等于“用户本地服务运行的是这份代码”；两者是不同证据。
