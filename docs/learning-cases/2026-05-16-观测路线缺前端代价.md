# 持久化路线 P0 跳过前端 · 9 个 commit 数据"写了没人读"的代价

> 日期：2026-05-16
> 状态：draft
> 标签：ai-interviewer, boundary, debugging

## 一句话结论

P0 减负"只做后端不做前端"把 9 个 drift commit 推进了"写了数据没人看"的薛定谔态——shadow rollout 类路线必须把"可观测前端 / admin endpoint"视为闭环必要件，不能用"P1 再说"兜底。

## 背景

2026-05-15 17:55-17:58 规划 drift feedback 持久化 P0 时，AI 一次问了 5 个澄清问题，第 5 个是"P0 是否加前端 admin？"用户和 AI 一致选了"P0 只后端接口，AdminPanel 面板留 P1"。这个决定看起来是合理的 P0 减负——后续 7 个 PR（实际拆成 8 commit）顺利落地，db_shadow 默认开启。

但 6 小时后（21:48 重新汇总路线）才发现：db_shadow 一路升档默认值的同时，**prompt 实际还是走 monitor，DB 里的 `(dim, check, fc)` 桶没有任何路径在消费**。过去 9 commit 处于"写了数据没人读"的薛定谔态，直到 `bbdeff5` 补 P1 parity admin endpoint 才真正能看到 DB 数据。

这是"shadow rollout 纪律"和"observe-only 闭环"两条原则的失败案例——**P0 减负把闭环砍掉了**。

## 现象

### 事实

- 17:58 对话敲定 drift P0"只后端接口，AdminPanel 面板留 P1"。
- 18:00 之后 8 个 commit 顺利落地：
  - `50e4ef6 feat: add verifier drift persistence models`
  - `e5c00cb feat: dual-write verifier drift events from verification node`
  - `4aa420c feat: aggregate and prune persisted verifier drift events`
  - `5cc219c feat: switch drift feedback to db_shadow with admin surface`
  - `0d1a2ed fix: thread failure_categories into drift feedback callers`
  - `d1f66a0 feat: schedule periodic drift maintenance jobs`
  - `91d33fb feat: expose drift freshness through admin api`
  - `1ab38e6 docs: add drift persistence plan`
- 这 8 个 commit 完成后状态：`drift_feedback_source` 默认 `"db_shadow"`，事件 dual-write 到 DB，聚合 + retention + scheduler 都到位。
- 但 `prompt_feedback._load_overruled_patterns` 在 `db_shadow` 模式下**仍然返回 monitor 的结果**（DB 查只用于 `log.info` parity 比较，不进 prompt）。
- 5 个 admin endpoint 中（events / patterns / freshness / aggregation·run / retention·run）**没有一个**展示"DB 和 monitor 在桶集合上的重合度"——所以无法判断"是否可以从 db_shadow flip 到 db"。
- 21:48 AI 重新汇总路线时自评："`drift_feedback_source=db_shadow` 默认开了 7 个 commit，但 prompt 实际还是走 monitor，DB 的 `(dim, check, fc)` 桶**目前没有任何路径在消费**。如果不做 P1 parity 可观测 → 不知道何时能 flip 到 `db` → 过去 8 个 drift commit 处于「写了数据没人读」的薛定谔态。"
- 22:08 才补完 `bbdeff5 feat: expose drift feedback shadow parity through admin api`，新增 `/admin/drift/shadow-parity` 路由 + 11 个测试用例，至此 P0 减负的代价才被挽回。

### 推断

- "shadow rollout"原则要求"先看数据再升档"。本案 P0 减负的本质是把"看"这一步砍掉了——升档（db_shadow 默认 ON）做了，但"看"被推到 P1。
- 之所以容易低估"看不见"的代价，是因为前面已经守住了 prompt 不动 / db_shadow / best-effort 三条纪律，让"P0 没什么风险"的感觉过强；忽略了"没有可观测就没有决策依据"。
- 减负的真正代价是：8 个 commit 期间没人能回答"flip 到 db 安全吗"，所以**路线无法前进**——闭环没合上，等价于这 8 commit 不存在。

### 未确认假设

- 类似风险可能在其它"observe-only"路线上重复——比如 strategy_memory ranking 的 `reward_shadow` 模式（commit `20fefe5`）：如果没有 admin 展示"shadow vs metadata 排序的差异"，是否也会进入同样状态？目前尚未验证。
- 未来 P2 结构化题库的"structured shadow"路径如果不配 admin parity，是否会重复同样的代价？规划阶段需要预先检查。

## 期望行为

- 任何 `db_shadow` / `observe-only` 类路线在 P0 完成时，必须能回答两个问题：
  1. 这条路线的数据 P0 完成后由谁读？怎么读？
  2. 如果要升档（从 shadow → 正式），决策依据从哪里来？
- 如果回答不上，"P0 没做完"。`admin endpoint` / 可观测前端不是 P1 后置项，是 P0 必要件。

## 根因判断

直接原因：P0 第 5 个澄清问题选"只后端接口，AdminPanel 面板留 P1"——把"可观测前端"从必要件降级为后置项。

深层原因：

- `shadow rollout` / `observe-only` 路线的本质就是"先写数据，再看数据决定是否升档"——"看"是这类路线的核心约束，不是可选项。
- 把"看数据"砍掉等于让升档决策没有依据——8 个 commit 完成后，路线**无法前进**，因为没人能回答"flip 到 db 安全吗"。
- 规划清单里没有"这条数据由谁读"的强制问题——只问了"是否加前端"，而前端 / admin endpoint 都是为了让人能读数据，缺一就闭环不合。

触发条件：前面 3 条纪律（prompt 不动 / db_shadow / best-effort）已经守住，给人"P0 没什么风险"的错觉；加上前端跨栈成本高（typecheck / lint / npm test 全套），自然倾向于推后。

## 调试过程

1. 17:55-17:58 规划 P0 时一次问 5 个澄清问题，第 5 个选"只后端"。当时没有人识别出"这条数据由谁读"这个问题。
2. 18:00-21:00 8 个 commit 顺利落地，覆盖模型 / dual-write / 聚合 / retention / scheduler / freshness / docs。期间没有"汇报数据"的环节，所以没人意识到"数据没人读"。
3. 21:48 AI 重新汇总路线时（综合 8 份 PChat + git log）才自评："过去 8 个 drift commit 处于「写了数据没人读」的薛定谔态。"
4. 21:48 立即给出 P1 修补方案：新增 `app/services/drift_feedback_parity.py` 服务 + `/admin/drift/shadow-parity` admin endpoint，让运营能看 7 日 Jaccard 重合率，作为 flip 决策依据。
5. 22:08 `bbdeff5` 提交，1 commit 完成：8 service 用例 + 3 admin 集成用例全绿。
6. 中间还遇到测试夹具全局赋值导致 16 个回归的弯路（已记录在另一篇复盘）。

## 解决方式

P1 补救（`bbdeff5`）：

- 新增 `app/services/drift_feedback_parity.py::compute_drift_feedback_parity()`：自动扫描 dimensions、对每个 dim 计算 monitor vs DB 的 patterns 集合、出 Jaccard 相似度（含 intersection / monitor_only / db_only 三个名单）。
- 新增 `GET /admin/drift/shadow-parity?top_n=5&min_support=2&dimensions=A,B` admin 路由。
- 文档加 §7 说明 flip 阈值：连续 7 日各 dim avg jaccard ≥ 0.9 可考虑把 `drift_feedback_source` 默认改 `"db"`。
- best-effort：DB 失败不 500、auto-scan 失败退化为"仅 monitor"。

此后路线才能基于"看 7 天数据"决定下一步动作，闭环合上。

## 可复用教训

- **凡是 `db_shadow` / `observe-only` 类路线，"可观测前端 / admin endpoint" 必须列为 P0 必要件**，不能列为 P1 后置项。
- **规划清单加一道强制闸**：这条数据 P0 完成后由谁读？怎么读？如果回答不上，"P0 没做完"。
- **"P0 减负"的代价要看后果**：减一个前端任务 = 数据写了没人读 = 8 个 commit 进入薛定谔态 = 路线无法前进。表面省一个 PR，实际多绕 1 个 P1 + 1 次回归弯路。
- **shadow rollout 的"看"是核心约束**：写代码（升档默认值）做了，"看"被推到 P1，等于路线只前进了一半。
- **路线推进感不等于实际推进**：8 commit 落地，看似进展顺利，但**没有人能回答 flip 安全吗**——这是路线停滞的信号。
- **后端 admin endpoint 是最小可观测形态**：即使不动前端，也要让 admin 能 curl 一个 JSON 接口看数据；前端可以 P1 再做，但 admin endpoint 不能省。
