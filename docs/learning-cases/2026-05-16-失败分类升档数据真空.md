# failure_categories 升档时发现"无数据可决策" · observe-only 数据真空

> 日期：2026-05-16
> 状态：draft
> 标签：ai-interviewer, boundary, debugging

## 一句话结论

observe-only 路线做完代码后必须立即跑一次"数据完整性自检"——本地 70 trace / 15 evaluator trace 全是 PR1 之前的、normalize 命中率 16%、neither 桶 93%，直到升档讨论时才被发现，过去 5 commit 等价于空跑。

## 背景

2026-05-15 17:35-17:49 完成 failure_categories taxonomy P0（7-enum + 全链路透传 + admin stats endpoint）的 3 个 commit（`75fd45c / 2d14c42 / bdcb617`），全程按 A1+B1+C1 边界（守 7 enum / 不动 schema / 只观测不消费）执行，1396 后端测试全绿。

22:09 进入"failure taxonomy 升档讨论"轮，AI 拉本地数据准备给出"升档 vs 不升档"的决策建议，结果发现本地 70 trace 中 evaluator trace 只有 15 条，且**全部是 PR1（commit `75fd45c`）之前的残留**——evaluator 还未输出 `failure_categories`，所有 LLM 侧 fc 都是空列表，normalize keyword 推断只抓到 1 条（16% 命中率），93% 落入 "neither" 桶（LLM 和 keyword 都没识别出）。

也就是说，过去 5 commit（`75fd45c → bdcb617` 写完 + `5cc219c / 0d1a2ed` 在 drift 路径上接 fc）虽然代码全绿，但**本地数据没有任何 PR1 之后的真样本**，路线在数据层等价于空跑。

## 现象

### 事实

- `.local/interviewer.db` 总 trace 70 条，evaluator trace 15 条。
- 22:11 服务层（`compute_failure_category_overlap_stats`）跑出来：
  - `sample_size: 15`
  - `llm_only: 0`（evaluator 还未输出 fc）
  - `normalize_only: 1`（keyword 只抓到 1 条）
  - `both: 0`
  - `neither: 14`（93% 两边都识不出）
- 这 15 条 evaluator trace 全部是 `75fd45c` 之前的残留（PR1 之后没有真面试跑过）。
- 三类可能的升档动作（A 退休 normalize / B 扩 enum 到 10 / C 调 evaluator prompt 强调"务必填写"）**全部需要 PR1 之后的真数据**作决策依据，本地 0 条。
- 22:12 用户选 D1：不升档、不动代码、等数据。
- 22:13 失败 taxonomy 升档进入"被动等"状态。

### 推断

- 路线只有"写代码 ship → 测试通过 → 跑下一个 PR"的循环，没有"PR ship 后 N 天再回头看本地数据真在累积"的回检步骤。
- 本地开发环境频繁 reset `.local/interviewer.db`（或开发时 DB 被部分清理），但没有"数据继续累积"的环境——这让 observe-only 路线"看不到效果"。
- 同样的"数据真空"问题在其它 observe-only 路线（drift db_shadow、strategy reward_shadow）上也可能存在——仅因升档讨论被触发才暴露 failure_categories 这一处。
- 16% 的 normalize 命中率（即使在 PR1 之前样本上）暴露了 keyword 规则本身在中文 evaluation 上不够覆盖——但这件事本身也需要更多样本才能确认。

### 未确认假设

- 是否还有其它 observe-only 路线（drift db_shadow / strategy reward_shadow / generator avoid_patterns）也处于数据真空？需要主动检查每条路线的本地数据状况。
- 自动构造数据（fixture 脚本 / 公开面试记录回放）的代价是否值得？目前没有评估。
- 真实面试数据要积累多久才能支撑统计决策？路线讨论里推测"至少 100 条 evaluator trace"，但这个阈值本身是经验值。

## 期望行为

- 任何 observe-only / shadow PR ship 时必须配两件事：
  1. **数据采集状况自检脚本**：能跑一个命令立刻看到"PR1 之后 N 条样本、各桶分布、最早样本时间戳"。
  2. **N 天后回检截止**：PR ship 后 N 天（例如 7 天 / 30 天），强制 review 本地 / 线上数据是否在累积，如果是 0 条要立即调查。
- 不要把"先写完代码 ship 上"当成路线终点——observe-only 路线的真正终点是"数据累积到能支撑下一个决策"。

## 根因判断

直接原因：commit `75fd45c → bdcb617` ship 后没有主动验证"是否累积到 PR1 之后的样本"，时间隔了 5 小时 + 5 commit 才被升档讨论触发暴露。

深层原因：

- observe-only 路线的隐含假设是"代码 ship 后数据会自动累积"——本地开发场景下这个假设经常不成立（DB 被 reset / 没人真跑面试 / fixture 跑不进 evaluator）。
- 路线推进节奏只看 "PR 是否绿"，没把"数据是否在累积"当成同等重要的推进信号——前者每个 commit 都有 1396 → 1461 passed 的数字，后者没有任何自动化指标。
- failure_categories 路线特别脆弱：它依赖 evaluator LLM 在真实面试中输出新字段，本地若没有"真实跑一场面试"的常规习惯，PR1 之后样本永远是 0。

触发条件：升档讨论时被迫拉本地数据，才发现"数据真空"。如果一直没人开升档讨论，这种状态可以持续到无限远。

## 调试过程

1. 22:09 用户选 A（failure taxonomy 升档讨论），AI 准备拉数据给出"升档 vs 不升档"的决策包。
2. 22:11 AI 跑 `compute_failure_category_overlap_stats(session, limit=200)` 服务层，本地 SQLite 返：sample_size=15 / llm_only=0 / normalize_only=1 / both=0 / neither=14。
3. AI 立即识别出："这 15 条全是 PR1（75f5180）之前的残留 trace，evaluator 还未输出 `failure_categories`，所以全部 LLM 侧为 []。" + "样本量 15 太小，不足以支撑「升档 vs 不升档」的统计结论。" + "normalize 只抓到 1 个说明 keyword 规则本身在不同席位的 evaluation 上命中率极低（16%）。"
4. AI 给出 4 类应对路径（D1 不动等数据 / D2 主动构造 fixture / D3 凭经验扩 enum / D4 只调 prompt），并强烈推荐 D1。
5. 22:12 用户选 D1。
6. 22:13 路线进入"被动等"，AI 同步刷新 7 项路线状态表，提醒：drift parity 7 天 + failure taxonomy 数据 + Q2 题库讨论三件事在等。

## 解决方式

本案没有"修复"——选择了 D1（不动代码等数据），即接受路线在 failure_categories 升档方向上**暂时无法前进**。

实际上"暴露问题"本身就是这次 retrospective 的核心价值：之前 5 commit 在数据层等价于空跑，这件事如果不开升档讨论，可能一直不会被发现。

可能的补救路径（未来动作）：

- 添加 `python -m app.scripts.failure_category_data_health_check` 自检脚本，能输出 "PR1 之后样本数 / 最早样本时间戳 / 各桶分布 / 数据健康度评分"。
- 在 `docs/PLAN_*.md` 模板里加 checklist："PR ship 后 7 天回检数据完整性"。
- 给所有 observe-only 路线（drift db_shadow / strategy reward_shadow / generator avoid_patterns）跑一次同类自检，看是否有其它路线处于同样状态。

## 验证方式

- 当前没有正式验证——只是观察到"数据真空"现象本身。
- 等积累足够 PR1 之后的真面试数据（至少 100 条 evaluator trace）后再重跑 `compute_failure_category_overlap_stats`，才能验证 normalize 命中率 / neither 桶比例是否仍然如此。

## 可复用教训

- **observe-only PR ship 时必须配两件事**：(a) 数据采集状况自检脚本；(b) PR ship 后 N 天回检截止。
- **"先写完代码 ship 上"不是路线终点**——observe-only 路线的真正终点是数据累积到能支撑下一个决策。
- **"代码全绿"不等于"路线在推进"**——代码层 5 commit 进展顺利，但数据层 0 增长，路线实质停滞。
- **数据真空发现的方式不应该是被动**——不要等升档讨论时才拉数据。每个 observe-only PR 都应该带一个"7 天后看数据"的提醒。
- **本地开发环境的 DB 不可靠**：频繁 reset / 没人真跑面试 / fixture 跑不进 evaluator——所以数据层验证必须有"在线上跑 N 天"的替代路径。
- **路线汇总时主动检查数据真空**：本案 AI 在路线汇总（21:48）和升档讨论（22:11）时各识别一次"数据看不到"的问题——这种"路线层 retrospective"应该成为常规动作。

## 未解问题

- 是否还有其它 observe-only 路线（drift db_shadow / strategy reward_shadow / generator avoid_patterns）也处于数据真空？需要主动跑同类自检。
- 主动构造数据（fixture 脚本 D2a / 手动跑面试 D2b / 公开面试回放 D2c）的代价是否值得？目前没有评估。
- 真实面试数据要积累多久才能支撑统计决策？路线讨论里推测"至少 100 条 evaluator trace"——这个阈值需要 cohort-aware 验证。
- 是否应该有"数据健康度仪表板"？把所有 observe-only 路线的样本数 / 累积速度 / 最新样本时间戳放一个 admin 页面，让数据真空一眼可见？
- normalize keyword 规则在中文 evaluation 上的低命中率（16%）是规则本身的问题还是样本偏差？需要更多数据才能区分。
