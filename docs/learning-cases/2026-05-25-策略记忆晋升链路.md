# 策略记忆晋升链路

> 日期：2026-05-25
> 状态：draft
> 标签：ai-interviewer, logic, debugging

## 一句话结论

即时奖励到策略记忆晋升是连通的，但不是单轮 reward 直接晋升，而是经过 bandit posterior、strategy signal、promotion 三段累计链路。

## 背景

在优化后台观测台“策略记忆”模块时，需要解释“即时奖励”“最近策略使用归因”“晋升候选”“全局策略记忆”之间的关系。用户关心 `即时奖励` 是否能够自然推动新策略晋升。

这次问题不是一个后端 bug，而是一个典型的“观测数据看起来像一条链，但实际分属不同生命周期”的理解风险。后台观测台同时展示：

- 最近策略使用归因：来自 `StrategyMemoryUsage`，记录已有策略记忆被注入某轮出题后的评分归因。
- 晋升候选：来自 `StrategySignal`，记录未来可能晋升为新策略记忆的聚合证据。
- 策略学习后验：来自 bandit posterior，记录某个 `context_key / action_id` 的 reward 累计。
- 全局策略记忆：来自 `StrategyMemory`，是运行时可被检索和注入的策略资产。

这些表都和 reward、action、context 有关，但不是同一个“reward 直接变策略”的线性过程。

## 现象

### 事实

- `reward_update_node` 会在每轮有效评分后计算 `immediate_reward`。
- 同一轮会把 reward 写入 bandit posterior、`InterviewTurn` 和已有策略记忆的 `StrategyMemoryUsage`。
- `experience_extractor_node` 在面试完成后读取 QA history 与 bandit posterior，生成 `StrategySignal`。
- `promote_strategy_signals()` 按 `group_key` 聚合 `StrategySignal`，满足阈值后才创建 `StrategyMemory`。
- `StrategyMemoryUsage.immediate_reward` 主要用于已有策略记忆的使用归因和质量统计，不是新策略晋升的直接输入。
- `experience_extractor_node` 为 bandit insight 写入 `StrategySignal.immediate_reward` 时，存的是 posterior mean / 平均 reward，而不是某个 turn 的原始即时 reward。
- `promote_strategy_signals()` 对 bandit 路径只接受 `high_reward_arm`，不会把 `low_reward_arm` 晋升为可用策略。
- 低置信晋升要求至少 30 个 distinct session；稳定晋升要求至少 100 个 distinct session。

### 推断

- UI 同时展示 usage reward、signal、promotion 状态时，容易让人误以为“最近策略使用归因”中的 reward 会直接晋升新策略。
- 对用户更有解释力的口径是：usage 是“已有策略被使用后的表现”，signal 是“新策略候选的证据”。
- “即时奖励”这个词本身容易给人一种单步触发感，但当前系统设计是跨 session 的统计学习，单轮高分只会贡献一次观察。

### 未确认假设

- 当前真实环境中的 `strategy_signals` 数量是否足以观察到自然晋升趋势，需要结合数据库样本确认。
- 是否需要单独暴露 promotion readiness，以减少对 usage 列表的误读。
- 自动晋升 scheduler 打开后，在真实长跑数据里是否会稳定产生低置信策略，需要继续看 `strategy_signals` 的 session 支持数分布。

## 期望行为

后台观测台应清楚区分三类数据：

- 每轮即时奖励：本轮 action 的即时反馈。
- 策略使用归因：已有策略记忆被注入后的效果记录。
- 晋升信号：跨 session 累计后可能生成新策略记忆的候选证据。

更精确地说，后台应该帮助用户形成下面这条心智链：

```text
一轮有效评分
  -> immediate_reward
  -> BanditPosterior(context_key, action_id)
  -> 面试完成后 experience_extractor 读取 posterior
  -> StrategySignal(group_key)
  -> promotion job 聚合跨 session signal
  -> StrategyMemory(promoted_signal)
```

同时也要明确另一条并行链：

```text
已有 StrategyMemory 被注入出题
  -> question.strategy_memory_refs
  -> reward_update 写 StrategyMemoryUsage
  -> refresh_strategy_memory_stats 聚合 StrategyMemoryStats
  -> quality transition 可禁用或稳定已有策略
```

这两条链都用 reward，但用途不同。

## 关键数据结构对照

| 数据结构 | 写入时机 | 主要含义 | 是否直接晋升新策略 |
|---|---|---|---|
| `BanditPosterior` | 每轮 `reward_update` | 某个上下文/动作 arm 的累计 reward 后验 | 间接，会被 extractor 读成 signal |
| `InterviewTurn` | 每轮 `reward_update` | 本轮评分事实、失败类型、即时 reward | 间接，QA pattern extractor 会读 |
| `StrategyMemoryUsage` | 已有策略被注入后完成评分 | 已有策略的使用归因和质量反馈 | 否 |
| `StrategyMemoryStats` | 手动/自动刷新统计 | usage 的聚合健康度 | 否，但会影响已有策略质量转换 |
| `StrategySignal` | 面试完成后的 extractor | 新策略候选证据 | 是，promotion 的直接输入 |
| `StrategyMemory` | promotion job | 可被运行时检索注入的策略资产 | 已晋升结果 |

## 错误心智模型与正确心智模型

错误心智模型：

```text
最近策略使用归因里的 immediate_reward 高
  -> 这条 usage 会直接晋升成新的策略记忆
```

正确心智模型：

```text
最近策略使用归因里的 immediate_reward 高
  -> 说明已有策略这次被用得还不错
  -> 后续刷新 stats 后，可影响已有策略的稳定/禁用判断
```

新策略晋升的正确路径是：

```text
多轮 reward 更新 posterior
  -> 面试完成后 extractor 生成 StrategySignal
  -> 多个 session 支持同一 group_key
  -> promotion 达阈值后创建 StrategyMemory
```

这个区别很重要，因为它决定排查入口：看“已有策略质量”时查 usage/stats；看“新策略为什么没晋升”时查 signal/posterior/extractor。

## 根因判断

直接原因：`StrategyMemoryUsage` 和 `StrategySignal` 都含有 reward 相关字段，但它们承担的生命周期不同。

深层原因：策略学习链路分为“行为即时反馈”“已有策略质量归因”“新策略候选晋升”三层，但后台观测台最初把这些概念放在同一个模块里，容易形成一条过度简化的心智模型。

触发条件：当用户看到“即时奖励”“最近策略使用归因”“晋升候选”同时出现时，会自然追问是否存在 reward 到 memory 的直接晋升关系。

更深一层的问题是：字段命名中的 `reward` 只描述数值性质，不描述归属生命周期。`StrategyMemoryUsage.immediate_reward`、`StrategySignal.immediate_reward`、`BanditPosterior.alpha/beta` 背后都是 reward，但一个服务已有策略归因，一个服务晋升候选，一个服务 bandit 决策。只看字段名会丢掉上下文。

## 调试过程

1. 从 `reward_update_node` 确认即时奖励的计算和写入路径。
2. 继续追踪 `experience_extractor_node`，确认新策略候选来自 QA pattern 或 bandit posterior insight。
3. 查看 `promote_strategy_signals()`，确认晋升阈值基于 `StrategySignal` 聚合。
4. 对比 `StrategyMemoryUsage`，确认它服务于已有策略的 usage/stats，而不是直接生成新策略。
5. 对照后台 UI 文案，确认“最近召回归因”会误导为检索召回，因此改成“最近策略使用归因”。
6. 再确认晋升阈值：低置信晋升不是看单条 reward，而是 `distinct_sessions >= 30`、`avg_reward >= 0.68`、`overrule_rate <= 20%`。
7. 最后把结论收敛为两条并行链路，避免把 usage/stats 与 signal/promotion 混成一条链。

## 解决方式

本次没有修改后端逻辑。当前解决方式是澄清后台观测台文案，将“最近召回归因”改为“最近策略使用归因”，并明确它展示的是完成评分轮次中的策略注入和 reward 归因。

同时，后续解释策略记忆时采用以下术语边界：

- `使用归因`：已存在策略记忆被注入后的结果。
- `晋升候选`：尚未成为策略记忆的 signal group。
- `全局策略记忆`：当前运行时会参与检索注入的策略资产。
- `自动晋升`：定期运行 promotion pass，不等于每轮 reward 即时晋升。

## 可复用教训

- 看到 reward 字段时先问：这是 action reward、usage attribution，还是 promotion evidence。
- 判断“能否晋升”时优先查 `strategy_signals` 和 promotion 阈值，而不是只看 `strategy_memory_usages`。
- UI/观测文案应避免把 retrieval、usage、promotion 这些不同阶段统称为“召回”或“归因”。
- “有 reward”只能说明学习事实存在，不能说明晋升条件已满足。
- 新策略晋升排查优先级应是：posterior 是否更新、extractor 是否跑、signal 是否生成、group 是否跨 session 达阈值、promotion 是否执行。
- 已有策略质量排查优先级应是：usage 是否写入、stats 是否刷新、global stats 是否足够、quality transition 是否触发。

## 未解问题

- 是否需要新增“晋升准备度”视图，直接展示每个 signal group 距离低置信晋升还差多少 session 或 reward。
- 是否需要在 Trace Explorer 中串起单轮 reward、posterior 更新、signal 生成的完整证据链。
- 是否需要在 `/admin/strategy-signals` 里直接展示“差多少 session / 差多少 reward / overrule 是否超阈值”。
- 是否需要为 `StrategySignal.immediate_reward` 改名或在 API 层加说明，避免被误解成单轮即时 reward。
