# 评分一致性归一化问题

> 日期：2026-05-13
> 状态：draft
> 标签：ai-interviewer, logic, boundary, debugging

## 一句话结论

评分系统里的 `score`、`passed`、覆盖证据、verifier 结论不能各自为政，必须在后端用确定性规则统一收口，否则报告会出现“10 分但未通过/覆盖不足”这类自相矛盾状态。

## 背景

当时正在改造 AI 面试官的面试报告评分语义。用户在报告页看到一个明显不协调的状态：某些维度分数很高，甚至 `10.0 / 10`，但 badge 仍然显示“覆盖不足”或类似未通过状态。用户进一步追问 `coverage_status` 是不是 evaluator 节点计算的、prompt 是怎么约束的，以及“如果打了 10 分，代码强制把 evaluation.passed / dimension_status 改 passed”是否合理。

讨论后形成的判断是：不能简单用“10 分必过”这种单条件兜底，因为高分也可能伴随 acceptance check 的 `no` 或 rubric coverage 的 `missing`。更稳妥的做法是加一个后端内部的一致性归一化函数，同时看分数、验收检查、覆盖证据，以及 verifier 的高置信推翻。

## 现象

### 事实

- 报告页出现过高分维度仍显示“覆盖不足”的状态。
- 用户明确质疑：如果维度已经 `10.0 / 10`，为什么还会显示未通过或覆盖不足。
- 当时已经有 evaluator 输出 `score`、`passed`、`acceptance_check_results`、`rubric_coverage` 等信号。
- workflow 中还有 verification 节点，它在 evaluator 后运行，可能根据 verifier 结果修改 `evaluation.passed`、`recommended_next` 和 `recommended_next_plan`。
- final_report 的 `coverage_status` 不是直接由 evaluator prompt 生成，而是根据最终 score、`dimension_status` 和阈值等后端状态投影出来。
- 现有代码中已增加 `evaluation_consistency.py`，包含：
  - `normalize_evaluation_consistency(...)`
  - `sync_dimension_status(...)`
- evaluator 节点和 verification 节点都会调用一致性归一化逻辑。

### 推断

- 原问题不是单纯 UI bug，而是后端状态语义没有统一边界：`score`、`passed`、coverage、dimension status、verification override 分别在不同节点被写入或消费。
- prompt 可以要求 evaluator 保持一致，但不能作为唯一防线；LLM 仍可能输出“高分 + passed=false”或“高分 + missing coverage”的组合。
- final_report 显示的“覆盖不足”并不一定意味着低分，它表达的是结论可靠性/证据覆盖状态；但如果上游 `passed` 和 `dimension_status` 不一致，UI 会显得更矛盾。

### 未确认假设

- 真实完整面试中仍可能出现“分数高但 UI 文案让用户以为低分”的体验问题，这需要结合报告页展示文案继续观察。
- 当前归一化使用 acceptance/rubric 的显式信号，而不是 contract 文本逐项匹配；这降低了误判，但也意味着如果 evaluator 没有填好这些结构化信号，归一化能力会受限。

## 期望行为

理想情况下：

- `score < quality_threshold` 时，不允许 `passed=true`。
- acceptance check 有 `no`，或 rubric coverage 有 `missing` 时，不允许 `passed=true`，即使分数很高。
- `score=10` 但存在 `no/missing` 时，不悄悄改分，也不强行通过，而是保留分数、修正 `passed=false`，并写入一致性 warning。
- `score >= threshold` 且 checks 全为 `yes/partial`、coverage 无 `missing` 时，如果 evaluator 给了 `passed=false`，后端可以修正为 `passed=true`。
- verifier 高置信 `partial/fail` 应优先于 evaluator 高分，强制进入 refine。
- verifier 低置信 `partial/fail` 不应直接推翻 evaluator，只进入 `soft_warnings`，供下一轮追问使用。
- final_report 看到的应是 post-verification、post-normalization 的最终状态。

## 根因判断

直接原因：

- evaluator 输出的 `score` 与 `passed` 可能不一致。
- evaluator 输出的 `passed` 与 acceptance/rubric 覆盖信号可能不一致。
- verifier 节点可能在 evaluator 之后推翻结论，但如果不同步 `dimension_status`，final_report 会看到旧状态。

深层原因：

- 评分链路有多个写入者和消费者：evaluator 写分数与通过状态，verification 可能修正通过状态，router/reward/final_report 又依赖这些字段。
- 原先缺少一个明确的“最终 evaluation 语义归一化”边界，导致每个节点都可能基于局部理解处理状态。
- 将一致性完全交给 prompt 不可靠，因为 LLM 可能在复杂 rubric、部分覆盖、verifier 反馈下输出自相矛盾的结构化字段。

触发条件：

- evaluator 给出高分，但 `acceptance_check_results` 中仍存在 `no`。
- evaluator 给出高分，但 `rubric_coverage` 中仍存在 `missing`。
- evaluator 高分通过后，verifier 高置信认为回答只有 `partial/fail`。
- final_report 用 `dimension_status` 投影 `coverage_status`，而 `dimension_status` 没有跟最终 evaluation 同步。

## 调试过程

1. 先从报告页现象拆开两个概念：分数高不等于证据覆盖完整，`coverage_status` 表达的是结论可靠性而不是能力分数本身。
2. 追踪字段来源：evaluator 产出 `score/passed/coverage`，verification 在 evaluator 后可能修改 verdict，final_report 读取 `dimension_status` 生成报告展示。
3. 识别简单规则“10 分必过”的风险：如果 `score=10` 同时伴随 required evidence missing，强行通过会掩盖 evaluator 自己给出的证据缺口。
4. 形成更稳的归一化策略：既看 score，也看 acceptance checks / rubric coverage，并允许 verifier 高置信推翻。
5. 最终将逻辑收敛为函数级改造，而不是新增 LangGraph 节点，减少额外状态同步点。

## 解决方式

已完成的修复包括：

- 新增 `evaluation_consistency.py`，集中提供：
  - `normalize_evaluation_consistency(evaluation, contract, quality_threshold, verification=None, ...)`
  - `sync_dimension_status(dimension_status, dimension, evaluation)`
- 归一化规则：
  - fallback evaluator 不参与归一化，避免系统兜底结果污染评分状态。
  - `score < quality_threshold` 强制 `passed=false`，并设置 `recommended_next="refine"`。
  - acceptance check 有 `no` 或 rubric coverage 有 `missing` 时，强制 `passed=false`。
  - 高分且存在 hard gap 时，保留 score，但追加 `consistency_warnings`。
  - `score >= threshold` 且覆盖信号完整或部分完整时，可将 `passed=false` 修正为 `passed=true`。
  - verifier 高置信 `partial/fail` 优先级最高，强制 `passed=false`、`recommended_next="refine"`、`recommended_next_plan="deep_probe"`。
  - verifier 低置信 `partial/fail` 不推翻，只追加 `soft_warnings` 并标记 `verifier_abstained=true`。
- evaluator 节点：
  - evaluator 返回后先做一致性归一化，再写入分数、维度状态和 QA history。
- verification 节点：
  - `_apply_verification` 后再次调用一致性归一化。
  - 同步 `dimension_status`，确保 final_report 看到 post-verification 状态。
- final_report：
  - `coverage_status` 逻辑保持不变，但输入状态更一致。

## 验证方式

测试覆盖包括：

- `score=10 + all yes + passed=false` 会修正为 `passed=true`。
- `score=10 + acceptance no/missing + passed=true` 会修正为 `passed=false`，并写入 `consistency_warnings`。
- `score=9 + yes/partial + passed=false` 会修正为 `passed=true`。
- `score=6.5 + passed=true` 会修正为 `passed=false`。
- verifier 高置信 `partial/fail` 覆盖 evaluator 高分，保持 `passed=false`。
- verifier 低置信 `partial/fail` 不推翻，只追加 `soft_warnings`。
- `sync_dimension_status` 使用最终 evaluation 同步维度状态。
- fallback evaluator 不降级已 passed 维度。

## 可复用教训

- LLM 输出的结构化字段不能默认自洽，尤其是 `score`、`passed`、coverage、recommended next 这类会驱动状态机的字段。
- “高分必过”是危险捷径；更合理的是“高分 + 证据完整 + verifier 未高置信推翻”才可通过。
- verifier 的角色不是重新打分，而是提供高置信推翻或低置信提醒；这两种路径必须区分，否则面试流程会抖动。
- 状态同步应发生在后端确定性边界，而不是依赖 final_report 或 UI 临时解释。
- `coverage_status` 应只表达证据覆盖/结论可靠性，不应偷偷改变 score；否则用户会更难理解总分和维度分。
- 函数级归一化比新增图节点更轻，适合这种“跨节点字段一致性”的修复。

## 未解问题

- 是否需要在报告 UI 中解释“覆盖不足但分数仍计入总分”的语义，仍可后续优化。
- 当前第一版没有自动 cap 分数；也就是说 `score=10 + missing evidence` 会保留 10 分但不通过。长期是否要引入分数上限，需要更多样本判断。
- `contract` 参数目前主要保留给未来更精确的 must-cover 匹配；当前实现只依赖 evaluator 明确产出的 acceptance/rubric 信号。
- 真实完整面试里是否仍会出现用户难以理解的 badge 文案，需要继续观察。
