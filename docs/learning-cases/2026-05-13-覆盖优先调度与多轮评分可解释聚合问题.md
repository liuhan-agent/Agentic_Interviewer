# 覆盖优先调度与多轮评分可解释聚合问题

> 日期：2026-05-13
> 状态：draft
> 标签：ai-interviewer, logic, boundary, debugging

## 一句话结论

这次问题的核心教训是：面试调度必须先保证维度覆盖，再允许局部深挖；多轮评分也必须显式暴露采用分的来源，否则报告会同时出现“未评分过多”和“分数黑盒”的体验问题。

## 背景

当时在改造 AI 面试官的面试报告评分语义。前一轮已经把“未评分/跳过/评估失败”和“真实 0 分”区分开，并让总分只统计有效 evaluator 评分。随后用户发现最近一场面试里，报告页仍然出现很多“未评分”，而“复盘训练计划”的内容也因此变少。

这次复盘聚焦两个相关问题：

- 调度层：为什么已通过或已评分的维度继续占用普通轮次，导致其它维度没有被问到、没有有效评分。
- 评分层：为什么允许同一维度多轮深挖后，报告主分缺少可解释的最近分、最高分、均值、采用分。

## 现象

### 事实

- 用户截图中，`系统设计` 已通过并有 `9.0 / 10`。
- `技术深度` 有 `8.7 / 10`，但显示“覆盖不足”。
- `代码质量`、`项目经验`、`问题解决` 显示“未评分”。
- 用户反馈：“感觉让复盘训练计划的内容都变少了”。
- 针对具体会话 `sess-20260513-123825-71291c` 的排查结果显示：
  - `scored_dimension_count=2`
  - `excluded_dimension_count=3`
  - evaluator trace 是正常调用，不是 evaluator LLM 大面积失败。
  - 该场面试中 `technical_depth` 被问了 5 轮，`system_design` 被问了 3 轮。
  - `coding_quality`、`project_experience`、`problem_solving` 没有获得有效 evaluator 评分。
- 改造前，维度分数主要通过 `scores_per_dim[dimension]` 保存一个合成分，缺少多轮评分统计说明。

### 推断

- “未评分过多”的主因不是 evaluator LLM 评分失败，而是 director 维度调度没有优先覆盖未评分维度。
- 训练计划内容变少，是后端已改成只用真实 scored evaluator 信号生成能力训练依据；当维度没有有效评分时，系统不会再把它伪造成能力弱项。
- `technical_depth` 允许多轮本身是合理的，但应在所有配置维度至少拿到有效评分之后再深挖。

### 未确认假设

- 新调度逻辑在完整真实面试中是否能稳定让所有配置维度至少获得一次有效评分，仍需要端到端跑新会话确认。
- Coach LLM 生成训练计划失败后进入 fallback 的具体原因尚未完全定位；本次只确认它不是这批“未评分”的主因。

## 期望行为

理想行为应分两层处理：

- 覆盖优先：只要还有未有效评分维度，已通过维度不应继续占用普通轮次；当前维度如果尚未产生有效评分，则允许继续追问以拿到首个评分。
- 深挖可解释：所有维度都有有效评分后，可以允许 `technical_depth` 等维度多轮 deep probe，但报告需要说明多轮分数如何聚合，例如最近分、最高分、均值和最终采用分。

## 根因判断

直接原因：

- `director_sample_node` 原来在 bandit 抽样前没有“未评分维度覆盖优先”的硬约束。
- 当前维度即使已经 `passed`，只要 bandit 继续选择当前维度相关动作，普通轮次仍可能继续停留在该维度。
- fallback/skipped/无分数这些“未有效评分”的 turn 没有被统一作为覆盖判断边界来处理。

深层原因：

- 系统把“维度覆盖”和“维度深挖”混在同一个调度过程里，缺少一条清晰的工程规则：先覆盖，再深挖。
- 多轮评分聚合只落到一个主分数，报告无法解释这个主分数是最近表现、最好表现、平均表现，还是历史加权结果。
- prompt 不能可靠承担调度和最终分聚合职责；这些属于后端状态机和聚合函数的边界。

触发条件：

- `technical_depth` 或 `system_design` 这类维度容易持续产出高质量追问，bandit 也更容易继续选择这些路径。
- 面试轮次有限，一旦已评分维度重复占用普通轮次，未评分维度就没有机会进入 evaluator。

## 调试过程

1. 先从用户截图确认问题不是单纯 UI 标签错误：确实存在多个维度没有分数，训练计划素材也随之减少。
2. 再检查具体会话的评分与 trace，确认 evaluator LLM 没有大面积失败；问题更像调度覆盖不足。
3. 定位到 director 选择逻辑：已 `passed` 的当前维度没有被覆盖守卫强制切走。
4. 进一步确认多轮评分的报告问题：同维度多轮是合理能力，但需要把聚合过程从单值黑盒改成显式 breakdown。
5. 最终把修复拆成两个独立层：覆盖优先调度和多轮评分可解释聚合。

## 解决方式

已完成的修复包括：

- 新增 `score_aggregation.py`：
  - 判断真实有效评分维度。
  - fallback、skipped、无数字分数不算覆盖。
  - 真实 `0.0` 仍算有效评分。
  - 维护 `latest_score`、`best_score`、`average_score`、`adopted_score`、`scored_turn_count`。
- 改造 `director_sample_node`：
  - bandit 抽样前先执行覆盖优先守卫。
  - 当前维度已 `passed` 且还有未评分维度时，强制切到未评分维度。
  - 当前维度已有评分但未通过，且剩余轮次不足以覆盖所有未评分维度时，强制切到未评分维度。
  - 当前维度还没有有效评分时，不提前切走。
  - 所有维度都有有效评分后，恢复 bandit 正常选择，允许继续深挖。
- 改造 evaluator：
  - 正常 evaluator score 更新 `score_breakdowns`。
  - `scores_per_dim[dimension]` 继续写入 `adopted_score`，保持兼容。
  - fallback evaluator 不更新 breakdown，也不算覆盖。
- 改造 final_report：
  - 优先使用 `score_breakdowns[*].adopted_score` 作为维度主分。
  - 旧 state 没有 breakdown 时，可以从 `qa_history` 重建。
  - 总分仍只平均有效 scored 维度主分。
- 改造前端报告：
  - 主视图仍显示一个维度主分。
  - 多轮评分时补充轻量说明：共评估几轮、最近分、最高分、均值、综合分。
- 改造 evaluator prompt：
  - 明确单轮 evaluator 只评价当前回答，不自行综合历史；最终聚合由后端处理。

新增或更新的关键测试覆盖：

- 已通过维度后仍有未评分维度时，director 强制切换。

## 可复用教训

- 调度策略不能只依赖 prompt 或 bandit；涉及覆盖率、公平性、轮次预算的约束应放在代码守卫里。
- “未评分”不是报告 UI 小问题，它通常反映上游状态机没有让维度进入可评价路径。
- fallback/skipped/无分数必须在覆盖判断、总分统计、训练计划生成中保持同一语义，否则会出现报告、训练计划、调度三方不一致。
- 允许多轮深挖前，必须定义分数采用策略；否则用户会合理质疑“为什么这个维度最后是这个分”。
- 单轮 evaluator 只应评价当前回答，历史聚合应由后端确定性代码完成。
- 当训练计划内容突然变少时，优先检查有效 scored evaluator 信号数量，而不是先怀疑 Coach LLM 内容质量。

## 未解问题

- 需要用新逻辑完整跑一场真实面试，确认配置维度能按预期获得至少一次有效评分。
- Coach LLM 成功调用但训练计划落入 fallback 的具体 parse/shape 失败原因仍需单独排查。
- 多轮 `adopted_score = 0.7 * previous + 0.3 * latest` 是否是长期最佳策略，还需要更多真实面试样本验证。
- 报告是否需要在后续展示更详细的“为什么这轮继续深挖/为什么切换维度”，尚未决定。
