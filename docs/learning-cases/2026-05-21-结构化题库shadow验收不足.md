# 结构化题库 Shadow 验收不足

> 日期：2026-05-21
> 状态：draft
> 标签：ai-interviewer, boundary, debugging, shadow-rollout

## 一句话结论

结构化题库 shadow mode 不能只验收“selector 写了 `question_items` / usage”；它的真实目的，是证明结构化题库在真实岗位、真实 `current_dimension`、真实 `job_level` 下能稳定服务主链路，并为后续 primary 接管提供证据。

## 背景

结构化题库最初以 `structured_shadow` 进入 AI 面试官主链路。设计目标是低风险：selector 选择 top candidates，写入 `selection_artifacts.question_items` 和 `QuestionUsage`，但不改变现有 Generator/RAG 出题行为。

这个方向本身是合理的。但在后续真实面试验证中，用户发现“结构化题库增强”并没有稳定体现到实际出题链路。进一步复盘后发现，早期验收更像模块验收：import 能导入、selector 能返回、workflow 能写 artifact、usage 能记录；但缺少真实主链路验收：同一个真实岗位 setup 下，director 实际选出的每个 `current_dimension` 是否都有结构化候选，是否和 role/job_level 对齐，是否能被 Admin/replay 解释。

## 现象

### 事实

- 当前 workflow 中存在三种模式：
  - `vector`：保留旧 RAG 出题路径，`question_items=[]`。
  - `structured_shadow`：写入结构化候选与 usage，但不改变 Generator prompt。
  - `structured_primary`：seed hit 且 role allowlist 命中时注入 `question_seed_block`，RAG 降为 shadow/fallback。
- 单元测试覆盖了若干关键行为：
  - `structured_shadow` 记录 `question_items` 且不改变 prompt。
  - `structured_primary` seed hit 注入结构化题目。
  - seed miss 或 uncovered role fallback 到 RAG。
  - reward 只回填真正 injected 的 rank1 usage。
- 用户真实跑过面试 session 并要求验证效果，线索包括：
  - `sess-20260516-145802-5fd1e4`
  - `sess-20260516-164341-53c84a`
- 真实验证暴露出结构化题库与主链路维度、job_level、岗位覆盖之间仍有脱节，需要后续 alignment fix / density fix。

### 推断

- 早期 shadow 验收把“数据被写出”误当成“真实链路可用”。但 shadow 的价值不在于写数据本身，而在于这些数据能支持回答：如果现在切 primary，哪些岗位/维度安全，哪些会 fallback，为什么。
- 测试里的 selector candidate 往往是人为构造的 happy path，没有覆盖真实 `interview_directions.json`、真实 job template、真实 director 维度路由和真实题库覆盖矩阵的组合。
- 如果 `question_items` 为空只被当作“允许的 shadow 结果”，而不是触发覆盖缺口分析，那么 shadow mode 就不会真正帮助产品判断出题效果是否变好。

### 未确认假设

- 本文没有重新查询上述真实 session 的逐 turn artifact；具体哪一轮、哪个 `current_dimension` 下为空，需要后续查 DB 或 replay。
- 早期 P0/P1.1 的所有测试缺口没有逐 commit 复核；本文只依据会话上下文和当前测试结构总结。
- “出题效果是否明显变好”仍缺少人工 pairwise review 或用户评价样本；本文只讨论验收方法不足，不断言效果一定没有提升。

## 期望行为

Shadow mode 的验收应该能回答三组问题：

1. 覆盖是否真实：
   - 目标岗位的主链路维度是否都有 active seed？
   - 目标 job_level 是否都能命中？
   - role/direction tags 是否命中，而不是靠 generic fallback 兜底？

2. 行为是否安全：
   - `structured_shadow` 是否完全不改变 Generator prompt？
   - `structured_primary` seed hit 时是否注入结构化题目？
   - seed miss / uncovered role 是否保留 RAG fallback？
   - reward 是否只回填真正 injected 的 usage？

3. 证据是否可观察：
   - Admin/replay 是否能看到 top candidates、match reasons、injected 状态？
   - 空命中是否能解释为内容缺口、维度错位、job_level 不覆盖、role 未覆盖或 selector error？
   - 是否能用真实 session artifact 判断“切 primary 是否安全”？

## 根因判断

直接原因：早期 shadow 验收以“是否写出 artifact/usage”为主，没有把“真实岗位主链路下的覆盖率和命中质量”作为完成条件。

深层原因：

- Shadow mode 被当成了低风险实现策略，而不是证据生产策略。
- P0/P1.1 分阶段推进时，为了不影响 Generator/RAG prompt，验收重点自然落在“不破坏现有行为”。但“不破坏”不等于“有效”。
- 当出题骨架从 RAG 迁移到结构化题库时，题库覆盖缺口会直接影响主链路；shadow 阶段如果不主动暴露缺口，primary 接管时才会暴露。
- Admin/replay 虽有可观察数据，但缺少明确验收判据，例如“目标岗位 × 主链路维度 × job_level 的 non-empty rate”。

## 调试过程

1. P0 shadow 闭环完成后，系统能在 structured shadow 下写入 `question_items` 和 usage，且保持 prompt 行为稳定。
2. P1.1 增强了 fit profile、role tags、reranker shadow、review 等观察能力。
3. 用户真实跑面试 session 后要求验证“结构化题库增强是否起作用”。
4. 分析过程中发现，部分轮次 structured candidates 与真实 `current_dimension` 不匹配或覆盖不足。
5. 问题进一步收敛为两类：
   - 维度对齐问题：题库维度没有服从主链路维度。
   - shadow 验收问题：之前没有用真实链路验收覆盖矩阵。
6. 后续通过 alignment fix、density fix、business hardening、RAG Role Demotion 等批次逐步补齐。

## 解决方式

已采取的改进方向：

- 补 Java 后端 alignment：题库维度对齐 `java_backend.dimension_catalog`。
- 补其它技术岗位 alignment：各岗位 active seed 只能使用主链路已有维度。
- 补 density：避免每个维度只有极少 seed/variant，降低 top3 质量不稳定。
- 增加 lint：
  - active seed 使用岗位目录外维度时失败。
  - 缺主链路维度覆盖时失败。
  - job_level 覆盖不足时失败。
  - variant 密度不足时失败。
- 将 `structured_primary` 变成默认主链路模式，但保留 `structured_shadow` / `vector` 回滚开关。

仍建议补充的验收方式：

- 增加一个“真实链路覆盖验收”脚本或测试矩阵：
  - 输入：direction / role / job_level。
  - 遍历该岗位 `dimension_catalog`。
  - 对每个 dimension 调 selector，断言 candidates 非空或输出明确缺口。
  - 统计 top3 seed 多样性、role 命中、job_level 命中、fallback 原因。
- Admin 增加 coverage matrix：
  - role × dimension × job_level。
  - active seed 数。
  - active variant 数。
  - 最近真实 session 命中率。
  - shadow empty 原因。

## 验证方式

现有验证已经覆盖的部分：

- `vector` 模式保持 `question_items=[]`。
- `structured_shadow` 写入 question items/usage，但不改变 prompt。
- `structured_primary` seed hit 注入结构化题目。
- seed miss / uncovered role fallback 到 RAG。
- reward 只回填 injected rank1。
- Admin question bank 和 usage 能展示结构化题库状态。

仍需要补强的验证：

- 用真实 job template / interview direction / job level 跑覆盖矩阵，而不是只构造 mock candidate。
- 对真实 session 的 `selection_artifacts.question_items` 做统计：
  - empty rate。
  - top1 injected rate。
  - role fallback rate。
  - dimension mismatch rate。
  - job_level miss rate。
- 将“shadow 数据为空”从普通结果提升为需要解释的诊断信号。

## 可复用教训

- Shadow rollout 的核心不是“低风险写数据”，而是“生产切换证据”。
- 对主链路能力来说，artifact 存在不等于能力可用；必须验证 artifact 是否覆盖真实路由。
- “不改变 prompt”只能证明安全性，不能证明效果。shadow 验收必须同时有安全性和有效性指标。
- 当用户问“到底有没有让出题变好”时，不能只回答实现了哪些机制；必须拿真实 session、候选命中、人工 review 或对照数据说话。
- 如果 shadow 阶段没有明确成功/失败判据，后续 primary 接管就会变成凭感觉推进。
- 空命中不是噪声。它往往是内容覆盖、维度对齐、岗位识别或 job_level 策略的入口信号。

## 未解决问题

- 是否需要把真实链路覆盖矩阵做成 CI 中的 bundled data test？
- 是否需要对每个新岗位包要求至少一条真实或模拟 session replay 验收？
- Admin 是否应该展示 shadow empty reason，而不是只展示最近 usage 列表？
- Pairwise review 的样本量达到多少后，才允许某岗位从 shadow-only 进入 primary allowlist？
- “出题效果变好”的人工评价标准是否需要固化，例如候选人贴合度、追问空间、泛题率、维度覆盖、fallback 率？
