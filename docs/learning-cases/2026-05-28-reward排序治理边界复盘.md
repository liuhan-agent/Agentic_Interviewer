# StrategyMemory / Question / Skill reward 排序治理边界复盘

> 日期：2026-05-28
> 状态：draft
> 标签：ai-interviewer, reward-ranking, governance, observability, boundary

## 一句话结论

让 reward 真正改变返回顺序之前，必须先把“统计数据来源、候选池范围、排序口径、线上生效开关”四个轴拆清楚；否则 `reward_shadow` 很容易被误解成另一套选择器、某一轮真实命中，或已经上线的 live reward 排序。

## 背景

这次讨论发生在 AI Interviewer 的策略记忆、结构化题库和 Skill Playbook 三类资产治理改造期间。

目标是让系统逐步从纯 metadata 排序，演进到“reward 可观测、可灰度、可回退”的排序治理模型。最初从 `StrategyMemory` 的 reward readiness 和 gated ranking 开始，随后扩展到 `QuestionUsage` 的 reward shadow，再到 `SkillUsage` 的 reward shadow / rollout。

用户关注的核心问题是：reward 到底什么时候、以什么粒度、基于哪些样本，才应该改变实际返回顺序。

## 现象

### 事实

- `StrategyMemory`、`Question`、`Skill` 三类资产最终都需要区分 metadata baseline 和 reward-influenced ranking。
- `reward_shadow` 使用真实历史 reward / usage 统计做模拟排序，但默认不改变线上返回顺序。
- `reward` live 模式只有在显式 override 且 gate 通过时，才允许改变真实返回顺序。
- `Question` 里还存在 `structured_shadow / structured_primary`，它们是结构化题库 selector rollout 状态，不等于 reward 排序模式。
- Admin UI 曾同时展示 `structured_primary / structured_shadow`、`metadata_top / reward_top`、`context readiness`、`seed reward` 等概念，导致用户多次追问这些 Top K 到底是什么、是否等于某一轮 `ask_question` 实际命中。
- 用户指出“metadata_top vs reward_top 就可以表示两种模式”，并要求先对齐 `StrategyMemory` 的 shadow / primary 做法，再统一题库口径。

### 推断

- 主要问题不是单个后端排序 bug，而是治理模型的概念层没有先统一，导致 UI、API 字段和对话解释不断补洞。
- “完整 Top K”这个说法过于强，会让人误以为它是某一轮完整动态检索结果；实际上 Admin 里的 Top K 更像治理模拟视图。
- `Question` 的上下文比 `StrategyMemory` 和 `Skill` 更复杂，因为真实 `ask_question` 命中还会受 resume anchor、candidate project fit、skills、qa_history、difficulty、probe intent、role pack fallback、seed/variant gate 等动态因素影响。

### 未确认假设

- 当前 context readiness 的 `context_key` 是否足够支撑后续 live reward 排序，还需要更多真实面试数据验证。
- Seed 级 override 与 context 级 override 的优先级是否长期保持当前设计，仍可能随题库选择器演进调整。
- Skill 的 reward 排序是否应该永远只做 context 级 override，暂未证明需要更细粒度。

## 期望行为

三类资产都应遵循同一套高层治理语言：

- 一套候选池：先明确这次模拟或排序覆盖的是哪些候选。
- 两种排序口径：metadata baseline 与 reward shadow / reward ranking。
- 一个 live 开关：只有 Admin 显式开启并通过 gate，reward 才能影响真实返回顺序。
- 明确 scope：global、context、seed、variant、skill card 等 scope 不能混用。
- 明确 shadow：shadow 是真实 reward 数据的离线/旁路模拟，不是假数据，也不是线上排序。
- 明确 fallback：样本不足、候选不足、overrule 过高或单候选无排序意义时，应自动退回 metadata，并写明 gate reason。

## 根因判断

### 直接原因

Admin UI 同时暴露了太多后端字段，但没有把字段归属到稳定的治理层级：

- `selector_rollout_mode` 是题库选择器状态。
- `reward_ranking_mode` 是 reward 排序状态。
- `metadata_top_*` 是 metadata baseline。
- `reward_top_*` 是 reward shadow simulation。
- `context readiness` 是按上下文聚合的灰度候选。
- `seed readiness` 是 Seed 内 Variant 排序灰度。

这些字段都是真实的，但如果不先说明 scope，就会看起来像几套互相矛盾的模式。

### 深层原因

三类资产虽然都叫“reward 排序”，但候选池天然不同：

- `StrategyMemory`：策略条目数量较小，适合较早做 context-level gated live reward。
- `Question`：真实命中依赖结构化题库 selector 和候选人动态上下文，Admin 全局/上下文 Top K 不应被描述成单轮实际命中。
- `Skill`：Skill card 会影响出题和 evaluator hints，较敏感，适合先做观测和 context-level rollout，不宜默认 live 排序。

如果不先建立统一模型，就会在每个模块里重新讨论 shadow、primary、Top K、override、gate 的含义。

### 触发条件

用户看到 Admin 面板里的 `structured_primary`、`reward_shadow`、`metadata Top K`、`reward shadow Top K`、`context readiness` 后，合理地追问“这些是不是同一套模式”“为什么 Top K 不一样”“是不是某一轮 ask_question 检索到的题库”。这暴露出 UI 文案没有先把治理视图和运行时视图区分开。

## 调试过程

1. 先从 `StrategyMemory` 出发，讨论 reward 是否应该真正改变返回顺序。
2. 决定采用 metadata 主排序、reward 有门槛加分、`__global__` 仅弱 prior、样本不足自动 fallback 的策略。
3. 扩展到 `QuestionUsage` 时，最初把 `structured_shadow / structured_primary` 与 `metadata_top / reward_top` 讨论混在一起。
4. 用户指出应先看 `StrategyMemory` 的 shadow / primary 模型，随后将题库改成一套 usage stats、两种排序口径。
5. 继续扩展到 `Question` context + seed 两级 override，用 context 控制跨 Seed 排序，用 seed 控制 Seed 内 Variant 排序。
6. 扩展到 `Skill` 时，沿用“一套候选池 + 两种排序口径 + 一个 live 开关”，但只做 context 级 override。
7. 最后对 Admin UI 文案做分层：全局题库排序模拟、Context 级灰度候选、Seed 内 Variant 灰度，避免把治理模拟说成单轮命中。

## 解决方式

已采取的方向：

- `StrategyMemory`：实现 gated reward ranking，只有上下文样本足够且 gate 通过才可 live reward；否则 metadata fallback，并写入 `ranking_reason`。
- `Question`：统一 reward shadow 口径，不再按 `structured_shadow / structured_primary` 分成两张 readiness；新增 context + seed 两级 override。
- `Skill`：新增 SkillUsage / SkillUsageStats / SkillRewardRollout，只做 context 级 reward 排序灰度，默认 `reward_shadow`。
- Admin UI：将“Reward Shadow”拆成治理语义更明确的区域，强调 Top K 是治理模拟，不是某一轮 `ask_question` 的实际候选命中。

这次没有把复盘结论写入运行时 prompt、workflow guard 或自动学习规则。

## 可复用教训

- 先定义概念轴，再做 UI 和 API 字段。尤其是 reward、shadow、primary、readiness、override 这类词，不能让 UI 自己解释。
- `reward_shadow` 应固定解释为：真实历史 reward 数据的旁路排序模拟，不改变线上返回顺序。
- `selector rollout` 和 `reward ranking rollout` 是两条轴，不能混称。
- Top K 必须标注 scope：global、context、seed、single-turn candidate，否则很容易被误认为同一个东西。
- Admin 治理台和 Trace Explorer 分工要清楚：
  - Admin 治理台看跨样本统计、灰度资格、排序模拟。
  - Trace Explorer 看某一轮真实命中、注入、路由、评分依据。
- 当 reward 排序会影响出题内容时，默认应先 shadow，再 readiness，再显式 override，最后才 live。
- gate reason 不是调试附属品，而是 reward 排序治理的核心输出。

## 未解决问题

- Question live reward 排序的 context 粒度是否足够，仍需更多真实使用样本检验。
- Seed override 是否应该支持更细的 role/job_level/dimension 作用域，暂未决定。
- Skill 是否需要类似 seed/variant 的更细粒度结构，目前按 context 级治理处理。
- Admin 面板未来可能需要提供“从某个真实 Trace 跳转到对应 context readiness”的连接，帮助用户把单轮命中和治理模拟关联起来。
