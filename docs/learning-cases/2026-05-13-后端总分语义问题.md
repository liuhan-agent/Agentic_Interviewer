# 后端总分语义问题

> 日期：2026-05-13
> 状态：draft
> 标签：ai-interviewer, logic, boundary, debugging

## 一句话结论

后端总分语义的核心教训是：`0.0`、`null`、跳过、LLM fallback、未覆盖证据必须显式建模，不能靠“排除 <= 0 分”或“默认 0 分”这种数字技巧表达状态。

## 背景

当时正在改造 AI 面试官的“面试报告”页面和后端评分语义。用户先注意到报告开头 `9.3 / 10` 却显示“接近达标”，随后又发现“评分维度”里有多个维度显示 `0.0 / 10`，但这些维度没有评价理由、弱项或有效证据，看起来不像真实低分，更像“未有效评分”。

这引出了一个更底层的问题：后端总分到底应该怎么计算？如果维度列表中有 `10.0`、`9.0`、`9.0` 和多个 `0.0`，但总分仍是 `9.3`，说明总分不是简单平均所有显示分数；而如果这些 `0.0` 其实是未评分占位，就不应该在 UI 上显示成真实 0 分。

## 现象

### 事实

- 报告页出现过总分 `9.3 / 10`，但状态显示“接近达标”的不协调体验。
- “评分维度”里有维度显示 `0.0 / 10`，同时状态是 `pending` 或“待提升/未评分”。
- 用户追问这些 `0.0` 是不是 LLM 调用出错，还是 evaluator 真的给了低分/0 分。
- 从语义上判断：
  - 如果 evaluator 真给了 `0.0`，应该有该维度的评价理由、弱项或正常 evaluator 记录。
  - 如果只有 pending、fallback、空白理由，更像未有效评分，不应该显示成 `0.0 / 10`。
- 后端已改造为：
  - `overall_score` 支持 `number | null`。
  - `dimension_scores[*].score` 支持 `number | null`。
  - 维度增加 `score_status`、`excluded_from_overall`、`exclusion_reason`、`coverage_status`。
  - `score_summary` 统计 scored/excluded/total 维度数量。

### 推断

- 原实现把“未评分占位”和“真实 0 分”都压进了 `0.0`，导致 UI 和总分语义分裂。
- 总分原来通过排除 `<= 0` 的方式规避未评分占位，但这会错误排除真实 `0.0`。
- 前端看到 `0.0` 时无法判断它是“真实低分”还是“未评分”，只能展示成看似严厉的 `0.0 / 10`。
- 训练计划如果直接消费这些伪 0 分，也会把“未评分/跳过/评估失败”误当成能力弱项。

### 未确认假设

- 更早期持久化报告中可能存在多种 legacy shape；目前的兼容逻辑能覆盖主要场景，但仍需要抽样历史数据验证。
- 用户看到的某些 `pending + 0.0` 可能来自旧报告、旧 state 或迁移前生成的会话；具体单场会话需要结合存档数据确认。

## 期望行为

理想行为应明确区分这些状态：

- 真实 evaluator 给出 `0.0`：
  - `score=0.0`
  - `score_status="scored"`
  - `excluded_from_overall=false`
  - 计入总分
  - UI 显示 `0.0 / 10`
- 没有被问到或没有有效 turn：
  - `score=null`
  - `score_status="not_evaluated"`
  - `excluded_from_overall=true`
  - 不计入总分
  - UI 显示“未评分”
- 用户跳过：
  - `score=null`
  - `score_status="skipped"`
  - `excluded_from_overall=true`
  - 不计入总分
  - UI 显示“已跳过”
- evaluator LLM fallback：
  - `score=null`
  - `score_status="evaluator_unavailable"`
  - `excluded_from_overall=true`
  - 不计入总分
  - UI 显示“评估失败”或“评分暂时不可用”
- 证据不足/覆盖不足：
  - 只影响 `coverage_status`
  - 不改变真实 scored 分数是否计入总分

## 根因判断

直接原因：

- `scores_per_dim` 的未评分初始值使用 `0.0`，与真实 evaluator 打出的 `0.0` 冲突。
- `overall_score` 通过排除 `<= 0` 的分数来计算平均值，隐式假设 `0.0` 不是有效评分。
- final_report 的维度分数 projection 没有明确告诉前端某个维度是否真实评分。

深层原因：

- 分数字段被拿来同时表达两个不同概念：
  - 数值表现：候选人在某维度得了多少分。
  - 评分状态：这个维度是否被有效评估。
- 后端数据 contract 没有显式建模“未评分/跳过/fallback/真实 0 分”的状态边界。
- UI 被迫从数字推断状态，导致 `0.0` 被展示成真实低分。
- 训练计划、总分、报告展示都依赖这套语义；一旦底层字段含混，多个模块会同时被影响。

触发条件：

- 某些维度没有进入 evaluator 或没有正常 evaluator 输出。
- 用户跳过题目。
- evaluator LLM 失败后走 fallback。
- 旧报告中遗留了 `score: 0.0`，但没有正常 evaluator evidence。

## 调试过程

1. 先从用户截图确认：多个维度显示 `0.0 / 10`，但报告总分明显不是所有维度简单平均。
2. 讨论并区分两类 0 分：
   - evaluator 真实打出的 `0.0`。
   - 未评分占位产生的 `0.0`。
3. 确认真实 `0.0` 的判定标准：该维度存在正常 evaluator 记录，且 score 为数字 `0.0`。
4. 明确跳过、fallback、未评估都不应伪造成能力弱项，也不应计入总分。
5. 将问题从“UI 怎么显示 0 分”上移到“后端评分 contract 如何表达状态”。
6. 最终确定改造方向：总分只统计有效 evaluator 评分，维度输出显式 `score_status` 和排除原因。

## 解决方式

已完成的修复包括：

- 后端状态初始化：
  - `scores_per_dim` 未评分值从 `0.0` 改为 `None`。
  - 类型语义改为 `dict[str, float | None]`。
- evaluator 节点：
  - 正常 evaluator 返回的分数写入 `scores_per_dim`，包括真实 `0.0`。
  - fallback evaluator 不写入分数。
  - 如果维度已有历史有效分数，fallback 不覆盖历史分数。
- final_report：
  - `_overall_score` 只平均 `score_status == "scored"` 的维度。
  - 真实 `0.0` 会计入平均。
  - 无任何有效 scored 维度时，`overall_score=None`。
  - 无有效总分时，`verdict/growth_signal/overall_verdict` 使用 `unknown`；`cancelled` 仍优先返回 `cancelled`。
  - `_build_dimension_scores` 输出明确状态：
    - `score`
    - `score_status`
    - `excluded_from_overall`
    - `exclusion_reason`
    - `coverage_status`
    - `passed`
    - `rationale`
    - `weaknesses`
- 维度状态判断：
  - 有正常 evaluator 数字分数：`score_status="scored"`。
  - 只有 skipped turn：`score_status="skipped"`。
  - 只有 evaluator fallback turn：`score_status="evaluator_unavailable"`。
  - 没有有效 turn：`score_status="not_evaluated"`。
- coverage 语义：
  - `coverage_status` 只描述结论可靠性/证据覆盖情况。
  - `coverage_limited` 不会把分数从总分中剔除。
- 前端类型：
  - `FinalReport.overall_score?: number | null`
  - `RubricScore.score: number | null`
  - 新增 `RubricScoreStatus` 和 `RubricCoverageStatus`。
- 前端展示：
  - `not_evaluated` 显示“未评分”。
  - `skipped` 显示“已跳过”。
  - `evaluator_unavailable` 显示“评估失败/评分暂时不可用”。
  - 只有真实 scored 数字才显示 `x.x / 10`。

## 验证方式

测试覆盖包括：

- `scores_per_dim={"coding_quality": 0.0, "system_design": 10.0}` 且两项都有正常 evaluator 记录时：
  - `overall_score == 5.0`
  - 真实 `0.0` 的 `score_status == "scored"`
  - `excluded_from_overall == false`
- skipped/fallback/not_evaluated 维度：
  - `score is None`
  - 对应 `score_status`
  - 不计入总分
- coverage_limited 维度：
  - `score_status == "scored"`
  - `excluded_from_overall == false`
  - `coverage_status == "coverage_limited"`
  - 分数仍计入总分
- 没有有效评分时：
  - `overall_score is None`
  - `verdict == "unknown"`
  - `growth_signal == "unknown"`
  - `score_summary.scored_dimension_count == 0`
- legacy `score: 0.0` 且无 evaluator evidence：
  - 按未评分处理，不显示假 0 分。

## 可复用教训

- 数值字段不要同时承担“数值”和“状态”两种语义；尤其是 `0` 这种业务上真实有效的值，不能拿来做占位。
- 如果系统存在 LLM fallback，就必须区分“模型没评出来”和“模型评得很低”。
- 总分计算应该基于明确的有效评分集合，而不是用数值大小做隐式过滤。
- 前端不要从 `score` 猜状态；后端应该直接提供 `score_status` 和 `exclusion_reason`。
- 训练计划不应从未评分/跳过/fallback 中制造能力弱项，否则会损害用户信任。
- `coverage_status` 和 `score_status` 是两个不同维度：
  - `score_status` 决定是否计入总分。
  - `coverage_status` 说明证据覆盖/结论可靠性。

## 未解问题

- 需要抽样更多旧持久化报告，确认 legacy shape 都能被新 UI 合理解释。
- 是否需要在报告页更明确说明“总分只统计有效评分维度”，仍可后续优化。
- 对于 `overall_score=null` 的报告，是否需要更专门的 UI 空状态和引导文案。
- 训练计划已避免把非 scored 维度当作能力弱项，但是否要单独生成“下次补评估方向”，仍可继续设计。
