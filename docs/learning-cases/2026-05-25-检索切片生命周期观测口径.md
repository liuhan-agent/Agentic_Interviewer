# 检索切片生命周期观测口径

> 日期：2026-05-25
> 状态：draft
> 标签：ai-interviewer, boundary, debugging

## 一句话结论

完成后清理 `session_anchor_chunks` 是合理生命周期行为，但观测指标如果仍按这张表统计，会把清理误读成未生成数据。

## 背景

在优化后台观测台“评分质量 / RAG 观察”模块时，用户发现“切片数”为 0，同时又认为相关数据应已进入向量库或快照。随后追问这些数据存在向量库，为什么还要看表，以及完成面试后清理 `session_anchor_chunks` 是否合理。

这个问题最初看起来像 UI 表格展示不美观或某个字段没填，但继续追问后发现本质是数据生命周期口径：同一个“候选人资料 RAG”链路里，同时存在运行态 chunk 表、setup snapshot、ask_question trace artifact、向量检索结果和后台 24h 统计。不同数据源的生命周期不同，不能混在一个指标里解释。

## 现象

### 事实

- 面试过程中会产生 session anchor 相关切片，用于本场面试的资料召回。
- 完成后存在清理 `session_anchor_chunks` 的逻辑。
- 清理内存或临时表数据不应影响历史报告、trace、final report 或向量库中的长期资产。
- 观测台如果直接按临时表统计，会在完成后看到切片数为 0。
- `/admin/session-anchors/sessions` 会查询最近窗口内的 `InterviewSession`、`SessionAnchorChunk` 和 `GenerationTrace(node="ask_question")`。
- 后端已经有 `_apply_session_anchor_setup_snapshot()`，可在 chunk 表没有记录时从 `InterviewSession.setup_snapshot` 回填 chunk count、chunker mode 和 embedding model version。
- 单测 `test_admin_session_anchor_sessions_uses_setup_snapshot_after_chunk_cleanup` 覆盖了完成后无 chunk row 但 snapshot 仍能显示 `total_chunks=29` 的场景。
- `delete_session_anchor_data()` 是显式后台删除入口，会删除 chunks/artifacts/cache，并 scrub setup snapshot 与 trace snapshot；这和普通完成后生命周期清理不是同一件事。

### 推断

- “切片数为 0”不一定代表没有切片生成，也可能代表临时生命周期已经结束。
- 24h 观测指标需要使用生命周期更长的数据源，例如 setup snapshot、trace 或单独 materialized stats。
- 只看 `SessionAnchorChunk` 表会偏向“当前仍存在的运行态数据”，不适合解释“过去 24h 已完成 session 是否生成过切片”。
- setup snapshot 是更适合 session 级历史概览的来源，但它只能回答生成状态和切片策略，不能完整替代真实召回 hit 明细。

### 未确认假设

- 当前生产数据中，哪些 session 的 setup snapshot 已完整保留切片策略和召回表现，需要抽样确认。
- 向量库与关系表之间是否存在统一的可追溯 ID，还需要后续 Trace Explorer 改造时继续确认。
- 普通完成链路“清理 session_anchor_chunks”的精确触发点，本次复盘没有重新逐行确认；已确认的是 Admin 显式删除入口和 snapshot 回填逻辑。

## 期望行为

后台观测指标应避免用短生命周期表解释长期历史。对 RAG 观测可区分：

- 运行态切片：当前 session 或当前进程仍在使用的临时切片。
- 历史观测：最近 24h 面试 session 的 setup snapshot、trace、召回记录。
- 资产覆盖：知识库或资料库中长期存在的可检索资产。

推荐的数据源分层：

| 问题 | 合适数据源 | 不合适数据源 |
|---|---|---|
| 这场 session 是否生成过简历/自介切片 | `InterviewSession.setup_snapshot` | 只看 `SessionAnchorChunk` 当前行数 |
| 这场 session 最近是否真正召回命中 | `GenerationTrace` 的 ask_question anchor artifact | setup snapshot |
| 当前运行态还有多少 chunk | `SessionAnchorChunk` | trace 或 snapshot |
| 删除候选人资料后是否 scrub 干净 | `delete_session_anchor_data()` 返回值和 DB 检查 | 普通 session 概览 |
| RAG 对评分分布是否有关联 | evaluator/score trace + anchor hit artifact | chunk count |

## 数据生命周期拆解

```text
创建/准备面试
  -> resume/self_intro vector status 写入 setup_snapshot
  -> session_anchor_chunks 写入运行态切片

出题 ask_question
  -> RAG 检索
  -> generation_trace 中留下 anchor artifact

面试完成或后续清理
  -> 运行态 chunk 可能被清理
  -> setup_snapshot / trace / final report 保留历史解释能力

显式删除 anchor data
  -> 删除 chunks、artifacts、cache
  -> scrub setup_snapshot 和 trace snapshot
```

这个生命周期决定了观测台不能只用一张表解释所有状态。

## 容易误读的指标

### 切片数

合理含义：

- 在 session 级历史表中，表示这场面试曾经记录的简历/自介切片规模。
- 在运行态资产表中，表示当前仍存在的 chunk 行数。

危险误读：

- `0` 就等于没有生成过。
- `0` 就等于 RAG 没工作。
- chunk 数越多，RAG 质量越好。

### 切片策略

合理含义：

- `A`、`SI` 等策略说明切片来自不同源或不同模式。
- 对排查“为什么某类资料没有召回”有帮助。

危险误读：

- 把所有 source_type 和 chunker_mode 平铺成同级标签，看起来像完全并列分类。
- 用策略标签替代真实召回表现。

### 召回表现

合理含义：

- 应看每个 ask_question trace 中是否有 hits、fallback reason、latency、source_type。

危险误读：

- 用 chunk_count 推断 hit_count。
- 用 setup_snapshot 推断每一轮 RAG 是否命中。

## 根因判断

直接原因：观测台中的“切片数”指标混用了运行态临时数据和历史观测需求。

深层原因：RAG 系统有多类数据生命周期：临时 session anchor、向量库资产、setup snapshot、generation trace。指标如果不标注来源和生命周期，就会把“被清理”误读为“未生成”。

触发条件：用户查看已完成 session 的 24h RAG 表格时，临时切片表已被完成链路清理。

更深层的问题是“表存在”被误当成“观测事实的唯一来源”。关系表、向量库、snapshot、trace 都是真实来源，但它们回答的问题不同。后台观测台应该从问题出发选择数据源，而不是从已有表出发拼指标。

## 调试过程

1. 先确认“切片数”并不是用户能直接判断质量的核心指标。
2. 追问数据是否存在向量库和表之间的关系，避免凭猜测解释。
3. 确认完成后清理临时切片是合理设计。
4. 将观测口径调整为优先使用 `setup_snapshot` 等更适合 24h 历史展示的数据。
5. 进一步确认代码中已有 `_apply_session_anchor_setup_snapshot()`，说明系统已经承认 snapshot 是 chunk 清理后的历史来源。
6. 对照单测 `test_admin_session_anchor_sessions_uses_setup_snapshot_after_chunk_cleanup`，确认该边界已有回归保护。
7. 将 UI 表格从“source_type 与 chunker_mode 并列聚合”调整为 session 级记录，降低维护和解释成本。

## 解决方式

本轮采用的方向是：不否定清理逻辑，而是调整观测数据源和 UI 口径。对最近 24h 的 session 级展示，应优先使用能够跨完成状态保留的快照或 trace，而不是依赖完成后会被清理的临时表。

已确认的更合理方向：

- “资料库覆盖”展示长期资产覆盖，不等同于 session 召回表现。
- “最近 24h 召回表现”按 session 展示，而不是只按 source_type / chunker_mode 聚合。
- session 行里展示切片策略、chunk count、召回尝试、命中、p50/p99 latency 等更贴近排查的问题。
- 需要历史解释时优先用 setup snapshot 和 trace，运行态表只作为补充。

## 可复用教训

- 观测指标要先确认数据生命周期，再决定统计源。
- 临时表为 0 不等于系统没有生成过数据。
- 面向 24h 历史的指标应优先来自持久化快照、trace 或专门统计表。
- RAG 质量不能只看 chunk 数，必须结合 retrieval attempts、hit count、fallback reason、latency 和最终评分。
- 如果一张表会被生命周期清理，就不要把它当作历史指标的唯一事实源。
- 对“向量库里有数据，表里为什么没有”这类问题，要先区分长期资产、session-scoped cache、runtime chunk 和历史 artifact。

## 未解问题

- 后续是否需要为 session anchor RAG 建立单独的 materialized stats，避免从运行态表临时拼指标。
- Trace Explorer 是否应展示 session anchor 切片策略、召回输入、召回结果和最终题目之间的完整链路。
- 是否需要把 `setup_snapshot` 中的 vector status schema 固化为更明确的 API contract。
- 是否需要在 Admin 上标注每个字段来源：chunk table、setup snapshot、trace artifact。
- 普通完成链路是否真的清理 `session_anchor_chunks`，其策略是否按隐私/成本/性能明确记录在文档中。
