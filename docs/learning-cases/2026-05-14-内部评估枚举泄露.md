# 训练回放内部评估枚举泄露

> 日期：2026-05-14
> 状态：draft
> 标签：ai-interviewer, boundary, debugging

## 一句话结论

训练回放这类用户可见接口不能直接透传 evaluator 的内部控制枚举，必须在后端出口统一映射成用户文案或清空。

## 背景

当时正在改造训练回放页，让它展示完整回答、评分依据、追问依据、开场线索和本题依据。用户在真实跑一场面试后查看训练回放，发现每轮底部的“下一步练习”展示了 `refine`。

这个字段本意是告诉用户下一步如何练习，但实际使用的数据源来自 evaluator 的内部决策字段。

## 现象

### 事实

- 回放页“下一步练习”曾直接显示 `refine`。
- `refine / advance / skip` 是 evaluator/workflow 使用的内部决策枚举，不是用户文案。
- `session_replay._turn_payload()` 原先直接用 `evaluation.recommended_next` 生成 `ReplayTurn.next_step`。
- final report fallback 路径也会从 `evidence.recommended_next` 或 `evidence.recommended_next_plan` 生成 `next_step`。
- 已修复为后端统一调用 `_next_step_text(recommended_next, recommended_next_plan)`。

### 推断

- 直接原因是 replay API 把内部控制字段当成用户可见解释字段透传。
- 更深层原因是 replay payload 缺少“展示字段必须经过安全投影”的边界规则。
- 类似风险可能存在于 `recommended_next_plan`、`recommended_probe_intent`、`failure_reason` 等内部字段，如果它们未来进入用户可见 payload，也需要先映射成展示友好对象。

### 未确认假设

- 尚未做全局扫描确认所有前端用户可见字段都不会透传 evaluator 内部字段。
- 旧报告中是否存在只存 `recommended_next_plan` 且该字段是用户文案的样本，还需要基于真实数据继续确认。

## 期望行为

- 用户看到的是自然语言练习建议，而不是内部枚举。
- `refine` 根据 `recommended_next_plan` 映射为不同层级的中文建议。
- `advance` 和 `skip` 不展示“下一步练习”。
- `refine / advance / skip / simple / adaptive / deep_probe` 等内部枚举不得进入 `ReplayTurn.next_step`。
- 历史数据中如果本来存的是用户可读文案，例如“练习容量估算”，仍然兼容展示。

## 根因判断

直接原因：`ReplayTurn.next_step` 的生成逻辑复用了 `evaluation.recommended_next`，但该字段是 workflow 控制语义，不是用户文案。

深层原因：训练回放接口同时承担“调试/追踪数据消费”和“用户可见复盘展示”两种需求，但缺少明确的数据投影边界。内部字段进入用户可见模型时，需要经过后端确定性映射、过滤或结构化包装。

触发条件：evaluator 返回 `recommended_next = "refine"`，而 replay API 没有额外映射，前端又直接渲染 `turn.next_step`。

## 调试过程

1. 用户通过截图指出“下一步练习”展示了 `refine`，确认这是用户不可理解的内部决策词。
2. 检查 evaluator 语义，确认 `recommended_next` 的合法值是 `refine / advance / skip`。
3. 检查 replay API，发现 trace 路径和 report fallback 路径都可能把内部枚举放进 `next_step`。
4. 先补测试，让 trace 路径的 `refine + deep_probe`、`advance/skip` 和 report fallback 的 `refine + simple` 暴露失败。
5. 添加 `_next_step_text()`，统一处理映射、兼容和安全过滤。
6. 重跑 `backend/tests/unit/test_session_replay_api.py`，确认新增和既有用例通过。

## 解决方式

后端新增 `_next_step_text(recommended_next, recommended_next_plan)`：

- `refine + simple` 映射为“继续补充本题的基础信息和关键细节。”
- `refine + adaptive` 映射为“围绕本题薄弱点，补充更具体的过程、证据和结果。”
- `refine + deep_probe` 映射为“进一步深挖本题中的关键决策、指标、取舍或边界情况。”
- `refine` 但计划缺失时，映射为“围绕本题薄弱点继续补充细节。”
- `advance` 和 `skip` 返回空字符串，不展示“下一步练习”。
- 如果命中 `simple / adaptive / deep_probe` 这类内部 plan 枚举，也返回空字符串，避免 report fallback 中误透传。
- 非内部枚举且不是系统 fallback 文案的历史自由文本继续保留。

## 验证方式

- 新增 trace 路径测试：`refine + deep_probe` 返回中文文案，且 payload 中不包含 `refine` 或 `deep_probe`。
- 新增 trace 路径测试：`advance / skip` 返回空字符串，且 payload 中不包含对应枚举或 `adaptive`。
- 新增 report fallback 测试：`refine + simple` 返回中文文案，且 payload 中不包含 `refine` 或 `simple`。
- 回归命令：
  - `pytest backend/tests/unit/test_session_replay_api.py -q`
- 验证结果：
  - `22 passed`

## 可复用教训

- 用户可见字段不能直接消费 LLM/evaluator 的内部控制字段，即使字段名看起来像展示文案。
- replay 这类复盘接口要有明确的安全投影层：内部字段先映射成中文文案、展示友好对象，或直接清空。
- fallback 路径也要和主路径共用同一套投影规则，否则 trace 缺失时仍可能泄露内部语义。
- 测试不仅要断言“展示了正确文案”，还要断言“没有泄露内部枚举”。
- 兼容旧数据时要区分“历史自由文本”和“内部枚举”，不要为了安全过滤把已有用户文案清掉。

## 未解问题

- 是否需要对整个 `ReplayResponse` 做一次内部字段泄露审计，确认没有其他字段暴露 `recommended_probe_intent`、`failure_reason`、`focus_source` 等内部语义。
- 是否需要在 API schema 或文档中明确：`ReplayTurn.next_step` 是用户文案，不是 evaluator decision。
- 是否需要为前端增加 source test，防止未来直接渲染内部字段名。
