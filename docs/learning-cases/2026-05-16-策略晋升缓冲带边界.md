# 单场经验生成全局策略的过拟合边界 · signal 缓冲带与阈值晋升

> 日期：2026-05-16
> 状态：draft
> 标签：ai-interviewer, boundary, logic

## 一句话结论

学习系统里"单场经验生成全局策略"是危险的过拟合捷径——必须插一层 `strategy_signal` 缓冲带，按 `distinct_sessions` 阈值（30/100）分级晋升，禁止单用户数据直接改全局策略。

## 背景

2026-05-15 早上讨论"策略记忆 reward 闭环"时，AI 起初提议保留旧的 `experience_extractor → save_strategy()` 链路（即"posterior 达标就直接生成 active markdown 策略"）。用户提出"一个人的数据基本不够，甚至会误导"的反例，迫使 AI 把"posterior 直接生成策略"改成"posterior 先写 signal，多场聚合后晋升"。这条边界后来固化在 PR6（experience_extractor 改写 signals）+ PR7（promotion job），是 commit `538e7f1` 的核心约束。

## 现象

### 事实

- 改造前：`experience_extractor_node` 在面试结束后调用 `save_strategy()`，把 QA pattern（同维度分数恢复/下降）或 Bandit posterior（某 arm 的 mean_reward 达标）直接写成 `knowledge/strategy/auto_*.md`。
- 改造前的最低门槛只看单场 QA 模式或一个 context+action 的 `experience_min_observations`——一个用户的一场面试就可能生成一条 active 全局策略。
- 改造后：`experience_extractor` 只写 `strategy_signals` DB 表（含 `group_key / signal_type / score_before / score_after / score_delta / status='observed'`）。
- 改造后 `strategy_promotion.py::promote_strategy_signals()` 按 `group_key` 聚合 signals，必须满足以下硬阈值才能生成 `strategy_memories`：
  - `low_confidence` 启用：`distinct_sessions ≥ 30` + `avg_immediate_reward ≥ 0.68` + `avg_score_after ≥ 7.0` + `verifier_overrule_rate ≤ 0.20`
  - `stable` 启用：`distinct_sessions ≥ 100` + `avg_immediate_reward ≥ 0.72` + `verifier_overrule_rate ≤ 0.15`
- 改造后还增加了自动降权/禁用：`uses ≥ 30` 且 `avg_blended_reward < 0.55` 或 `verifier_overrule_rate > 0.35` 时自动 disabled / 降 confidence。

### 推断

- Bandit posterior 是"某 context+action 后验"，**不等于**"某条策略文本有效"——前者可作候选信号，后者需要 `strategy_memory_usage` 实证。改造前没区分这两件事。
- 旧路径的过拟合风险至少有四种来源叠加：候选人本身强 / 题目简单 / action 合适 / Evaluator 偏宽——任一原因都可能造成单场 reward 高，但不可归因到"策略起作用"。
- 30/100 阈值是经验值，源自"少量样本不更新全局行为"的工程直觉，没有经过 A/B 验证；可能在 cohort 差异较大的 dimension 上仍偏低或偏高。

### 未确认假设

- 当前 `distinct_sessions` 计数没有按 user_id 分桶——如果少数用户高频面试，可能伪装成"很多 distinct session"。session_id 与 user_id 的对应关系在隐私层是否需要保留以做防护，尚未敲定。
- 是否要按 dimension / job_level cohort 分别调阈值（例如 system_design 样本稀缺时 distinct_sessions ≥ 20 即可）——目前所有 cohort 用同一套阈值。
- 自动降权机制（`uses ≥ 30 且 avg_blended_reward < 0.55 → disabled`）在 seed 策略上是否过激——seed 策略可能初期 reward 低但长期价值高，目前没有"保护 seed 策略不被自动 disabled"的开关。

## 期望行为

- `experience_extractor` 在面试结束后只产 signal，不直接产 active strategy。
- 同一 `signal_key`（基于 `group_key + session_id` 派生）幂等去重，重复运行不重复写。
- promotion job 必须聚合到 `distinct_sessions ≥ 30` 才允许晋升 `low_confidence` 策略；100+ 才允许 `stable`。
- seed / manual 策略表现差时允许自动 disabled（但不删除），可被人工 re-enable。
- delayed reward 优先于 immediate reward 进入 `blended_reward` 计算（更接近真实结果）。

## 根因判断

直接原因：旧的 `save_strategy()` 路径把数值后验（"这 action 在该 context 下平均 reward 高"）直接翻译成 active 策略文本（"在该 context 下应该用 X"），中间缺少"多场样本聚合"和"覆盖率验证"两层。

深层原因：

- "经验提取"和"全局策略学习"是两个不同的抽象层——前者是单场观察，后者需要跨用户/跨场次/跨题型累计。旧实现把两者合并在同一个 node 里，导致单场观察直接成为全局规则。
- 缺少对"个性化适配 vs 全局学习"边界的明确划分——单用户数据可以做"当前场次追问 / 个人训练计划 / 个性化复习"，但不能做全局策略学习。

触发条件：早期为了让"AI 面试官有自我进化"卖点能跑起来，把闭环做得过紧——一场面试结束就立刻能看到"AI 学到了新策略"。代价是过拟合风险被忽略。

## 解决方式

新链路：

```
面试结束
  → experience_extractor 写 StrategySignal (status='observed')
  → promote_strategy_signals 后台 job
    → 按 group_key 聚合
    → distinct_sessions >= 30 + avg_reward >= 0.68 + ... → 生成 StrategyMemory (low_confidence)
    → distinct_sessions >= 100 + avg_reward >= 0.72 + ... → 升 stable
  → retrieve_strategies 时按 promotion_stage / confidence / support_count / avg_reward 软排序
```

降权链路：

```
strategy 启用后
  → strategy_memory_usage 累积 reward
  → strategy_memory_stats 聚合
  → uses >= 30 且 avg_blended_reward < 0.55 → confidence 降
  → uses >= 30 且 verifier_overrule_rate > 0.35 → disabled
  → seed / manual 策略允许 disabled 但不删除
```

## 可复用教训

- **任何"经验 → 全局规则"的转换都要插 signal 缓冲带**：单场观察不能直接成为全局策略。
- **阈值要分层**（draft / low_confidence / stable）配自动降权——光靠晋升不够，必须配套退出机制。
- **区分"个性化适配"和"全局策略学习"**：单用户数据只能做前者，后者必须跨用户聚合。
- **不要为了"AI 在学习"的视觉效果牺牲过拟合纪律**——一场面试结束就改全局策略很爽，但代价是早期高 reward 策略自我强化、压制探索。
- **数值后验 ≠ 策略文本有效**：Bandit posterior 学的是 context+action，不直接证明某条策略文本起作用；必须配 `strategy_memory_usage` 实证。
- **保护 seed 策略**：自动降权机制要区分 seed / promoted 来源，避免初期 reward 低但长期价值高的人工种子被误 disabled。

## 未解问题

- `distinct_sessions` 计数是否要按 user_id 分桶？少数用户高频面试会伪装成 distinct sessions。
- 阈值 30/100 在不同 cohort（dimension / job_level）上是否应该差异化？
- 自动降权机制在 seed 策略上是否过激？是否需要"seed 策略保护期"？
- 当前 `signal_key` 去重粒度是"group_key + session_id"——同一用户多场重复出现同模式时是否仍算独立 signal，没有去重？
- 是否要做"反向 sanity check"——promoted 策略产生后，检查它和 seed 策略冲突时谁优先？

## 扩展发现（2026-05-16 复盘后自检）

后续全 observe-only 路线自检发现，晋升缓冲带链路当时没有真实跑通：`strategy_signals / strategy_memory_usages / strategy_memory_stats` 均为空，且根因之一是 `strategy_memories=0`，seed 未导入。

完整数据真空诊断集中记录在 `2026-05-16-失败分类升档数据真空.md`。本案保留的独立教训是：**晋升机制不能只验证阈值逻辑，还要验证 active seed、usage、signal、stats 四段是否真的有数据流入。**
