# RAG 职责边界重划

> 日期：2026-05-21
> 状态：draft
> 标签：ai-interviewer, boundary, rag, architecture

## 一句话结论

RAG 不应该继续承担“题库/出题骨架”的职责；结构化题库负责“问什么”，skills/playbook 负责“怎么追、看什么信号”，RAG 只保留为 fallback、支持性知识、候选人锚点和可观察 artifact。

## 背景

AI 面试官早期把 RAG 作为一个宽泛能力接入 Generator：岗位题库、技术题、业务题、行为题、示例简历、skills 文档等都曾被视为可检索语料。这样做在原型阶段方便：有内容就能被向量库召回，Generator 能拿到一段 `retrieval_block` 继续出题。

但随着结构化题库、selector、usage、reward、skills playbook 逐步建立，继续让 Chroma/RAG 承担“题库功能”开始带来边界问题：题目骨架无法稳定受控，维度/岗位/job_level 对齐难以保证，命中结果不容易归因，出题质量到底来自 RAG 召回还是结构化题库也说不清。

因此本轮改造中，RAG 的角色被重新定义：它不再是题库，不再决定“问什么题”；题库由 YAML/DB 结构化 seed/variant 接管，playbook 决定追问方式，RAG 退到 fallback、支持性知识、候选人锚点和 artifact。

## 现象

### 事实

- README 中已有当前边界说明：RAG 不再拥有 question-bank 或 skills playbook 内容；默认出题由结构化题库负责，RAG 保留为 supporting knowledge、shadow artifact 和 fallback。
- RAG ingestion 已排除 legacy question/playbook 目录，包括：
  - `knowledge/tech_questions/`
  - `knowledge/business_questions/`
  - `knowledge/behavioral_questions/`
  - `knowledge/sample_resumes/`
  - `knowledge/skills/`
- `structured_primary_seed_hit=True` 时，Generator prompt 中的 legacy `retrieval_block` 应为空。
- seed miss、uncovered role 或 selector 失败时，RAG fallback 仍可进入 Generator prompt。
- skills/playbook 后续也从“RAG 可检索 Markdown”转为结构化 playbook registry，并进一步准备 DB-backed runtime。
- 候选人锚点 RAG 是后续重新赋予 RAG 的新职责：它服务候选人简历/自我介绍的 session-scoped semantic anchors，不是题库 RAG 的回归。

### 推断

- 早期 RAG 角色过宽，是因为系统还没有结构化题库和 playbook 分层，Generator 只能从一个宽泛 `retrieval_block` 中拿上下文。
- 当结构化题库接管出题骨架后，如果 Chroma 仍召回 legacy 题库 markdown，会形成双重出题来源：selector 选一个 seed，RAG 又给另一个题库语料，Generator 可能混合两者，导致主链路控制权不稳定。
- 如果 skills 仍留在向量库，playbook 的选择也会从规则 selector 退回语义召回，难以稳定解释“为什么这一轮注入这张卡”。

### 未确认假设

- 本文没有逐行复核当前 `_iter_documents()` 的所有排除规则，只依据会话决策、README 线索和测试线索总结。
- README 中仍存在一些历史描述，例如“使用本地 Chroma 知识库做 RAG 检索”“技术题库/业务题库目录”等；这些可能需要后续文档清理，避免新读者误解当前架构。
- 当前是否已有新的“支持性知识目录”投入 RAG，本文未验证；如果没有，legacy Chroma 可能暂时处于低内容或空内容状态。

## 期望行为

RAG、结构化题库、skills/playbook 三者边界应保持清楚：

- 结构化题库：
  - 决定“问什么”。
  - 维护 seed/variant。
  - 对齐 direction / role / dimension / job_level。
  - 记录 usage、injected、reward attribution。

- Skills Playbook：
  - 决定“怎么追”。
  - 提供 `generator_moves`、`watch_for`、`avoid`。
  - 预留 evaluator hints，但不默认进入 Evaluator runtime。
  - 通过规则 selector / DB registry 注入，不依赖 Chroma 语义召回。

- RAG：
  - 不再承担题库或 playbook 语料。
  - 在 structured primary seed hit 时不进入 Generator 的 legacy `retrieval_block`。
  - 在 seed miss / uncovered role / selector failure 时作为 fallback。
  - 可作为 supporting knowledge 或 candidate/session anchor 的检索能力。
  - 可以写入 artifact，供 Admin/replay/debug 观察。

## 根因判断

直接原因：RAG 早期被当作通用“内容注入器”，题库、skills、示例简历、岗位知识都可以进入同一个检索管道，导致 `retrieval_block` 同时承担出题、提示、补充知识和 fallback 多种职责。

深层原因：

- 在没有结构化题库时，RAG 是最快的内容接入方式；但它的灵活性也掩盖了出题控制权不稳定的问题。
- 向量召回适合“找相关信息”，不适合承担“按岗位/维度/等级稳定选择出题骨架”的职责。
- 题库和 playbook 都是高度结构化、需要可解释选择和可审计变更的内容；继续放在 Chroma 中，会削弱 selector、lint、Admin、usage、reward attribution 的闭环。
- `retrieval_block` 作为一个宽泛 prompt slot，容易让不同来源的内容互相污染：题库 prompt、技能提示、候选人锚点、支持知识都可能混在一起。

## 调试过程

1. P0/P1.1 阶段先把结构化题库以 shadow 方式接入，避免直接改变 RAG 出题行为。
2. 后续扩展岗位和维度覆盖，并修复题库与主链路维度对齐问题。
3. 用户进一步提出要“砍掉 RAG 的题库功能”，让结构化题库进入主链路。
4. 改造方向确定为 RAG Role Demotion：
   - 默认 `question_selector_mode=structured_primary`。
   - covered role seed hit 时注入 `question_seed_block`。
   - seed hit 时 legacy `retrieval_block=""`。
   - seed miss / uncovered role fallback 到 RAG。
5. 继续清理 skills：
   - `skills/*` 不再作为 Chroma 语料。
   - 改成结构化 playbook selector。
   - 后续落到 `skill_playbook_cards` DB 表。
6. 再往后，RAG 重新找到更合适的职责：候选人锚点 RAG，用于 session-scoped resume/self-intro semantic anchors，而不是通用题库。

## 解决方式

已经采取的方向性修复：

- RAG ingestion 默认排除 legacy 题库与 skills/playbook 目录。
- `rag_mode` 保持只表示 vector/hybrid 检索算法，不再混入结构化题库语义。
- `question_selector_mode` 独立表达出题控制权：
  - `vector`
  - `structured_shadow`
  - `structured_primary`
- `structured_primary` seed hit 时：
  - Generator 使用 `question_seed_block`。
  - 可同时使用 `candidate_anchor_block` 和 skills block。
  - legacy `retrieval_block` 不进入 prompt。
- seed miss / uncovered role / selector error 时：
  - 保留 RAG fallback，不让面试断流。
- Skills playbook 迁出 RAG：
  - Markdown 作为内容权威源。
  - DB 作为 runtime / Admin 观察存储。
  - 规则 selector 选择 top cards。

## 验证方式

现有验证方向：

- Workflow：
  - seed hit 时 `retrieval_block=""`。
  - seed miss 时 `retrieval_block` 继续传入 Generator。
  - `structured_shadow` 不改变 prompt。
  - `vector` 模式保持旧行为。
- RAG ingestion：
  - legacy question dirs / sample resumes / skills 不再作为 RAG 语料进入索引。
  - Admin knowledge coverage 不再把这些目录算作 RAG coverage。
- Skills playbook：
  - file backend / DB backend 都能提供同形状 `SkillEntry`。
  - Generator skills block 来自 playbook selector，而不是 Chroma。
- Candidate/session anchor RAG：
  - 作为独立职责，用 `RESUME_RAG_MODE` 控制 shadow/primary/off。
  - 与 legacy `retrieval_block` 的题库 RAG 角色区分。

## 可复用教训

- RAG 是检索能力，不是天然的题库系统。
- 如果内容需要稳定路由、审核、版本、usage、reward attribution，就应该结构化建模，而不是依赖向量召回。
- 一个 prompt slot 如果承载太多来源，最终会让职责边界和效果归因都变模糊。
- “RAG 降级”不等于删除 RAG；它是把 RAG 从不适合的职责中移走，让它服务更适合的语义检索场景。
- 对 AI 面试官来说：
  - 结构化题库解决出题骨架。
  - Playbook 解决追问策略。
  - Candidate/session anchor RAG 解决候选人经历语义召回。
  - 支持性知识 RAG 只有在有干净知识目录时才值得进入。
- 清理文档和 Admin coverage 很重要；否则旧 README 或旧目录名会让后续维护者以为 RAG 仍负责题库。
