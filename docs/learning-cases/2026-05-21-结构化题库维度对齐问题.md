# 结构化题库维度对齐问题

> 日期：2026-05-21
> 状态：draft
> 标签：ai-interviewer, boundary, debugging, question-bank

## 一句话结论

结构化题库的 `seed.dimension` 必须服从面试主链路正在考察的 `current_dimension`；如果题库自己发明或沿用另一套内容维度，即使 seed/variant 数量充足，真实面试里的 structured selector 也会因为维度错位而空转。

## 背景

本轮会话围绕 AI 面试官的 RAG 降级、结构化题库接管出题、策略记忆、skills playbook 等模块做了多批改造。结构化题库最初以 shadow mode 进入主链路：在不改变 Generator 出题行为的前提下，selector 选择 top candidates，写入 `selection_artifacts.question_items` 和 `QuestionUsage`，再逐步走向 `structured_primary`。

后续用户跑真实 Java 后端面试 session 后发现，结构化题库增强并没有稳定发挥作用。进一步追问后暴露出关键问题：题库内容曾集中在 `system_design` 和一个题库侧维度 `backend_systems`，但真实面试主链路当前考察的是 `interview_directions.json` 中 Java 后端的维度目录，例如 `technical_depth`、`problem_solving`、`coding_quality`、`project_experience`、`communication` 等。

## 现象

### 事实

- 结构化题库 shadow/primary 选择逻辑依赖当前轮次 `dimension`。
- 用户明确指出：`seed.dimension` 必须对齐当前面试主链路正在考察的 `current_dimension`，不能由题库侧另行发明维度。
- 当前源码中，`interview_directions.json` 是岗位维度目录来源之一，Java 后端等岗位都有 `dimension_catalog`。
- 后续修复提交包含：
  - `ffbfbc6 feat: align structured question bank with interview main pipeline`
  - `cf305ed feat: expand ai-track question bank density to spec`
  - `a9dd5c7 feat: expand non-ai-track question bank density to spec`
  - `4721a36 feat: prefer seed-diverse top-k in question selector`
  - `e1b85a9 feat: promote structured question bank primary coverage`
- 当前源码中，`question_selector_mode` 默认已是 `structured_primary`，并保留 `structured_shadow` / `vector` 作为回滚开关。
- `backend_systems` 在后续 alignment fix 中不再应作为 active 题库维度，而只适合作为 `skill_tags` / `scenario_skill_tags` 一类内容标签。

### 推断

- 初期 P0/P1.1 验收更偏向“import 成功、selector 能选、workflow 能写 artifact”，但没有充分覆盖“真实岗位 setup 下 director 选出的每个 current_dimension 是否都有对应 active seed”。
- `backend_systems` 之所以容易混入，是因为它从内容组织角度看很自然：Java 后端确实有事务、数据库、异步任务、接口幂等、事故定位等主题。但从主链路看，它不是 director/reward/strategy memory 使用的维度 key。
- 真实 session 暴露问题，是因为 runtime 最终按主链路维度路由，而不是按题库作者心中的知识分类路由。

### 未确认假设

- 本文没有重新查询触发问题的完整 DB trace；会话中提到的真实 session 线索包括 `sess-20260516-164341-53c84a`，但本文未逐 turn 复核 `current_dimension`、`question_items`、`QuestionUsage`。
- 旧 `backend_systems.*` seed 的完整迁移前后 diff 未在本文中逐条列出，只记录方向性结论。
- 非 Java 岗位后续是否还有类似“内容主题合理但主链路维度不一致”的残留，需要继续用覆盖 lint 和真实 session 验证。

## 期望行为

结构化题库进入主链路时，题库维度必须是“主链路路由键”，不是“内容分类名”。

理想状态：

- `QuestionSeed.dimension` 只使用当前岗位 `dimension_catalog` 中已经存在的维度。
- selector 在 `current_dimension + role_tags + direction_tags + job_level` 下能稳定返回候选。
- 如果某岗位某维度没有 active seed，要在 lint 或 Admin 覆盖矩阵中暴露，而不是等真实面试时 shadow 空转。
- reward、strategy memory、verifier drift、final report 等下游模块继续按同一套 dimension key 归因，不被题库侧维度污染。

## 根因判断

直接原因：结构化题库早期把部分内容主题建成了题库侧 dimension，例如 `backend_systems`。这个维度在内容上合理，但和面试主链路的 `current_dimension` 不一致，导致 selector 在真实轮次维度下找不到或找不全候选。

深层原因：

- 把“题库怎么组织内容”和“面试主链路怎么路由、归因、评分”混成了一件事。
- P0 shadow 验收没有强制要求“岗位主链路维度全覆盖”，导致单点测试通过但真实链路仍可能空转。
- `dimension` 这个字段承载了多个系统约定：director 选题、selector 过滤、reward key、strategy memory、报告维度。题库一旦写入非主链路维度，就不是局部内容问题，而是跨模块契约问题。

触发条件：

- 结构化题库从 shadow 逐步靠近主链路。
- RAG 题库功能被降级，结构化题库开始承担“问什么”的责任。
- 用户用真实 session 验证，而不是只看 YAML 数量或单元测试。

## 调试过程

1. 用户跑真实 Java 后端面试，要求验证“结构化题库增强是否起作用”。
2. 初步分析发现，结构化题库候选主要集中在 `system_design` / `backend_systems`，而真实轮次存在其它维度。
3. 用户追问“维度和面试主链路选的维度有什么关联”，进一步指出题库 `seed.dimension` 必须对齐 `current_dimension`。
4. 修复路线改为先做 Java 后端 alignment：以 `java_backend.dimension_catalog` 为唯一维度来源，移除 active `backend_systems` 题库维度，迁移相关 seed 到 `technical_depth`、`problem_solving`、`coding_quality` 等主链路维度。
5. 后续扩展到其它技术岗位 alignment / density，并加入 coverage lint，确保 active seed 不使用岗位目录外维度，非架构技术岗位覆盖 `junior/mid/senior`。
6. 在 RAG Role Demotion 后，结构化题库正式接管出题主链路，RAG 降为 fallback / 支持性知识 / artifact。

## 解决方式

已采取的方向性修复包括：

- Java 后端题库对齐 `interview_directions.json` 中的主链路维度。
- `backend_systems` 不再作为 active 题库维度，只保留为技能/场景标签。
- 增加 Java 后端与其它技术岗位的 alignment lint：
  - active seed 使用岗位目录外维度时失败。
  - 主链路维度缺覆盖时失败。
  - 非架构技术岗位缺 `junior/mid/senior` 覆盖时失败。
  - 每个 active seed 至少需要足够 variant 密度。
- 后续补充 density，使非 Java 技术岗位不只是“每维非空”，而是有更可用的内容密度。
- `structured_primary` 接管主链路时，仍保留 `structured_shadow` / `vector` 回滚开关。

## 验证方式

本轮会话中已经做过多批 targeted 验证，本文只记录与本问题相关的验证方向：

- import/lint：
  - bundled YAML strict import 通过。
  - active seed 维度必须属于岗位主链路维度目录。
  - 旧 extra dimension seed 通过 `--archive-missing` 归档，不继续 active。
- selector：
  - `job_level=junior` 下，Java 后端和其它非架构技术岗位在各自主链路维度返回非空 candidates。
  - 返回结果不包含岗位目录外维度。
  - `match_reasons` 保留 `role_tag:<role>` 与 `direction_tag:<direction>`。
- workflow：
  - `structured_shadow` 写入 `question_items` 和 `QuestionUsage`，不改变 prompt。
  - `structured_primary` 在 seed hit 时注入 `question_seed_block`，seed miss / uncovered role fallback 到 RAG。
  - reward update 只回填真正 injected 的 rank1 usage。

## 可复用教训

- 内容系统接主链路时，第一优先级不是“内容多不多”，而是“路由键是否和主链路一致”。
- `dimension`、`role`、`job_level` 这类字段如果同时被 director、selector、reward、strategy memory、report 消费，就必须当作跨模块契约，不能让某个内容模块自行解释。
- shadow mode 的验收不能只看“有没有写 artifact”，还要看真实 session 中每个 `current_dimension` 是否能稳定命中。
- lint 要覆盖“目录外维度”和“岗位主链路维度缺口”；否则题库越扩，错位越隐蔽。
- 合理的内容分类不一定是合理的系统维度。`backend_systems` 适合做 tag，不适合做主链路 dimension。
- 当 RAG 从题库角色降级后，结构化题库的覆盖缺口会变成主链路风险，不能再依赖向量库“碰巧召回”来兜底质量。

## 未解决问题

- 是否需要一个自动化的 session replay 验收脚本，输入岗位和 job_level 后，逐个主链路维度断言 structured selector 能返回候选？
- Admin 是否应直接展示“岗位 × 维度 × job_level”的 coverage matrix，并标出 structured_primary 是否允许注入？
- 当前 business / service / management 方向是否也存在“内容主题合理但主链路维度覆盖不够”的问题，尚需真实 session 验证。
- 如果后续 `interview_directions/job_templates` DB registry 化，如何保证 question seed lint 读取的是同一份 registry，而不是再次出现配置双源？
