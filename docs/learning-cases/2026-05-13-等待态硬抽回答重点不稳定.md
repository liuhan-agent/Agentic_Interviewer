# 等待态硬抽回答重点不稳定

> 日期：2026-05-13
> 状态：draft
> 标签：ai-interviewer, ux, frontend, waiting-state

## 一句话结论

等待态不适合展示“从用户回答里硬抽出来的已捕捉重点”，除非有稳定结构化来源，否则很容易显得潦草、错位或误导。

## 背景

AI 面试官生成下一题耗时较长。为了让用户等待时不焦虑，等待面板曾尝试展示上一轮回答的简短信息，包括“刚才你提到”或“已捕捉重点”一类内容。

## 现象

### 事实

- 用户反馈“展示内容这一块没成功”，并指出“已捕捉重点”显得潦草。
- 用户指出“上一题的反馈”似乎错位。
- 开场介绍、普通问题、最后一题提交后的等待目标不同：
  - 开场介绍后是在组织第一道正式问题。
  - 普通问题后是在生成下一题。
  - 最后一题后是在整理整场面试总结。
- 后续方案改为展示固定“面试小贴士”，按 `self_intro`、`final`、当前维度、`default` 选择文案。

### 推断

- 前端从用户回答中轻量截取或抽取关键词，无法稳定代表回答重点。
- “已捕捉重点”这类措辞会让用户以为系统已经理解并总结了回答，但实际上只是轻量规则或局部文本处理。
- 当等待面板、上一题反馈、历史回答同时出现时，如果没有严格 turn 对齐，很容易产生“反馈属于哪一题”的认知错位。

### 未确认假设

- 错位反馈的具体数据路径尚未在 trace 或日志中完全复盘。
- 如果未来后端能返回结构化的“本轮考察点 / 追问依据 / 反馈摘要”，等待态是否可以重新展示更具体内容，尚未验证。

## 期望行为

- 等待态可以降低焦虑，但不应假装已经完成了高质量理解。
- 等待文案应该低承诺、稳定、可解释。
- 开场介绍、普通问题、最终总结应使用不同语义，不能统一套“已捕捉重点”。
- 如果展示和上一轮回答相关的内容，必须有明确结构化来源和 turn 对齐。

## 根因判断

直接原因：

- 等待面板试图从用户回答中生成“有价值内容”，但前端没有模型理解能力，也没有稳定结构化字段可用。
- 轻量抽取结果容易只呈现局部词汇，无法覆盖回答里的真实重点。

深层原因：

- 等待态 UI 的职责边界不清：它应该解释“系统正在做什么”和提供低风险提示，而不是承担“总结用户回答”的职责。
- “看起来更智能”的展示可能提升短期观感，但一旦内容不准，比空白等待更伤信任。

触发条件：

- 用户回答较长、信息密度较高。
- 当前题目属于开场介绍或最终总结等特殊阶段。
- 页面同时展示历史回答、上一题反馈和 loading 面板。

## 调试过程

1. 先确认用户不希望等待面板继续展示粗糙的回答摘录或“已捕捉重点”。
2. 讨论是否需要修改 AI 面试官输出结构，结论是 v1 不改后端出题链路。
3. 确认前端能拿到维度标签，因此可以用维度驱动稳定小贴士。
4. 设计并实现“后端给文案池，前端负责轮换、去重、兜底”的方案。
5. 将开场介绍、普通问题、最终总结拆成不同展示语义。

## 解决方式

- 移除从用户回答中硬抽重点的展示方式。
- 等待面板改为展示：
  - 当前阶段文案。
  - 本轮考察维度。
  - 固定文案池中的面试小贴士。
- 后端新增等待小贴士文案池接口，前端在面试开始或等待首次出现时拉取一次。
- 前端按 scope 选择文案：
  - `self_intro`
  - `final`
  - 当前维度
  - `default`

## 验证方式

- 前端 source tests 覆盖 `NextQuestionLoader` 的阶段文案、小贴士接口、轮换逻辑。
- 后端测试覆盖 waiting tips catalog 的解析、接口契约和维度覆盖。
- 类型检查通过：`npm run typecheck`

## 可复用教训

- 等待态展示要谨慎区分“状态解释”“提示建议”和“内容理解”。没有结构化证据时，不要展示像理解结论的内容。
- 对 LLM 产品来说，低承诺但稳定的文案，通常比高承诺但不准的“智能摘要”更可信。
- 开场、普通题、最终总结是不同状态，UI 文案必须按状态拆开。
- 如果未来要展示“AI 已理解你的回答”，最好由后端结构化产物提供，并和 turn 明确绑定。

## 未解问题

- 尚未彻底复盘“上一题反馈错位”的数据层根因。
- 未来是否引入后端结构化追问依据，用于更具体的等待态提示，仍待设计。
