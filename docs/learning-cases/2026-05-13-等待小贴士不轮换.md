# 等待小贴士不轮换

> 日期：2026-05-13
> 状态：draft
> 标签：ai-interviewer, ux, frontend, waiting-state

## 一句话结论

等待 UI 的“小贴士会轮换”不能只依赖定时器，还必须保证同 scope 文案数量足够，并且选择算法不会在候选耗尽后固定回到同一条。

## 背景

AI 面试官出题等待时间可能超过 1 分钟。为降低用户等待焦虑，等待面板从“从回答中抽取重点”改为展示“面试小贴士”，由后端提供文案池，前端按当前场景和维度轮换展示。

## 现象

### 事实

- 用户截图显示等待面板已用时 42s，但“面试小贴士”仍停留在同一条。
- 当时业务维度 scope 每个只补了 1 条小贴士。
- 前端 `selectNextWaitingTip` 的逻辑是先取未展示过的 tip；当候选都展示过之后，回退到 `candidates[0]`。
- 修复后补充了后端测试，要求所有配置维度至少有 2 条小贴士。

### 推断

- 对只有 1 条文案的业务维度，定时器即使正常触发，也只能再次选择同一条。
- 对有 2 条以上文案的维度，如果这些文案之前都展示过，旧逻辑也可能固定回到第一条，造成“轮换卡住”的感知。

### 未确认假设

- 真实浏览器中是否还存在 React effect 依赖导致 interval 被频繁重建的问题，尚未用 Playwright 长等待截图验证。

## 期望行为

- 等待超过 10 秒时，小贴士应尽量切换到另一条。
- 同一轮等待中不应连续显示完全相同的小贴士，除非该 scope 确实只有 1 条可用文案。
- 新增面试维度时，测试应提醒同步补充足够的小贴士。

## 根因判断

直接原因：

- 部分业务维度 scope 只有 1 条文案，没有可切换目标。
- 前端选择器在候选耗尽后回到第一条，未避开当前正在显示的 tip。

深层原因：

- “文案覆盖所有维度”和“每个维度至少可轮换”是两个不同约束，最初只验证了前者。
- 对“轮换”的测试只覆盖了存在定时器和去重入口，没有覆盖候选耗尽后的连续展示行为。

触发条件：

- 用户等待时间超过一个轮换周期。
- 当前维度的文案数量不足，或该维度文案在本会话中已经全部展示过。

## 调试过程

1. 先检查 `NextQuestionLoader` 的定时器和 `selectNextWaitingTip`。
2. 统计 `interview_waiting_tips.json` 中每个 scope 的文案数量，发现大量业务维度只有 1 条。
3. 确认旧选择器在 `unused.length === 0` 时使用 `candidates`，并返回第一条。
4. 增加测试，要求所有配置维度至少有 2 条文案，并要求选择下一条时避开当前 tip。

## 解决方式

- 为所有业务维度补充第二条小贴士。
- 修改前端选择器，传入 `currentTipId`，优先返回不同于当前 tip 的候选项。
- 增加测试：
  - 所有配置维度都有小贴士 scope。
  - 所有配置维度至少有 2 条小贴士。
  - 前端选择器存在避开当前 tip 的逻辑。

## 可复用教训

- UI 文案轮换类功能要同时验证“定时器存在”“候选池足够”“选择器不会连续返回同一项”。
- 覆盖率测试不要只问“有没有 scope”，还要问“这个 scope 是否有足够内容支撑体验承诺”。
- 当文案池由后端提供、前端负责轮换时，后端测试也要守住最小内容质量门槛。

## 未解问题

- 尚未用浏览器自动化验证 30s 或 60s 长等待下的真实视觉轮换。
- 当前轮换策略仍是确定性选择，未来是否需要随机化或按会话种子打散，暂未决定。
